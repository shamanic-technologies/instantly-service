# Replies, qualification, opt-outs, clicks

Detail for the reply pipeline (`reply-kind.ts`, `lead-optouts.ts`, `reply-opt-out.ts`, `reply-qualification-fallback.ts`, `manual-qualifications.ts`, `stop-on-click*.ts`, click classification, forwarding, responder). Root CLAUDE.md points here; read before touching those files.

## Reply kind (`src/lib/reply-kind.ts`, single source of the vocabulary)
- Answers one question: what did the prospect send back. **Nothing about the deal**: `lead_meeting_booked` / `lead_closed` are lead-outcome facts owned elsewhere (they shared one statement per lead with sentiment and one overwrote the other). Do NOT put a deal-progress value back and do NOT record deal outcomes here.
- Kinds: positive `lead_interested`, `lead_referral` (not them, relevant, hands us the right person), `lead_info_requested`, `lead_meeting_requested` (a REPLY fact, not `lead_meeting_booked`); negative `lead_not_interested` (about the MOMENT, recyclable), `lead_wrong_person`, `lead_changed_job` (objective facts about the PERSON, DISQUALIFYING; never collapse `lead_changed_job` into a sibling), `lead_opt_out_requested` (below); neutral `lead_neutral`; automated `lead_out_of_office`, `auto_reply_received` (never stop the sequence, RFC 3834). No reply = absence of an event, not a writable value.
- **Legacy `lead_meeting_booked`/`lead_closed` are still ACCEPTED on `POST /orgs/manual-qualifications` and resolved at WRITE to `lead_interested`** (`resolveReplyKind`; throws on anything else). Bronze `instantly_manual_qualifications_raw.status` keeps the raw click; `reply_kind` column (migration `0039`, appends a resolved `lead_interested` silver event per legacy statement, never rewrites) freezes the resolution. `GET` returns both. `promoteEvent` resolves Instantly deal-progress at the single ingestion choke point (poll `lt_interest_status` 2/3/4 to `lead_interested`).
- **A referral FORWARDS but reports NEUTRAL, by design**: `REPLY_KIND_CLASSIFICATION` projects `lead_referral` to `neutral` while `POSITIVE_REPLY_KINDS` (forward set) keeps it; a test asserts the DIVERGENCE. The coarse value reaches email-gateway, lead-service, features-service as positive-reply count and cost, so a referral must not price as sales interest. Three surfaces move together: `REPLY_KIND_CLASSIFICATION`, `buildRepliesFromDetail` (`repliesPositive`/`repliesNeutral`), `timeToFirstPositiveReply` SQL. Migration `0042` back-derived classification for referral rows. `REPLY_CLASSIFICATION_MAP` re-exports `REPLY_KIND_CLASSIFICATION`; `SENTIMENT_EVENT_TYPES`, `POSITIVE_QUALIFICATION_EVENT_TYPES`, self-send `QUALIFICATION_EVENT_TYPES` stay one list.
- `repliesDetail` adds `referral`/`infoRequested`/`meetingRequested`/`changedJob` and emits `meetingBooked`/`closed` as hard `0` (required by contract `RepliesDetail` until v2). `repliesPositive` = interested + infoRequested + meetingRequested.

## Disqualified vs recyclable (status read)
`POST /orgs/status` emits additive `replyKind` (null when none) and `disqualified` (`replyKind in DISQUALIFYING_REPLY_KINDS`: `lead_wrong_person`, `lead_changed_job`, `lead_opt_out_requested`) on every StatusScope. **`disqualified` is STRICTLY a function of `replyKind`, never an independent aggregate** (brand scope takes `replyKind` from the same campaign row that wins `replyClassification`). `REPLY_KIND_CLASSIFICATION` is unchanged: all negatives still project to `negative`. Stored on gold `instantly_lead_status_current.reply_kind` (migration `0047`, derived in `refreshLeadStatusCurrent`): a standing human statement wins OUTRIGHT (`ORDER BY (k.source='manual') DESC, k.timestamp DESC`), withdrawn statements skipped. Guards: `status.test.ts`, `reply-kind.test.ts`, `status-gold-reply-kind.test.ts`.

## Recorded opt-out (`POST /orgs/opt-outs`, `src/lib/lead-optouts.ts`, `src/routes/lead-optouts.ts`, bronze `instantly_lead_optouts_raw` + `instantly_lead_optout_withdrawals`, migration `0047`)
- **NEVER inferred**: a named staff member stated a named person asked to stop through a named, REQUIRED, closed-vocabulary `channel` (`sms`, `phone_call`, `email_reply`, `forwarded_thread`, `in_person`, `web_form`, `other`). Readable forever via `GET /orgs/opt-outs`.
- **It STOPS THE SENDING**: `promoteEvent` promotes the same real `lead_unsubscribed` (stops sequence, cancels holds, `delivery_status='unsubscribed'`) but that tells the sender nothing, so it ALSO pauses the Instantly campaign (or `stopSelfSendSequence` on `self:`), like manual qualification.
- **Scope is the PERSON** `(org_id, lead_email)`, every campaign the org holds for the address (request body has no `campaign_id`). Same event type as a clicked unsubscribe, so gold/`/orgs/status` need no second branch. **Address matched `lower()` everywhere** (`normalizeLeadEmail`, shared with the re-contact window and serve path); stored row keeps original casing.
- **Withdrawable**: `POST /orgs/opt-outs/withdrawals` appends a withdrawal, marks only the `lead_unsubscribed` events THIS record promoted (`source='manual'` + `source_row_id`) `withdrawn_at`; `refreshLeadStatusCurrent` joins `AND (e.event_type <> 'lead_unsubscribed' OR e.withdrawn_at IS NULL)`, scoped to that event type on purpose (withdrawing a reply qualification must not retract that a reply arrived). A clicked unsubscribe is never touched. **A withdrawal does NOT resume stopped sequences** (a new send is a new decision).
- **`GET /orgs/opt-outs` is UNBOUNDED BY DEFAULT (no `limit` default or ceiling); do NOT restore one.** human-service gates every serve on it and refuses to serve when the set may be truncated (the old 200/500 cap would have blocked the first org past 500). Explicit `limit` still pages.
- **A recorded opt-out refuses future sends**: `POST /orgs/send` gates on it (409 `lead_opted_out`) BEFORE the re-contact window (a timing rule expires, consent never does). ORG-scoped. Fail loud. retry-stuck and the self-send worker are not gated. Idempotent: standing record writes nothing, second withdrawal = 404 `no_standing_optout`; the bronze record is written even with no campaign (`campaignsAffected: 0`); an unpausable campaign is logged and counted in `campaignsStopped`.
- Guards: `lead-optouts.test.ts` (incl. unbounded-read), `lead-optouts-route.test.ts`.

## A reply that ASKS to stop (`lead_opt_out_requested`, `src/lib/reply-opt-out.ts`)
Instantly filed "please remove me" replies as `lead_not_interested` (the recyclable bucket). Prod 2026-09-17: 7 explicit removal requests, 0 `lead_unsubscribed`, one on an active campaign; all on the `instantly` transport.
- `lead_opt_out_requested` is a NEGATIVE, DISQUALIFYING kind. **Deliberately ABSENT from `SENTIMENT_EVENT_TYPES` (`routes/analytics.ts`): adding it double-counts** (the kind plus the promoted `lead_unsubscribed`, which `repliesDetail.unsubscribe` already sums into `repliesNegative`). Do NOT "restore the lockstep"; gold `reply_kind` reads the whole vocabulary.
- **Routes through `recordLeadOptOut`**, not a direct promotion (person scope, sender pause, withdrawal, consent log). It is NOT the inference `lead-optouts.ts` bans: the prospect states it in words, stored on the record (`statedBy: "reply-classifier"`, `channel: "email_reply"`, sentence in `notes`).
- **The `promoteEvent` hook is gated on `MIRRORED_INBOUND_EVENT_TYPES`, not `reply_received` alone, and runs AFTER `maybeMirrorCampaignEmails`** (mirror puts the words in bronze; ordering test). Several attempts, each one cheap read; `recordLeadOptOut` idempotent per (org, lead); a standing opt-out short-circuits before the model call. `self:` sequences are skipped (the IMAP poller passes its classification, `PollSummary.optOutsRecorded`).
- **NO regex pre-filter anywhere on this path** (a removal request is a sentence; a miss is legally consequential). The prompt ignores our own quoted footer. Prompt pins worked examples (a test asserts they stay): "Stop", "Unsubscribe", "unsusbsribe", "No interest, please stop sending emails." are opt-outs; "Not for us, thanks." and bare "No interest" are not (`SYSTEM_PROMPT` exported only for that guard).
- Fail-soft at callers (`maybeRecordOptOutFromReply` swallows inside the webhook; 5xx counts toward Instantly disabling the subscription), fail-loud in the module (`recordOptOutFromReply` throws). Unusable classification records nothing.
- Backfill `POST /internal/audit/reply-optout-backfill` (`src/lib/reply-optout-backfill.ts`, `dryRun` default TRUE, NAMES the leads; excludes `self:`/`reserving:` and already-opted-out). Hook fires on a reply EVENT only; `inbound-replies-backfill` covers the rest. Opt-out is org-scoped (cross-brand suppression is human-service policy).

## A reply Instantly gave NO verdict on (`src/lib/reply-qualification-fallback.ts`)
Every reply side effect gates on the reply KIND (forward, funded-leg trigger, follow-up debt, rep call, opt-out). On the `instantly` transport that comes from Instantly's own qualification event; when it never arrives nothing happens and nothing says so (2026-09-21: 2 of 8 replies unqualified, one was "STOP!"). The fallback classifies with our own classifier and promotes via `promoteEvent` (re-opens every gate, no side effect reimplemented).
- **Grace `QUALIFICATION_GRACE_MS` = 15 min (measured: of 84 pairs 70 within 60s, 74 within 15 min); floor `QUALIFICATION_MAX_AGE_MS` = 7 days.** Both bounds load-bearing: promoting rings the rep, triggers the funded leg and files follow-up debt, all claiming the buyer is waiting NOW (first prod sweep promoted a 2026-07-08 reply). The floor also ends an unbounded retry. Cost of early speech accepted (~7%).
- Candidate gate = absence of EVERY kind (an out-of-office has a verdict); excludes `self:` and `reserving:`. **The mirror is re-run first** (a reply webhook can beat Instantly's `/emails`; its retry is gated on a later inbound event that never comes). No body = no classification; no bronze id = no promotion. `source: 'emails_backfill'` (NOT `poll_emails`, which means Instantly's own verdict). Event carries the REPLY's timestamp. Fail-loud per reply, idempotent.
- In-process interval `reply-qualification-worker.ts` (5 min), **NO kill switch** (the only path that qualifies such a reply; unqualified logs nothing). `POST /internal/audit/qualify-unanswered-replies` hand-run (`dryRun` default TRUE, names the leads). Guard `reply-qualification-fallback.test.ts`.

## Manual qualification (`POST /orgs/manual-qualifications`, `src/lib/manual-qualifications.ts`)
Exists because Instantly did NOT detect the reply, so its stop-on-reply never fires. `applyManualQualificationSideEffects` ALSO pauses the Instantly campaign (`pauseSequenceOnInstantly`); the holds are our ledger, the pause stops the real email.
- **ONE predicate gates BOTH halves: `isSequenceStoppingQualification`** (resolves to a kind, then `isSequenceStoppingReplyKind`; `SEQUENCE_STOPPING_REPLY_KINDS` = all positive + negative + `lead_neutral`; `lead_out_of_office` and `auto_reply_received` EXCLUDED). Gating one half is the bug. Guard `manual-qualifications-side-effects.test.ts`.
- **Minimal, like stop-on-click: ONLY pause on Instantly.** No local `status='paused'`, no cost-cancel, no contact-delete: nightly reconcile's `finish` closure does it; marking the row terminal makes `reconcileAll` skip it and leaks holds. Fail-soft (errors logged, row already committed). Org-scoped. (2026-08-18 remediation: 20 sequences paused by hand.)
- **Withdrawal** `POST /orgs/manual-qualifications/withdrawals` `{campaign_id, email, notes?}`, org-scoped, `x-user-id` required. A correction, NOT an erasure: append to `instantly_manual_qualification_withdrawals` (migration `0041`, `qualification_id` UNIQUE), no `none`/`unset` kind. STANDING = latest bronze row with no withdrawal pointing at it (`findStandingManualQualification`); `insertManualQualification` idempotency compares against the standing one. Silver is MARKED (`instantly_events.withdrawn_at`, only `source='manual'`); gold CTE `latestSentimentCteBody` (`analytics.ts`) filters `e.withdrawn_at IS NULL`. The pin is RELEASED (`reply_classification` recomputed from the latest surviving event, `reply_classification_source` back to `'auto'`; nothing left = NULL, never fabricated neutral). 404 `no_standing_qualification` / 404 `campaign_not_found`. `GET` returns withdrawn statements with `withdrawnAt`/`withdrawnBy`. **Withdraws the KIND and its pin, NOT the fact a reply arrived**: do NOT retract the `reply_received` event (its stop/refund/pause already happened). Guards: `manual-qualification-withdrawal.test.ts`, `manual-qualifications.test.ts`, `stats.test.ts` (`e.withdrawn_at IS NULL`).

## Stop-on-click
On a REAL `email_link_clicked`, if the CAMPAIGN's leg ARRIVES on `website_visit`, pause the lead's Instantly campaign (`maybeStopOnClickForLeg`).
- **Gate = campaign `legKey` (campaign-service) read against features-service's leg catalogue** `GET /public/channels` `channels[].stepTransitions[] = {legKey, from, to:{key}}` (`src/lib/leg-catalogue.ts`, cached 5 min/replica). The leg KEY is never parsed. `legArrivalStep` reads the leg on the campaign's own `featureSlug`; an unlisted channel falls back to every channel stating the leg and answers only when they AGREE. Lineage (do NOT restore): brand `current_goal`, campaign `funnel_key` (retired, distribute.you#4413), campaign leg. Arrival `website_visit` = STOP; `conversation` = keep sending; NULL leg or platform send (no `campaignId`) = no-op, no catalogue call; unknown leg = WARN, no stop; unreadable catalogue = fail-soft no-op. WARN only for unknown leg (tell: `docker logs distribute-instantly-service-1 --since 24h | grep -c stop-on-click` at 0 while clicks arrive).
- A REPLY is separate and unconditional (`reply_received` is in `SEQUENCE_STOP_EVENTS`; only `auto_reply_received` exempt). Only a HUMAN click reaches this (scanners are classified out).
- **Minimal by design: ONLY pause on Instantly**; no local `status='paused'`, cost-cancel or contact-delete (retry-stuck preflight skips a paused campaign; nightly reconcile `finish` heals). Fail-soft, never throws into the webhook. Always-on, no kill switch (needs `CAMPAIGN_SERVICE_URL`, `CAMPAIGN_SERVICE_API_KEY`, `FEATURES_SERVICE_URL`).
- Backfill `POST /internal/campaigns/stop-on-click-backfill` (`src/lib/stop-on-click-backfill.ts`): re-asks the same question through the same `maybeStopOnClickForLeg` for leads with a REAL (`inferred=false`) click on a still-`active` sequence; idempotent, fail-soft per lead, `{limit}`, 202 + background.

## Click classification (a link scanner is not a website visit)
- **A click/open question starts with `instantly_events.source`**: on `self_send` the tracker is OURS and the open is INFERRED from the click (same timestamp, `inferred=true`), so there is no vendor to ask; a "possible bug" email to Instantly about it is wrong-recipient (2026-10-02, Olive draft).
Corporate scanners fetch every URL; the `/c/` redirect used to promote each into `email_link_clicked` and stop-on-click paused sequences on it (prod 2026-09-11: 131 of 337 smtp leads "clicked" vs 95 of 2049 on Instantly). `self-send/click-classification.ts` (pure), `click-promotion.ts` + `click-promotion-worker.ts`, `click-scanner-backfill.ts`.
- **NO time threshold, by decision** (scanner delay clusters at 20-60s, where a phone human lands). Rules key on WHAT the client did.
- **Promotion is DEFERRED** because the decisive signal (a paired opt-out-link fetch within seconds; 135 of 309 click hits) can arrive after the click. **Promote-then-retract rejected** (the pause is the harm; owner: no reactivation). Hold `CLICK_DECISION_HOLD_SECONDS` 120s, strictly > `PAIRED_UNSUBSCRIBE_WINDOW_SECONDS` 60s.
- **Strongest signal = Chrome version shape (`isUnreducedChromeVersion`)**: Chrome froze its UA at 110 (`Chrome/<major>.0.0.0`), so a UA claiming Chrome >=110 with a FULL build number is not a browser (`>=110` floor leaves `Chrome/84.0.4147.89`). Without it 80 of Opsfolio's 131 clickers survive; with it 18. Do NOT blocklist plain `Chrome/14x.0.0.0` (a human UA). Request-time signals stored with the hit: non-GET method, non-browser UA (Safe Links MSIE 8/Trident 4, `Go-http-client`, preview bots), missing UA. A test pins the exclusion of the dominant `Windows NT 10.0 ... Chrome/14x` string.
- **Scanner NETWORK rule (`scanner_network`, 2026-10-02)**: a click from a /24 where another click was ruled `scanner` within ±7 days (`scannerNetworkEvidenceSql`, shared by promotion and backfill; private ranges excluded, pre-fix hits carry Caddy's `172.18.x`). Microsoft Defender rotates between the unreduced Windows UA and an ordinary reduced Mac UA from the same Azure /24s: Olive's 7 "human" clicks, 268/383 fleet-wide. Promotion asks it in a SECOND pass, after the tick's own scanner rows are written (both halves of a Defender pass are pending in one tick). Guards: "scanner's network" tests in `click-classification.test.ts`, the ordering test in `click-promotion.test.ts`.
- `tracking_hits_raw.classification` = `human|scanner|legacy|NULL` (NULL = not yet decided, migration `0051`). Bronze keeps every hit with its reason; only `human` reaches silver.
- **Drain = in-process interval `startClickPromotionWorker` (60s, armed after `listen`), NOT a cron, NO kill switch** (only path by which a self-send click reaches silver). `POST /internal/self-send/promote-clicks` by hand. Idempotent without a cursor (promoted event timestamp = hit's `received_at`, collides on `instantly_events_dedupe_idx`; promote FIRST, mark bronze second). A throwing hit stays undecided and retries.
- Real client IP recorded (`tracking_hits_raw.client_ip`) via `app.set("trust proxy", 1)` (pre-fix hits all read Caddy's `::ffff:172.18.0.27`); trust exactly ONE hop.
- **Backfill `POST /internal/audit/click-scanner-backfill`** (`dryRun` default TRUE, per-brand counts; else 202, log `click-scanner-backfill: done`): candidates = every click hit NOT already `scanner` (`classification IN ('legacy','human')`), re-applying the SAME pure rule; a `scanner` verdict is never re-opened; scanner silver events deleted by `source_row_id` plus `inferred=true` projections, gold rebuilt (lead keeps `clicked` if any click survived). Scoped to `source='self_send'` (Instantly-webhook clicks are clean). Reactivates nothing itself (see below).
- **Resuming what a scanner stopped `POST /internal/audit/reactivate-scanner-paused`** (`reactivate-scanner-paused.ts`, owner 2026-10-02; run AFTER the backfill; `dryRun` default TRUE, else 202, log `reactivate-scanner-paused: done`): self-send `paused` rows with a `scanner` click, no click still human/undecided, no answer/qualification/opt-out in the org, no newer same-brand sequence, not closed by the stalled sweep; reopens ONLY holds cancelled at/after the first scanner click on never-sent steps, back to `provisioned`, row `active` + `metadata.reactivatedAfterScannerClick`. A BILLED hold (cost ids) is never reopened (`skippedBilled`: its runs-service charge stays cancelled).
- Guards: `click-classification.test.ts`, `click-promotion.test.ts`, `click-route.test.ts`, `click-scanner-backfill.test.ts`, `reactivate-scanner-paused.test.ts`.

## Sales-interest chain (all fired from `promoteEvent`, all fail-soft, none retroactive, none awaited in the webhook)
**ONE gate for the whole chain: `isSalesInterestQualification` (from `trigger-sales-interest-campaign.ts`) = `REPLY_KIND_CLASSIFICATION === 'positive'`, NOT `POSITIVE_REPLY_KINDS`.** The forward set also contains `lead_referral`; a referral must NOT trigger a funded campaign, enqueue a debt or ring a rep. Tests assert gate parity over every reply kind. Do NOT widen it.
- **Trigger the campaign bought to answer** (`src/lib/trigger-sales-interest-campaign.ts`): asks campaign-service `POST /internal/campaigns/trigger-for-step` with `{brandId, offerId, step: "conversation"}` + `x-org-id` and decides nothing else (leg, campaign, affordability are campaign-service's; run starts at `gate-check`). Scope READ off the caller campaign (`getCampaignTriggerScope`, shared `fetchCampaign`); a campaign with no brand/offer and platform sends make no ask. Empty `legKeys` or a named skip (`unfunded`, `run_in_flight`, `no_workflow`) is the ordinary answer, not an error. No queue, no retry (campaign-service reaches the lead on its next tick; a missed trigger costs latency). Reuses `CAMPAIGN_SERVICE_URL` + `_API_KEY`.
- **Enqueue the debt** (`src/lib/enqueue-followup-on-interest.ts`, after the trigger): lead-service `POST /orgs/campaigns/{campaignId}/followups/schedule-by-email` (`lead-client.ts`), `dueAt` = NOW (zero rows fleet-wide had a due date, so no interested buyer was ever answered). **By EMAIL on purpose** (exact, case-folded; unknown 404 `lead_not_found`, two matches 409 `ambiguous_lead`; never fuzzy). `campaignId` = the CALLER campaign row id, not the Instantly id nor the identity family; platform sends no-op. **Do NOT add a backfill sweep** (would answer dead conversations). Failures WARNED with lead-service's named refusal. Needs `LEAD_SERVICE_URL` + `LEAD_SERVICE_API_KEY`.
- **Take a declining buyer back OUT** (`src/lib/stop-followups-on-decline.ts`): stops on every NEGATIVE kind, `lead_referral`, and a real `lead_unsubscribed`; NOT `lead_neutral`, NOT automated kinds, never a buying signal (disjointness test). Reads state first (`readFollowupState`) and stops only when a due date or claim stands (lead-service prints "follow-ups stopped" on the customer timeline).
