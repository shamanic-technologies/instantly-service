# Project: instantly-service

Cold email outreach service via Instantly.ai API V2. Handles campaign management, lead upload, email accounts, warmup, analytics, and webhook processing.

## Commands

- `npm test` — run all tests (Vitest)
- `npm run test:unit` — unit tests only
- `npm run test:integration` — integration tests only
- `npm run build` — compile TypeScript + generate OpenAPI spec
- `npm run dev` — local dev server (nodemon)
- `npm run generate:openapi` — regenerate openapi.json
- `npm run db:generate` — generate Drizzle migrations
- `npm run db:migrate` — run migrations
- `npm run db:push` — push schema to database
- `npm run backfill:inferences` — one-shot CLI: project synthetic predecessor events onto existing silver rows. Manual only — NEVER wired into boot (port-bind hazard).
- `npm run cleanup:stacked-sigs` — one-shot CLI: clean stacked signatures from Instantly campaigns whose lead has been pushed but not yet received any email. Dry-run by default; pass `-- --commit` to actually PATCH Instantly. See [Signature handling](#signature-handling--idempotent-strip-then-append). Manual only.
- `npm run audit:dupes -- <orgId>` — read-only CLI: audit cross-campaign duplicate contacts (same email sitting in ≥2 **active** Instantly campaigns). **Source of truth = Instantly API**, never the local DB (the DB can be stale — the duplicate FACT is derived from Instantly). The local DB is read only to label each collision `same-brand` / `cross-brand` / `unknown-brand` (Instantly has no brand field). Read-only — audits, never heals. Flags: `--json`, `--limit N`, `--severe-only`. Manual only. See [Cross-campaign duplicate audit](#cross-campaign-duplicate-audit--read-only).
- `npm run heal:dupes -- --commit` — MUTATING CLI: pause redundant active Instantly campaigns. For each email in ≥2 active campaigns, **keep the oldest** (`timestamp_created`) and **pause** the rest. Dry-run by default; `--commit` to act; `--limit N` to batch. Pause is reversible (no delete). Instantly-only (no cost refund / DB write — runs-service is internal-DNS-only from a local shell). Run AFTER the retry-stuck fix deploys (else the worker re-spawns dupes). Idempotent/resumable. Manual only. See [Cross-campaign duplicate audit](#cross-campaign-duplicate-audit--read-only).
- `npm run cleanup:finished-contacts -- --commit` — MUTATING CLI: delete contacts of **finished** Instantly campaigns to reclaim the plan's uploaded-contacts quota. Finished = Instantly status **paused (2)** or **completed (3)**; active (1) is never touched. **Source of truth = Instantly API** (status + membership), never the local DB. `DELETE /leads` is campaign-level (the only delete that frees quota — deleting from "Lists" does not). Dry-run by default; `--commit` to act; `--limit N` to batch; `--json`. Idempotent/resumable (already-deleted leads drop out of the next sweep; a 404 delete is counted, not fatal). Instantly-only (no local DB write — the recurring reconcile path marks rows terminal). Selection logic is pure + unit-tested in `src/lib/cleanup-finished.ts` (`selectContactsToDelete`). Manual only. See [Finished-contact cleanup](#finished-contact-cleanup--reclaim-quota).
- `npm run cleanup:escaped-newlines -- --commit` — MUTATING CLI: repair sequence steps whose body carries a LITERAL escape sequence (`\` + `n`) where a line break was meant, so the **un-dispatched** follow-ups render as real paragraphs. **Source of truth = Instantly API** (live `getCampaign` bodies + the PATCH); the local DB only NARROWS candidates. Rewrites ONLY steps above the campaign's `lastSentStep` — an already-sent step is left alone and reported (the email is gone; rewriting it would silently alter the historical record). Dry-run by default; `--commit`, `--limit N`, `--json`. Idempotent/resumable, fail-loud on a per-campaign error. Instantly-only (no local DB write, no cost — a campaign PATCH spends nothing). Pure logic + tests in `src/lib/escaped-newlines.ts`. Manual only. See [Escaped-newline repair](#escaped-newline-repair--pending-steps-only).

## Architecture

- `src/index.ts` — Express app entry point
- `src/schemas.ts` — Zod schemas (source of truth for validation + OpenAPI)
- `src/zod-setup.ts` — Side-effect module that extends Zod with `.openapi()`. Import it BEFORE any module that creates `z.object(...).openapi("Name")` schemas.
- `src/routes/` — Route handlers (campaigns, leads, accounts, analytics, send, webhooks, health)
- `src/middleware/serviceAuth.ts` — API key auth middleware
- `src/lib/instantly-client.ts` — Instantly API V2 HTTP client
- `src/lib/runs-client.ts` — Runs service HTTP client for cost tracking
- `src/db/schema.ts` — Drizzle ORM table definitions (campaigns, leads, accounts, events). Gold stats are derived-on-read from silver in `analytics.ts`/`status.ts` — there is NO `analytics_snapshots` materialized table (a dropped legacy table; do not reintroduce a snapshot **table** cache). Live aggregation was proven too slow under load (2026-06-13: `/orgs/stats` + `/public/stats` flooded email-gateway with ~10s AbortSignal timeouts — bursts of identical re-aggregations saturating the DB host). The mitigation is the LIGHTEST possible, NOT a snapshot table: (1) a short-TTL in-memory cache (`src/lib/stats-cache.ts`, 60s default, per-replica) on GET `/stats`, GET `/public/stats`, **POST `/orgs/status`** (v0.57.2 — keyed on orgId+brandId+campaignId+sorted emails), AND **GET `/internal/audit/sending-forecast`** (v0.60.2 — platform-scoped, fixed key `sending-forecast`) — keyed on params (+ orgId for the authed routes). **RULE: any route that live-aggregates over the silver event log AND is called by email-gateway on the send/retry path MUST wrap its DB work in `getOrSetCachedStats`.** email-gateway retries the SAME request on its ~10s AbortSignal timeout and the abort does NOT cancel the server-side query, so each retry piles another identical heavy aggregation onto the pool (max 20) → the timeout flood. The in-flight dedup collapses the retry storm to one query. TWO routes have been the gap that bit — audit EVERY email-gateway-hit aggregation route, not just `/stats`: (a) `/orgs/status` was uncached, then #426 (contract v1.2.0) added a per-scope `COUNT(DISTINCT step)` sentCount subquery to it → the flood returned on `POST /orgs/status` 11h after that merge (fixed v0.57.2); (b) `/internal/audit/sending-forecast` was uncached (its `loadPendingLeads` fleet scan + a per-lead config LATERAL, plus a live paginated `listAccounts`) → email-gateway (`/public/stats/sending-forecast`) → features-service → api-service all 500'd (fixed v0.60.2, #464 — cache wrap + a composite index, see the [Sending forecast](#sending-forecast--capacity-vs-scheduled-volume) section). Before adding ANY new aggregation to a status/stats/forecast route, confirm the route is cached; (2) `instantly_events_stats_covering_idx` (campaign_id, event_type, lead_email, step) → index-only scan on the filtered `/orgs/stats` path (does NOT help the no-filter `/public/stats`, which the planner seq-scans regardless — that path leans on the cache); (3) `queryStats` / `queryGroupedStats` / the per-step block (`computeStepStats`/`computeStatsPayload`) parallelize their independent reads via `Promise.all`; (4) `work_mem = '32MB'` set per pool connection (`src/db/index.ts`, `pool.on("connect")`). Each `COUNT(DISTINCT lead_email)` sorts ~88k events; at the pg default (4MB) that sort spills to temp disk (`EXPLAIN`: `external merge Disk: 7616kB`) → I/O contention + the pool connection held longer, which is what starves the pool (max 20) under burst and produces the `timeout exceeded when trying to connect` flood. At 32MB the sort stays in memory (`quicksort Memory: 11312kB`, zero temp). Do NOT lower `work_mem` back to the default to "save RAM" — it reintroduces the spill. It is a PER-CONNECTION setting, so the worst case is `max:20` × 32MB, and `work_mem` buys headroom, not infinite scale — if the flood returns under higher traffic, the DB host's memory is the next wall, and that host is now shared by every service's database (one Postgres container on one box), so the blast radius of over-allocating here is fleet-wide, not just this service. (Sized 2026-06 against the Neon compute this DB ran on then, which autoscaled 0.25→1 CU under exactly this load; the sizing carries over because the spill is a property of the pg default `work_mem`, not of the host.) If you add a new cached stats route, `clearStatsCache()` MUST be called in its unit-test `beforeEach` or cross-test cache hits skip the DB and break assertions.
- `src/db/index.ts` — Database connection. Pool tuned under stats burst: `max:20`, `idleTimeoutMillis:60_000`, `keepAlive:true`, `connectionTimeoutMillis:5_000` (was 15_000 — a starved pool-acquire blocked the next request the full 15s before `withConnectRetry` retried; 5s fails fast → retry, and still leaves room for a slow first connect), and `work_mem='32MB'` per connection (see the stats note above). Do NOT raise `connectionTimeoutMillis` back to 15s. The long `idleTimeoutMillis` + `keepAlive` were added when this DB was a Neon compute in Singapore and the default 10s idle teardown churned warm cross-region connections between bursts; keep them regardless — holding a warm connection across bursts costs nothing and a reconnect on every burst is pure latency.
- `src/lib/stop-lead-sequence.ts` — the ONE implementation of "stop the sending for this lead", branching on transport (Instantly pause vs `stopSelfSendSequence`). Three callers, all of them places that learn about a reply Instantly did NOT see: manual qualification, the IMAP poller, the inbound-replies backfill. Fail-soft — the reply is already recorded, so a failed pause is logged, never thrown.
- `src/routes/audit.ts` — Staff ops reads/writes (platform-scoped, no org). `GET /internal/audit/sending-forecast` powers admin.distribute.you's "Audit → Instantly" page: fleet **capacity** vs upcoming scheduled **volume** in one response (see [Sending forecast](#sending-forecast--capacity-vs-scheduled-volume)). `POST /internal/audit/accounts-sync` snapshots `GET /accounts` → bronze/silver + runs `reconcileLifecycle` (202 + background, `accounts-sync: done`; wired as the placement cron's first step). `GET /internal/audit/capacity-history?days=N` (clamped 1–365) → `{ series: [{ date, inProductionCount, dailyCapacity }] }` reconstructed from `instantly_accounts_raw` (daily_limit over time) + lifecycle events (status over time). See [Account lifecycle](#account-lifecycle--auto-driven-per-account-state-bsg).
- `src/lib/account-lifecycle.ts` — pure `deriveLifecycle` (4-state, first-match-wins). `src/lib/account-lifecycle-sync.ts` — `reconcileLifecycle` IO glue (PATCH warmup on flip → insert lifecycle event → update silver).
- `src/lib/sending-window.ts` — pure: which UTC day a send books on a mailbox, resolved through the LEAD's own Mon-Fri 08:00-17:00 local window (`nextLocalSendInstant`, `sequenceFootprintDays`, `isWithinLocalSendWindow`). Consumed by send selection, the capacity snapshot and the self-send dispatcher; NEVER by the ops projections. See [Account selection](#account-selection--lifecycle-gated-read-from-silver).
- `src/lib/self-send/` — dispatching our own mail instead of Instantly (see [Self-send transport](#self-send-transport--dispatching-our-own-mail)). `transport.ts` = pure `resolveTransportForSend`; `mailbox-credentials.ts` = Primeforge app-password → Gmail SMTP/IMAP; `sequence-steps.ts` = pure step extraction + the `delayForGap`-compatible delay array; `unsubscribe.ts` = stateless HMAC opt-out links; `message.ts` = the message, built through the EXISTING `buildEmailBodyWithSignature`; `smtp.ts` = dispatch + reply-class failure classification; `dispatch.ts` / `dispatch-worker.ts` = what is due and sending it; `inbound.ts` / `imap-poller.ts` = reading replies and bounces back out of the mailbox.
- `src/routes/unsubscribe.ts` — public, unauthenticated opt-out (`/u/:payload/:signature`), gated entirely by the HMAC. GET renders a confirmation; only POST unsubscribes (link scanners).

## Sending forecast — capacity vs scheduled volume

`GET /internal/audit/sending-forecast` (platform-scoped, no org; same `serviceAuth` tier as `/internal/accounts`). Pure logic in `src/lib/sending-forecast.ts` (unit-tested `tests/unit/sending-forecast.test.ts`); route `src/routes/audit.ts` does IO only. Two independent halves in one response:

**Performance (v0.60.2, #464) — the handler is CACHED and the config LATERAL is INDEXED. Do NOT unwrap either.** (1) The whole computation is wrapped in `getOrSetCachedStats` (60s TTL, fixed key `sending-forecast`) — this route lives-aggregates AND makes a live paginated `listAccounts` call, and email-gateway (`/public/stats/sending-forecast`) retries on its ~10s AbortSignal timeout without cancelling the server query, so the uncached version flooded the pool → features/api 500s (same class as `/orgs/status`; see the `src/db/schema.ts` cache RULE). The in-flight dedup collapses the retry storm to one loader run. Fail-loud preserved (a loader throw caches nothing, still 500s). `clearStatsCache()` is in `audit-route.test.ts` `beforeEach`. (2) `loadPendingLeads`'s per-lead latest-config LATERAL (`WHERE instantly_campaign_id=$1 ORDER BY fetched_at DESC LIMIT 1`) is served by the composite index `instantly_campaigns_config_raw(instantly_campaign_id, fetched_at DESC)` (migration `0026`) — ordered index scan + LIMIT 1 reading only the winning row, vs the old bitmap-heap-scan-all-~16-configs + top-N-sort of their large jsonb payloads (~50k block reads/call × 6,400 loops; prod EXPLAIN 678ms→349ms warm, far larger cold). **The table is ~550k rows / ~1.38GB, so migration `0026` is `CREATE INDEX IF NOT EXISTS` and the index was pre-built CONCURRENTLY out-of-band** (a non-concurrent boot build scans the whole heap → port-bind outage; boot-window rule). Any new prod-scale env MUST pre-build it concurrently before deploy.

- **Capacity** (`dailyCapacity`, `healthyAccountCount`, `totalAccountCount`, `blockedDomainCount`): `computeCapacitySummary(accounts, lifecycleByEmail)`. `dailyCapacity = Σ daily_limit` over the **`in_production` accounts** (the exact live-send pool — `lifecycle_status == 'in_production'`, read from silver; see [Account lifecycle](#account-lifecycle--auto-driven-per-account-state-bsg)). `blockedDomainCount` = the count of `deactivated_by_user` accounts (the `instantly_domain_policy` brand/product domains). Under the 2026-06-29 Gmail-spam halt nearly the whole fleet is `in_recovery`, so `dailyCapacity` is legitimately near-zero — render it, never fabricate a non-zero.
- **Volume** (`days[]`): `projectDailySchedule(pendingLeads, asOf)`. A TRUE per-day projection of active campaigns' remaining **un-sent** steps onto future calendar days, **capacity-INDEPENDENT** and bounded by sequence structure. It is NOT `backlog ÷ capacity` — with capacity ~0 a capacity-paced drain would never terminate. Source of "un-sent" = `sequence_costs` rows with `status='provisioned'` (a hold stays provisioned until its `email_sent` webhook actualizes it), gated to live campaigns (`instantly_campaigns.status='active'` AND `delivery_status IN ('contacted','sent')`).
- **Cadence = the REAL per-step delays from bronze config (shared with the queue breakdown, v0.57.6+).** `loadPendingLeads` resolves each lead's latest bronze sequence-config step delays (`instantly_campaigns_config_raw.payload->'sequences'->0->'steps'->i->>'delay'`) and passes them as `PendingLead.stepDelays` (config-ordered 0-based; gap cost-step `k`→`k+1` = `steps[k-1].delay`, identical indexing to `queue-breakdown.ts`). `scheduleLead` accumulates the real per-gap delays; `STEP_GAP_CALENDAR_DAYS = 3` is now the per-gap FALLBACK for a missing config delay (also the queue-breakdown fallback → one shared fallback). This makes the forecast's inter-step cadence identical to the per-account queue-bucket projection — the two ops views share ONE cadence source of truth. Guard: the `delayForGap` / real-delay `scheduleLead` / `classifyQueuedSequence`-coherence tests in `tests/unit/sending-forecast.test.ts`. Do NOT revert to a hardcoded canonical gap. **Day bucketing = the raw nominal UTC send day, with NO weekend snap — IDENTICAL to the queue breakdown, and load-bearing for coherence.** The former weekend forward-snap (business-hours-weekday model) pushed a weekend-due step to the next Monday, so on a weekend today/tomorrow read `scheduledCount:0` while the per-account "Sending accounts" table (which never snaps) still counted the step as `queuedNextToday`/`queuedNextTomorrow` — the two staff surfaces disagreed for the same pending steps. Dropping the snap makes them agree by construction: a weekend day carries its REAL due-step count, and the forecast's per-day count reconciles with the fleet-aggregated queue-breakdown buckets. Do NOT reintroduce a weekend snap. Guard: the "raw nominal day (NO snap)" + weekend-asOf-AC + "weekend day carries its REAL due-step count" tests in `tests/unit/sending-forecast.test.ts`. Same honesty caveat as the breakdown: the projected date is a nominal-cadence LOWER BOUND (real dispatch slips later under daily-limit/throttling), not Instantly's exact dispatch date.
- **Key resolution:** the shared cold-email workspace key comes from **key-service's platform decrypt endpoint** `GET /keys/platform/instantly/decrypt` (global platform key, no org/user — `resolvePlatformInstantlyApiKey` in `key-client.ts`), NOT a local env var. Do NOT reintroduce a `process.env.INSTANTLY_API_KEY` read on the request path (that's a CLI-only override). 404 (platform key not configured) → fail loud 500, no impact on other routes. Fail-loud throughout — no silent zero fallbacks.

## Unibox backfill — the replies exist in ONE place, and cancelling deletes them

Instantly's cancel dialog states it plainly: cancelling a plan or a single inbox **permanently deletes every conversation those mailboxes sent or received, lead replies included**. Silver records THAT a lead replied (`reply_received` + its reply kind); the words they wrote live only in bronze `instantly_emails_raw`, which until now was filled solely by the reconcile poll's `GET /emails?campaign_id=` — so coverage follows whichever campaigns reconcile happened to re-poll. Measured 2026-08-29: **133 leads had replied fleet-wide and 26 had a stored inbound body (~20%)**, and the 5-inbox `resilientnirvana.com` domain about to be cancelled had **zero emails stored at all** while Instantly's dialog offered 6 lead replies across 479 conversations.

`POST /internal/audit/emails-backfill` (platform-scoped, same `serviceAuth` tier as the other `/internal/audit` sweeps) mirrors the WHOLE Unibox into bronze. Sweep in `src/lib/emails-backfill.ts` (pure `groupByCampaign` unit-tested in `tests/unit/emails-backfill.test.ts`); the route does IO dispatch only. 202 + background, log `emails-backfill: done`. Body `{ maxPages?: number }` bounds the walk for a probe; omitted, it runs to the end (~1,200 pages ≈ 75 min).

- **Reads `/emails` with NO campaign filter** via `listEmailsPage`, which returns the workspace newest-first through one cursor. Exhaustive by construction — no account list to get wrong, so it also captures mail from mailboxes ALREADY deleted, which is exactly the set a cancellation is about to destroy. Do NOT rewrite this as a per-campaign sweep: at 44k campaigns and Instantly's 20 req/min cap on `/emails` that is ~40 hours, versus ~75 minutes for the whole workspace.
- **`listEmailsPage` is deliberately caller-driven pagination**, against this repo's "all of X helpers must fully paginate" convention. The workspace holds >100k emails: an all-of-X helper would hold the entire Unibox in the heap before writing a row, and lose every page it had read if the sweep died. The caller loops it and persists each page as it arrives.
- **⚠️ An UNPACED `/emails` call returns a 429 whose body carries no `items`, which is indistinguishable from an empty page** — a hand-rolled probe that skips the throttle reads "this mailbox has no email" for a mailbox full of it (observed while sizing this work: a raw-`fetch` probe reported 0 emails for all 5 resilientnirvana boxes; the same query through the throttle returned full pages). Always go through `instantlyRequest`, which paces the `/emails` slot at 3.5s and retries.
- **Bronze only.** Nothing is promoted to silver, no event is synthesized. This is a photocopy of what Instantly holds, not a new source of facts.
- **Migration `0043` makes `instantly_emails_raw.instantly_campaign_id` NULLABLE.** A workspace-wide read legitimately returns mail attached to no campaign; skipping those rows would drop exactly what the sweep exists to preserve, and minting a campaign id for them would fabricate a fact. Every reader filters by a concrete id, so widening it changes no query. `org_id` is resolved per campaign from `instantly_campaigns` (chunked `inArray`, never a large JS array through `= ANY(...)`) and is null for a campaign we hold no row for.
- **Idempotent + fail-loud.** The insert conflicts on `instantly_email_id` and does nothing, so a re-run re-reads pages and writes only what is new; `emailsStored` counts NEW rows, so a second run honestly reports what it added. An error on any page propagates — a sweep that silently skipped a page would report a clean run over a Unibox it had not finished copying.
- **⚠️ A DEPLOY KILLS THE SWEEP, so pass `{startingAfter}` to resume — a 75-minute in-process job cannot survive this repo's merge rate.** The deploy cron recreates the container on every merge, and the first full run was killed THREE times in 70 minutes by unrelated sibling merges (placement work, #653/#656/#657), each time after ~13 minutes. Nothing looks wrong: `RestartCount` stays 0, the exit code is 0, and the container's logs simply start fresh, so the only tell is that the bronze row count stops moving. Because the sweep walks newest-first from the top, a naive re-run then spends its whole life re-reading pages it already stored (~22 min per 400 pages at the mandated 3.5s pacing) and never reaches new ground. So the summary AND every progress line carry `cursor` / `nextCursor`; feed the last one back as `startingAfter` and the next run continues from there. `nextCursor` is null only when the list is genuinely exhausted.
- **Spends nothing metered** — a read against a flat subscription, so no run/cost is declared (same reasoning as the placement tests and the infra inventory sweep).
- **Run it BEFORE any cancellation**, and verify by the thing that motivated it: every lead with a `reply_received` event should have a stored inbound (`ue_type <> 1`) body.
- **⚠️ VERIFY COVERAGE BY THE LEAD'S CAMPAIGN, NOT BY `from_address_email = lead_email` — a prospect frequently replies from a DIFFERENT address than the one we mailed** (an assistant, a shared `partners@`/`editor@` box, a personal address). Matching the sender against the lead undercounts badly and reads as lost data: on the first full run it reported 75 of 133 replied leads covered, while joining through `instantly_campaigns` on the campaign id showed 87 — the other 12 were stored all along under another sender. Also note `payload->'lead'->>'email'` is NULL on inbound rows, so it cannot be used as the join key either. The correct query is `EXISTS (SELECT 1 FROM instantly_campaigns c JOIN instantly_emails_raw m ON m.instantly_campaign_id = c.instantly_campaign_id WHERE c.lead_email = <lead> AND m.payload->>'ue_type' <> '1')`.
- **A residual gap is EXPECTED and is not the backfill's to close: a reply recorded by `source='manual'` or `poll_leads` never existed as an email in the Unibox.** A manual qualification is created PRECISELY because Instantly did not detect the reply (see [Manual qualification](#manual-qualification--stop-the-sequence-on-both-sides)), and a `poll_leads` reply is inferred from `lt_interest_status` on the lead object, not from a message. After the first full sweep, 44 of the 46 uncovered leads were exactly these — so a cancellation destroys nothing further for them, and chasing them with a wider sweep would find nothing. Measure the gap by reply SOURCE before treating it as missing data.
- **Prod result, first full run (2026-08-29):** 112,995 emails mirrored (13,541 → +99,454), 369 inbound, covering 2026-02-10 → 2026-08-29, in four resumed chunks. Replied-lead coverage 26 → 87 of 133. The five `resilientnirvana.com` inboxes queued for cancellation went from zero stored emails to 1,359, including all **6** lead replies Instantly's own dialog offered — the number that made the cancellation safe.

## Reconciliation audit — local truth vs Instantly truth, side by side

`GET /internal/audit/reconcile` (platform-scoped, no org; same `serviceAuth` tier as `/internal/audit/sending-forecast`). Pure logic in `src/lib/reconcile-audit.ts` (unit-tested `tests/unit/reconcile-audit.test.ts`); route `src/routes/audit.ts` does IO only. For each **countable fact** returns `{key, label, local, instantly, delta, sourceOfTruth}` where `delta = local − instantly` — so an operator seeing a non-zero delta on admin.distribute.you can investigate the underlying bug (lost webhook, lagging reconcile, a pause/throttle we never observed).

- **Reconciles COUNTS, never the forecast's future DATES.** The sending-forecast VOLUME is an inherent projection — the exact future send DATE of a step exists nowhere (Instantly schedules dynamically off daily limits / business hours / throttling / pauses), so timing cannot be reconciled. Do NOT add a "date reconciliation" — it would compare against a number that doesn't exist. (The forecast's volume MAGNITUDE, however, IS reconcilable — see `pendingSends` below.)
- **Output = THREE comparable metrics only (`activeCampaigns`, `emailsSent`, `pendingSends`); Instantly is SoT for all three.** `buildReconciliation` emits exactly these. TWO former rows were REMOVED (v0.50.7) because their two sides measure DIFFERENT quantities, so their delta is a structural artifact, not drift an operator can act on — do NOT re-add them to the output:
  - `contactedDispatched` ("Leads dispatched"): Instantly's fleet-aggregate `contacted_count` tracks per-step DISPATCHES (empirically ≈ `emails_sent_count`), NOT distinct leads, while the local side counts distinct `(campaign, lead)`. Proven airtight against prod (68,570 contacted ≈ 69,295 emails — impossible under a distinct-leads reading, since a contacted lead has ≥1 email). Distinct-leads vs dispatch-count always shows a huge fake gap.
  - `contactsStored`: local counts ALL `instantly_campaigns` rows ever created (never decrements), while Instantly's `leads_count` is CURRENTLY-stored and drops as the armed finished-contact cleanup (`DELETE_FINISHED_CONTACTS_ENABLED=true`) deletes contacts to reclaim quota. Guaranteed-positive-by-design, not drift.
  - Both counts are STILL computed (`summarizeInstantlyCounts` + the local SQL + the snapshot columns) — only the output pairing was dropped. The snapshot table keeps its 5 columns (no migration).
- **`pendingSends` counts STEP-SENDS on both sides, and is DERIVED on Instantly.** Instantly has no ready-made remaining-step field, but each campaign's `sequences` carry the loaded followup steps and analytics carry `emails_sent_count`, so (one campaign = one lead) Instantly's remaining = `Σ over ACTIVE campaigns of max(0, stepCount − sent)` (`computeInstantlyPendingSends`). Do NOT re-mark `pendingSends` local-only — the data is derivable, not missing (regression guard: it was shipped local-only in v0.50.4, corrected in the next hotfix). **UNITS (v0.50.7 fix): the local side counts `COUNT(DISTINCT (campaign_id, lead_email, step))` provisioned holds, NOT `COUNT(*)`.** A step used to provision TWO `sequence_costs` rows (account + domain), so `COUNT(*)` DOUBLED the local number vs Instantly's one-per-step remaining. Since migration `0038` a step queues ONE row, but HISTORICAL rows are still doubled — keep the DISTINCT form, do NOT revert to `COUNT(*)`.
- **Instantly side = two bulk sweeps.** (1) `listAllCampaignAnalytics` → `GET /campaigns/analytics` with `id` omitted returns ALL campaigns' analytics as a single **non-paginated** array (confirmed via developer.instantly.ai — no cursor/limit on this endpoint), the ONE client helper that deliberately does NOT paginate. (2) `listAllCampaignSequenceLengths` → paginated `GET /campaigns` (each campaign object carries its `sequences`) for the per-campaign `stepCount`. Per-campaign iteration is infeasible at fleet scale (thousands of campaigns × rate limit); both sweeps are bulk/paginated, not N calls. Instantly ACTIVE lifecycle code = `1`.

## `db.execute` returns a `QueryResult`, NEVER an array — unwrap it, never cast it

This service runs on **node-postgres** (`pg`), where drizzle's `db.execute()` resolves to a `QueryResult` OBJECT (`{ rows, rowCount, … }`). It is postgres.js — the org standard everywhere else — that resolves to a bare array, so an idiom copied from a sibling repo compiles here and dies on the first real query with `TypeError: rows is not iterable`. **`tsc` cannot catch it**: the only thing that makes the array shape typecheck is a cast (`as unknown as Array<…>`), and a cast that lies to the compiler is exactly what removes the one check that would have failed. Every module therefore defines a private `rowsOf(result)` (`.rows` with an array fallback) and reads through it; direct `result.rows` is equally correct. **Do NOT introduce a third way, and do NOT cast a `db.execute` result to an array type — if a cast is needed to make it iterate, it is already wrong.**

⚠️ **A unit test mocking `db.execute` proves nothing about the shape unless the mock returns what the DRIVER returns.** `mockDbExecute.mockResolvedValue([...])` is the postgres.js shape, so the whole suite passes against code that cannot run — the mock and the bug agree with each other. Mock the real thing (`{ command, rowCount, oid, fields, rows }`); `tests/unit/transport-split.test.ts` has a `pgResult()` helper for it. Same blind spot as the array-parsing note below, one layer up: there the mock hides a VALUE mis-parse, here it hides the RESULT shape.

Cost 2026-08-30 (v0.75.0 → v0.75.1, the transport A/B split): `fetchTransportAssignmentCounts` cast its result to an array and iterated it. From 06:46 UTC every single `POST /orgs/send` threw `rows is not iterable` — 81 send-errors across 2 orgs over ~13 hours, each failing its parent Windmill job AFTER the lead had been enriched and its email generated and paid for, so the spend happened and no email did. Nothing was red anywhere: the deploy was healthy, `tsc` was green, and the suite passed because every mock returned an array. Sending was restored by disarming `SEND_TRANSPORT_AB_ENABLED` on the box, which short-circuits `resolveTransportForNewSequence` before the query — i.e. the only branch that reaches it is armed AND self-send-capable, which is precisely the branch no test covered.

## node-postgres array parsing — return `jsonb_agg`, NEVER a raw `numeric[]`

Any SQL (`db.execute(sql\`…\`)`) that returns a Postgres ARRAY for JS consumption MUST build it as a **JSONB array (`jsonb_agg(...)`)**, NOT a native array type via `ARRAY(SELECT …)` / `ARRAY_AGG(<non-int>)`. **node-postgres parses `jsonb` into a JS value reliably, but returns a `numeric[]` (and other non-`_int4` array OIDs) as its RAW TEXT form — a string like `"{3,7,0}"`** — so `?? []` does NOT catch it (a string is truthy) and a downstream `.map(...)` throws `X.map is not a function`. `int[]` from `ARRAY_AGG(<int column>)` happens to parse fine (pg-types registers `_int4`), which is why the trap hides — a query that works with an int array breaks the moment you switch the element to `numeric`/`text`/computed. Prefer `COALESCE(jsonb_agg(expr ORDER BY …), '[]'::jsonb)`; guard a null/non-array source (`jsonb_array_elements` throws on a non-array) and, in the mapper, `Array.isArray(x) ? x : []` so a shape surprise degrades one row, never 500s the endpoint. The per-account queue breakdown (`account-sending-stats.ts`) selects raw jsonb (`payload->…->'steps'`) and was safe; the sending-forecast loader (`audit.ts` `loadPendingLeads`) shipped a `numeric[]` and 500'd the whole fleet forecast — `rawDelays.map is not a function` (fixed v0.59.1, #454). Pure-function unit tests CANNOT catch this — the mis-parse only happens against real node-postgres, not the mocked `db.execute`; validate array-returning SQL against the real prod database before shipping (`ssh` to the box → `docker exec distribute-postgres-1 psql -U postgres -d instantly_service`).

## Signature handling — idempotent strip-then-append

`buildEmailBodyWithSignature` (`src/lib/send-lead.ts`) MUST be idempotent: `f(f(x)) === f(x)`. It ALWAYS calls `stripAccountSignature` on the input body before appending the signature. Guarantees a body re-sent N times (e.g. retry-stuck redispatching the same lead) never accumulates N stacked signatures.

**Signature source priority:**

1. `account.signature` — per-sender override configured in Instantly's UI (account settings). Intentionally empty in prod.
2. `buildDefaultSignature(account)` (`src/lib/send-lead.ts`) — **per-account name + fixed brand line**. **Source of truth in prod.**

**PERSON line = the account's OWN name; brand line fixed.** The signature is now derived per-account so the From-name and the signature agree under multi-persona sending (e.g. `amy@…` signs "Amy Moore", `kevin@…` signs "Kevin Lourd"):

```
{account.first_name} {account.last_name}     ← derived from the sending account
Distribute.you | Marketing Agency            ← fixed SIGNATURE_BRAND_LINE
```

`buildDefaultSignature(account)` joins `account.first_name` + `last_name` (falls back to `DEFAULT_SENDER_NAME = "Kevin Lourd"` when both are absent). **NO title** — a fixed "Founder" cannot apply across many distinct sender personas (DFY pre-warmed accounts ship with names like Amy Moore / Louis Williams), so the title line was dropped 2026-06-30. The brand line renders as **plain text — NOT a clickable `<a>` link**: `buildEmailBodyWithSignature` autolinkifies the prospect body ONLY, appending the signature block verbatim. Do NOT reintroduce sig-wide autolinkify.

The signature is intentionally code-derived (not Instantly-UI driven). When the brand line / format changes, edit `SIGNATURE_BRAND_LINE` / `buildDefaultSignature` and ship a hotfix. Do NOT re-add per-account UI signatures without updating this rule — code prefers the UI value over the derived default. Guard: the "signs with the account's OWN name" + canonical-fallback tests in `tests/unit/send.test.ts`.

**Visible unsubscribe footer (`UNSUBSCRIBE_FOOTER_HTML`, appended below EVERY signature).** `buildEmailBodyWithSignature` appends a small / grey / italic opt-out line — a `<p>&nbsp;</p>` spacer paragraph (the blank-line gap) then `Don't want to hear from me again? <a href="{unsubscribe_link}">unsubscribe</a>` — as part of the `sigBlock` (INSIDE the strip-and-reappend region, so idempotency holds — a re-sent body never stacks the footer). **The link MUST use Instantly's SINGLE-brace `{unsubscribe_link}` server-side merge variable — the `{{...}}` mustache form does NOT resolve** ([help.instantly.ai/articles/6191077](https://help.instantly.ai/en/articles/6191077-how-to-add-unsubscribe-link)); it renders per-lead at send into a functional opt-out URL. This is the VISIBLE opt-out path, distinct from and complementary to the RFC-8058 `List-Unsubscribe` header set on every campaign (`insert_unsubscribe_header: true` in `createAndActivateCampaign`), which powers the mailbox-native (Gmail/Apple/Outlook) one-click unsubscribe button. **Instantly's HTML sanitizer PRESERVES the inline `style` attribute on PATCH/create round-trip — verified 2026-07-19 via a live create→GET→delete probe: `style="font-size:12px;color:#999999;font-style:italic"` and the anchor + `{unsubscribe_link}` survived intact (only `&nbsp;`→space and `<br>`→`<br />` normalization).** So the grey/small/italic rendering is real, not stripped. Because the footer adds one intentional `<a>` anchor, the send tests assert the ONLY anchor is the unsubscribe link (`(result.match(/<a /g)).length === 1` + `href="{unsubscribe_link}"`), NOT `not.toContain("<a ")`. Guard: the "visible unsubscribe footer" + spacer + idempotent-with-footer tests in `tests/unit/send.test.ts`. Do NOT switch `{unsubscribe_link}` to `{{...}}`, and do NOT move the footer outside the strip-and-reappend region (breaks idempotency).

**HTML-formatted, HTML-separated.** The signature MUST be wrapped in `<p>...</p>` (use `<br>` for in-sig line breaks). Separator is `<p>--</p>`, NOT `\n\n--\n`. Reason: Instantly's HTML sanitizer aggressively strips plain text and bare `--` outside element wrappers on PATCH round-trip — only `<a>` anchors and tag-wrapped content survive. An earlier plain-text signature was reduced to a stray `<a>distribute.you</a>` anchor on every PATCH (historic damage 2026-05-28: ~700 rows shipped with stacked broken anchors and no signature text). Guard: `should append HTML <p>--</p> separator + signature to body` + sibling cumulative-strip tests in `tests/unit/send.test.ts` assert the `<p>--</p>` form.

`stripAccountSignature` is HTML-tolerant. It looks for the EARLIEST occurrence of any of these standalone `--` markers (RFC 3676 sig delimiter, in its plain or HTML-wrapped forms):

- `\n\n--\n` plain (with optional trailing space, e.g. `\n\n-- \n`)
- `<p>--</p>` paragraph-wrapped (with optional `&nbsp;`)
- `<br>--<br>` line-break-wrapped
- `<div>--</div>` div-wrapped

…and slices everything from the marker onward. If no marker matches, body is returned unchanged. Senders whose original body legitimately contains one of these markers will lose content past that point on a re-send — accepted edge-case.

Historic bug 2026-05-28: the original `stripAccountSignature` matched only the plain `\n\n--\n` marker. Bodies stored as HTML never matched, so every retry-stuck re-send appended a fresh signature on top of the existing one. A row redispatched 72 times shipped a body with 72 stacked signatures. Fix: HTML-tolerant marker list + strip-then-append in `buildEmailBodyWithSignature`. Guard: this section + the `stripAccountSignature` and `buildEmailBodyWithSignature` cumulative-stack tests in `tests/unit/send.test.ts`.

If you add a new HTML wrapper form (e.g. `<section>--</section>`), add a regex to `SIG_MARKERS` AND a unit test case covering both the marker shape and a 3-stacked case for that shape.

## Escaped-newline repair — pending steps only

The body this service PATCHes into Instantly arrives verbatim from the caller (`bodyHtml`, email-gateway → this service); `buildEmailBodyWithSignature` only appends the signature block. So an email that ships with a VISIBLE `\n` (the two characters backslash + `n`) was born upstream, in **content-generation-service**: its plain-text→HTML conversion splits on REAL newline characters, and when the LLM's structured output returns the body with newlines OVER-ESCAPED there is nothing to split — the whole email ships as one paragraph with the escape sequences intact. Prod evidence 2026-07-30: campaign `007ee456…` (`joby@littleandlargepubcompany.co.uk`) delivered `…hospitality groups.\n\nThey specialize in…` to the prospect. **Do NOT "fix" this by normalizing caller bodies on the send path** — the producer owns its own output, and a consumer-side rewrite of every inbound body would silently mask a producer regression.

Measured against prod 2026-07-31: **53 of 40,979** delivered campaign configs carry a literal escape (~0.13%), continuously from 2026-05-27, across EVERY cold-email workflow (lithium, legato, ballad, granite, helium, pelican, moraine, arcadia, rampart, navigator) and both `sales-` and `pr-cold-email-outreach` — model behaviour, not one broken prompt. Of those, only **10 active campaigns / 16 un-dispatched steps** were still repairable; the rest had already sent every step.

`npm run cleanup:escaped-newlines` repairs the repairable part. Pure logic in `src/lib/escaped-newlines.ts` (`hasEscapedNewlines` / `fixEscapedNewlines` / `planStepFixes`, unit-tested `tests/unit/escaped-newlines.test.ts`); the script does only Instantly + DB IO.

- **Only UN-DISPATCHED steps are rewritten** (`step > lastSentStep`, where `lastSentStep` = MAX(step) of REAL `inferred=false` `email_sent` silver events). A dirty step that already went out is left alone and WARNed, never silently repaired: the email is gone, so a rewrite would only alter the historical record Instantly holds.
- **Source of truth = Instantly.** The DB narrows candidates (`status='active'` AND the latest bronze config carries a literal escape **OR the campaign has no bronze config at all** — 218 active campaigns had none, and skipping them would have been an unverified gap); the dirty fact and the bodies acted on are read live via `getCampaign`.
- **The transform is per-`<p>` block**, so a split re-opens the paragraph with the SAME attributes (the unsubscribe footer is a styled `<p>`). Outside a `<p>` every escape degrades to `<br>` — it never fabricates an unbalanced `</p><p>`. Idempotent by construction (no literal escape survives), and the signature block + footer come out byte-identical, so `stripAccountSignature` / `buildEmailBodyWithSignature` idempotency still holds.
- The PATCH sends the FULL step array back (Instantly REPLACES `sequences`), unmodified steps included. Dry-run by default; fail-loud per campaign (a partial repair must not read as a clean run).

**⚠️ ANY sweep that selects `instantly_campaigns WHERE status='active'` and then calls Instantly per row MUST exclude the reservation sentinels — `AND instantly_campaign_id NOT LIKE 'reserving:%'`.** A DIS-148 reservation is an in-flight claim, not an Instantly campaign: the row is `active`, it has no bronze config (so it lands in every "no config → check it live" branch), and `GET /campaigns/reserving:<uuid>` 400s `params/id must match format "uuid"`. The sentinel is a REAL row by design (the column is `notNull().unique()`), so this is not bad data to clean up — every consumer that treats `instantly_campaign_id` as an Instantly id has to filter it. The existing readers get this right (`retry-stuck`, the cost resolvers) because they join through committed rows; a NEW standalone sweep is where it bites. Found by the prod dry-run of `cleanup:escaped-newlines`, 1 sentinel in 245 candidates.

**A CLI whose candidate selection is hand-written SQL MUST be dry-run against PROD before merge — unit tests mock `db.execute` and therefore cannot see the selection SET at all.** They validate the pure transform and nothing about which rows reach it, so an over-broad `WHERE` (the sentinel above), a mis-parsed column, or a silently-empty result all ship green. The same blind spot the node-postgres array-parsing note calls out, one layer up: there the mock hides a VALUE mis-parse, here it hides a ROW-SET defect. Read the dry-run's own counts against a number you derived independently (a `psql` query straight against the prod database), not just against "it printed something".

## Campaign-schedule timezone — a CLOSED vendor enum, resolved never forwarded

`campaign_schedule.schedules[].timezone` is a **closed enum of 102 values** ([create-campaign](https://developer.instantly.ai/api-reference/campaign/create-campaign) → `campaign_schedule.schedules.items.properties.timezone.enum`), a Windows-style list carrying roughly one representative zone per UTC offset — NOT "any IANA zone". Anything outside it 400s the create outright: `body/campaign_schedule/schedules/0/timezone must be equal to one of the allowed values`, and the run dies **before any email exists at Instantly**, after the lead was served and its body generated and paid for. Silent waste, not a missed send.

**The zone is now also PERSISTED (`instantly_campaigns.timezone`, migration `0046`) and read back by send selection**, because the Mon-Fri 08:00-17:00 schedule runs in the RECIPIENT's zone while the mailbox's quota is a UTC day — so the zone decides which day of that quota each send spends. Stored RAW; the enum snap below is applied where a day (or a request body) is computed. See [Account selection](#account-selection--lifecycle-gated-read-from-silver).

**Every value on the campaign-creation path goes through `resolveInstantlyTimezone` (`src/lib/instantly-timezone.ts`) — never pass a caller zone straight into the body.** The timezone is a scheduling PREFERENCE, so it degrades, never blocks. Graded resolution: (1) already an enum member — checked on the RAW input, **before** canonicalization, because the enum itself carries legacy spellings whose primary names are absent (`America/Godthab`, `Asia/Rangoon`, `Africa/Blantyre`); (2) its canonical primary name (reuses `canonicalIanaTimezone`, so `Asia/Calcutta` / `US/Eastern` / `Japan` land for free); (3) the enum member with the closest UTC-offset SIGNATURE sampled at four points across the year, same-region preferred then earliest enum position; (4) `America/Chicago` when absent / empty / not an ICU zone. Total — nothing throws, every path ends on an enum member.

**Step 3 is load-bearing, do NOT replace it with a CLDR `windowsZones` mapping alone.** CLDR is what the enum is built from and resolves most volume, but it leaves **US Pacific** — our second-largest zone — unresolved: no enum member shares Pacific's DST signature since `America/Dawson` stopped observing DST in 2020. Signature distance lands Pacific on `America/Dawson` (exact in summer, one hour late in winter — acceptable for an 08:00-17:00 window, and far better than not sending). Measured mappings: New York→Detroit, Denver→Boise, London→Isle_of_Man, Berlin/Brussels/Amsterdam/Budapest/Oslo/Rome/Stockholm/Zurich→Belgrade, Sofia→Bucharest, Shanghai→Hong_Kong, Phoenix→Dawson.

**The enum is PINNED in `tests/unit/instantly-timezone.test.ts`** — the resolver trusts the list, so a value the vendor rejects cannot be caught at runtime, only by that test. The suite also asserts every `Intl.supportedValuesOf("timeZone")` entry resolves to an accepted member (the "no input can 400 this field" criterion).

Incident 2026-08-07/08: lead-service's `timezone` went from 0 populated rows to ~95% overnight (upstream enrichment), so real IANA zones started reaching Instantly for the first time. 91 then 79 send-errors — 100% of all send-errors in the window — fleet `email_sent` 1044 → 759 → 131/day, ~$7.80 of LLM spend burnt on emails never sent. ## Per-brand re-contact window — the send-time half of a rule the serve path cannot finish

A brand's prospect must not receive two cold emails from us inside **three months**. That rule is enforced twice, on two different facts, and BOTH halves are required:

- **Upstream, at SERVE time** (human-service `suppression.ts`) — before we pay to reveal an email. It works: zero re-serves inside the window since it shipped.
- **Here, at SEND time** (`findRecentBrandContact`, `src/lib/recontact-window.ts`, called from `POST /orgs/send`) — this section.

**The second half is not redundant, and the upstream guard structurally cannot cover it.** A serve and an actual email are separated by the sending queue, which has run up to three months behind — a lead handed over in May leaves in August. So a perfectly compliant serve still produces an email days after the previous one landed in the prospect's inbox. Measured in prod 2026-08-28: **2,709 pairs** of emails to the same person for the same brand under 90 days apart across 11 brands, **222 of them in the last 30 days**, worst gap **25 seconds**. **Nothing in the fleet knows what was actually SENT except this service** — it performed the terminal action against the vendor. Do NOT resolve this by asking another service; the send evidence is ours, and delegating it re-creates the bug.

- **It is a LOOKUP of our own send ledger, not a detector.** One row, one timestamp, one comparison. No ratio, no threshold, no heuristic — the moment you find yourself counting something, you have written the wrong thing.
- **Evidence = a REAL (`inferred = false`) `email_sent` silver event** on a campaign whose `brand_ids` overlap this send's `x-brand-id`. An inferred row is a synthetic predecessor projected from a downstream event: it asserts a send nobody witnessed, so refusing a live send on one would refuse on a fabricated fact. Both transports converge (webhook AND self-send dispatch promote `email_sent` through the same `promoteEvent`), so there is ONE source of send truth regardless of which pipe carried the mail.
- **The window is `now() - interval '3 months'`, evaluated by Postgres** — byte-identical in meaning to `windowCutoff()` on the serve side. Calendar-accurate, NOT a 90-day approximation: two halves of one rule must not drift. Do not change it here alone.
- **The identity key is `lower(trim(email))`**, the same normalization the serve path applies — `Joe@X.com` and `joe@x.com` are one inbox, and a case-sensitive match would let exactly that pair through. Served by the hand-written expression index `instantly_campaigns_lead_email_lower_idx` (migration `0040`; drizzle has no expression-index form, so it is documented as a comment in `schema.ts` — do NOT drop it on a `db:generate` diff). Prod EXPLAIN: 43ms seq-scan → 10ms indexed.
- **⚠️ THE GATE RUNS BEFORE THE RESERVATION AND BEFORE THE ACCOUNT SELECTION.** A refused send therefore creates no reservation, no Instantly campaign, no run and no `sequence_costs` row — nothing is billed for an email that never left. Moving it later would leave a reservation (which blocks the pair for 30s) or a step run behind for a send that never happened.
- **The refusal is an explicit `409`, never a silent drop and never a fake 200.** Body carries `code: "recent_brand_contact"` plus the offending `brandId`, `lastEmailedAt` and `windowInterval`. The route's OTHER 409 (identity conflict) now carries `code: "lead_id_conflict"`, so a caller can tell the two apart — and both apart from a transport failure (500).
- **A platform send (no `x-brand-id`) skips the lookup entirely.** The window is PER BRAND; with no brand there is nothing to compare against. That is an absence, not a fallback.
- **Fail loud.** A DB error propagates to the 500 handler. A gate that cannot read its own history must not wave the send through.
- **Only `POST /orgs/send` is gated, deliberately.** retry-stuck's redispatch and the self-send dispatch worker both continue an EXISTING sequence for a person already contacted — that is the same outreach, not a re-contact.
- **KNOWN RESIDUAL, stated rather than papered over:** the gate keys on what was SENT, so two enrollments queued for the same person+brand that have BOTH not dispatched yet still pass. With the queue running months deep this window is real. It is the cross-campaign duplicate concern already documented under [Cross-campaign duplicate audit](#cross-campaign-duplicate-audit--read-only), not a hole in this gate — widening this lookup to cover pending enrollments would turn a send-evidence lookup into a scheduling predicate.

Guard: the "per-brand re-contact window" tests in `tests/unit/send.test.ts` (refuses-inside-window + no-campaign/no-run/no-cost, distinguishable from the sibling 409, first-ever contact unaffected, static SQL shape incl. `interval '3 months'` / `inferred = false` / `lower(c.lead_email)`, brand-less send skips the lookup, fail-loud on a lookup error).

## Send idempotency — reserve BEFORE the external Instantly call (DIS-148)

`POST /orgs/send` is idempotent under retry/concurrency for `(campaignId, leadEmail)`: a retried or concurrent send creates **at most one** Instantly campaign, and the loser returns **200 duplicate** (`{success:true, added:0, duplicate:true}`), NEVER a fatal 409. Trigger for the original bug: when instantly-service is slow, email-gateway's 10s `AbortSignal.timeout` fires and it retries — the abort only cancels the caller's wait, so the retry races the original. Both used to pass a read-only dedup check, both called Instantly (each picking the next sender in rotation → two real campaigns), and the loser's insert hit the unique index → fatal 409 → email-gateway mapped it 502 → Windmill flow failed.

**The fix is an ORDERING invariant in `src/routes/send.ts` — do NOT revert it to read-then-act.** The atomic claim on the `(campaignId, leadEmail)` unique index happens BEFORE `sendLeadToInstantly` (the external side-effect), not after:

1. **Reserve** — one `INSERT … onConflictDoUpdate(target:[campaignId,leadEmail], setWhere: reservation-is-stale).returning({id})`. The reserved row carries a unique **`reserving:<uuid>` sentinel** in `instantlyCampaignId` (column stays `notNull().unique()` — the sentinel is the "in flight" marker; NO nullable column, NO migration, so the 6 reader services that assume non-null are untouched). Winner ⇔ `RETURNING` non-empty. The single upsert covers all four cases: fresh-insert (winner), already-committed real-id row (loser → 200 dup), fresh concurrent sentinel (loser → 200 dup), and **stale** sentinel older than `STALE_RESERVATION_MS` (30s — crashed mid-send → reclaim → winner).
2. **Winner only** → `sendLeadToInstantly` → **phase-2** `UPDATE` overwrites the sentinel with the real `instantlyCampaignId`.
3. **Release on failure** — `sendLeadToInstantly` `!ok`, or any throw in the inner try → `releaseReservation()` `DELETE`s the row **only while it still matches `reserving:%`** (no-op once phase-2 committed) so a later legit retry can re-claim. Fail loud — no swallow.

`authorize` (credit affordability) + the leadId-conflict 409 stay BEFORE the reserve (they early-return without reserving). Cost provision/actualize (`addCosts`) is winner-only in the step loop — losers declare no cost. The leadId-conflict case (same email, different `lead_id`) is still a real **409**, unchanged. Guard: the "Reservation idempotency (DIS-148)" tests + the rewritten duplicate/concurrent tests in `tests/unit/send.test.ts`. This is idempotency-under-retry for the SAME `(campaignId, leadEmail)` — it does NOT dedup across *different* logical campaigns (that's the separate cross-campaign concern below).

**Platform sends (`campaignId=null`) reserve on `(run_id, leadEmail)`, NOT `(campaignId, leadEmail)` — fixed 2026-06-27 (v0.49.2).** Postgres treats every NULL as DISTINCT in a unique index, so for a platform send the `(campaignId, leadEmail)` arbiter NEVER collides → the original DIS-148 reservation silently did NOT cover platform sends, and every email-gateway timeout-retry created a fresh duplicate Instantly campaign. Incident: outlets-service run `27acff0b` fired 80 platform price-request sends; retries produced **160 active campaigns / 80 leads** (each journalist queued for the 3-step sequence twice; 80 dups paused via Instantly + DB during remediation). The fix branches the reservation `onConflictDoUpdate` target in `send.ts`: `campaignId` present → `(campaignId, leadEmail)`; `campaignId` null → **partial unique index `instantly_campaigns_platform_run_lead_active_idx`** on `(run_id, leadEmail)` `WHERE campaign_id IS NULL AND status='active'` (migration `0020_platform_send_dedupe.sql`; partial indexes are hand-written SQL + journal entry, same convention as `instantly_events_one_shot_dedupe_idx` — NOT a drizzle `.where()`, documented as a comment in `schema.ts`; do NOT drop it on a `db:generate` diff). The email-gateway retry forwards the SAME `x-run-id`, so `(run_id, leadEmail)` is the stable idempotency key (verified: all 160 incident rows shared `run_id`). Scoped to `status='active'` so the index covers exactly the live reservation/retry window and builds cleanly against healed prod data (paused/completed historical duplicates are excluded). Edge case: a platform send with `campaignId` null AND `run_id` null (x-run-id is OPTIONAL on `/orgs/send` via `requireOrgId`) degrades to old behavior (no dedup) — acceptable because platform sends in practice always carry `x-run-id`. Guard: the platform-dedup tests in `tests/unit/send.test.ts` (`reserves on the (run_id, lead_email) arbiter` / `platform retry … is an idempotent duplicate`).

## Sending declares NO cost — the mailbox estate is a FIXED cost we absorb (migration 0038)

**This service declares zero cost to runs-service.** The three names it used to write — `instantly-account-email-sent`, `instantly-domain-email-sent`, `instantly-contact-uploaded` — are gone from `/send` and from the retry-stuck redispatch. The Instantly subscriptions (Email Outreach, Inbox Placement, the pre-warmed accounts) and the MailForge / PrimeForge mailbox estate became a **fixed cost we absorb rather than rebill**. The offsetting move is in costs-service, where the markup on everything we DO still rebill went from 4× to 5×.

- **NOT replaced by a zero-priced cost row, and do not "restore" one.** A zero asserts "this cost nothing", which is false — it costs real money, we simply stopped passing it on. Absence is the honest representation. The catalog NAMES stay in costs-service (historical runs rows reference them, and the reconcile sweep still PATCHes old holds by cost id); only their advertisement as a current billable price went away.
- **The per-step RUN stays.** It is the unit of volume — how many sends, for which brand, on which campaign — and every downstream stat reads it. A billing change is not a reason to go blind.
- **There is NO affordability gate on `/send` any more, and that is not a lost gate — it MOVED UPSTREAM.** `authorizeCreditSpend` was deleted from the route (and `src/lib/billing-client.ts` with it, having lost its only consumer, same as `brand-client.ts` did when stop-on-click was repointed). A cold-email run pulls the lead (Apollo credits) and generates the body (LLM tokens via chat-service) before it ever reaches this route, and both still declare and authorize, so an org out of credit fails long before a send. Consequence on the contract: **`/orgs/send` no longer returns 402** — a caller's 402 branch is simply never taken. Do NOT re-add an authorize call here; it would gate live sends on an empty basket.
- **⚠️ Known downstream effect, accepted: the per-brand DAILY BUDGET loosens.** campaign-service paces its cap on COMMITTED spend (provisioned + actual) and its own `gate-check.ts` notes that the bulk of the committed-minus-actual gap was genuine `instantly-account-email-sent` holds for scheduled follow-ups. With those gone, a brand's "Budget spent today" drops and a campaign can commit more work per day at the same configured budget. Mechanical, not a bug — but if the cap needs to bite the same way, that is a campaign-service change, not a reason to re-declare cost here.

## Send cost lifecycle — a hold resolves by REAL send evidence (org + platform)

**⚠️ `sequence_costs` IS THE SEND QUEUE, not just a ledger — this is why the rows survived the billing change above.** Every ops surface reads `status='provisioned'` as "scheduled but not yet sent": the self-send dispatch worker (what actually goes out), the fleet `sending-forecast`, the per-account queue breakdown, capacity-aware account selection, account-health `queueSize`, reconcile's `pendingSends`. Dropping the row along with the cost would have emptied the send pipeline. So `/send` still writes one row per step — it just carries **`cost_id = NULL`** (migration `0038` made the column nullable). Do NOT re-add `.notNull()`: that makes the queue undeclarable without a billing row. The unique index on `cost_id` stays NON-partial — Postgres treats every NULL as distinct, so unbilled rows never collide.

**One row per step now, was two** (one per cost name). Every reader already collapses to `COUNT(DISTINCT step)` / `array_agg(DISTINCT sc.step)`, so counts are unchanged — and the old "`COUNT(*)` doubles the local number vs Instantly's one-per-step remaining" caveat no longer applies to new rows. Keep the DISTINCT form regardless: historical rows are still doubled.

**Settling goes through ONE helper — `settleHoldCost` (`src/lib/hold-settlement.ts`).** The LOCAL status flip ALWAYS happens (it is what removes the step from the due set and makes the dispatch worker idempotent); the runs-service PATCH happens only when the hold carries a cost id, i.e. a historical row from before the cutover. Errors are not swallowed — `updateCostStatus` throws before the local flip, so each caller keeps its own semantics (terminal run-gone 404 → cancel locally; transient → leave `provisioned` for the next sweep). All five settle sites go through it: `handleEmailSent`, `cancelRemainingProvisions`, `reconcileProvisionedHolds`, `retry-stuck`'s `cancelExistingCosts`, `campaign-error-handler`. Guard: `tests/unit/hold-settlement.test.ts` + the unbilled-hold cases in `tests/unit/silver-promote.test.ts`.

A hold MUST still resolve: **actualize** when the step's `email_sent` webhook fires, or **cancel** when the sequence can no longer send that step (reply/bounce/unsub, or the Instantly campaign is paused/completed). The live resolvers are `handleEmailSent` + `cancelRemainingProvisions` in `silver-promote.ts`, fired from `promoteEvent`. For an unbilled hold this is now purely a queue transition; for a historical one it is still a real refund/charge.

**A hold is matched to its send by the per-lead `instantly_campaign_id`, NOT the caller `campaign_id` — persist-at-write (migration 0027).** The pre-0027 resolvers matched `sequence_costs.campaign_id = <caller id>` and early-returned on a null caller id. Platform sends store `campaign_id=NULL` (mig 0017), so the `campaign_id = NULL` predicate NEVER matched and `handleEmailSent` early-returned → **every platform-send email cost stranded `provisioned` forever** (560 rows at the fix; oldest 2026-06-09). The webhook/reconcile side identifies a send by its per-lead `instantly_campaign_id` (globally unique, 1 Instantly campaign = 1 lead), which was never stored on the hold — the classic "writer already held the value, persist it" gap (same family as mig 0025 `account_email`). Fix: `sequence_costs.instantly_campaign_id` column, populated at send time (`send.ts` phase-2 + `retry-stuck` redispatch — the id is already in hand), and the resolvers match on it via `matchesHoldCampaign` (`silver-promote.ts`): prefer `instantly_campaign_id = campaign.instantlyCampaignId` (works for org AND platform); fall back to `(instantly_campaign_id IS NULL AND campaign_id = campaign.campaignId)` for historical ORG rows (persisted pre-0027). The guard is now `if (!campaign.instantlyCampaignId) return` (always present). Do NOT revert the match to the caller `campaign_id` — it re-breaks platform sends. Guard: the "actualizes a PLATFORM send hold (campaignId NULL)" test in `tests/unit/silver-promote.test.ts`.

**Backlog reconcile — `POST /internal/campaigns/reconcile-provisioned-holds` (`src/lib/reconcile-provisioned-holds.ts`).** Unified, evidence-based sweep that supersedes the two single-purpose sweeps (`actualize-orphaned-sends` = the actualize case for org; `refund-stranded-holds` = the cancel case for org finished campaigns — both JOIN `sc→ic ON (campaign_id, lead_email)` and exclude `campaign_id IS NULL`, so NEITHER covered platform or lead-stopped-but-active). It classifies EACH provisioned hold from instantly-service's OWN real (`inferred=false`) silver evidence — NEVER an assumption (the observation that holds sit on `completed` runs is misleading: `send.ts` marks the step run `completed` at dispatch time regardless of whether the email fired):
- real `email_sent` at the hold's step → **actualize** (billable; `hasSent` wins even if the lead later stopped — the email already went out).
- else terminal (lead replied/bounced/unsubscribed on this send, OR its Instantly campaign is paused/completed, OR — for an unresolvable historical platform hold — the lead has no `active` platform campaign left) → **cancel** (refund; will never send that step).
- else in-flight (active campaign, step not yet dispatched) → **SKIP**. Cancelling here would under-bill if the step later sends — this is the legitimate sending-forecast pipeline (`pendingSends`), NOT stranding.

It acts on each hold's OWN `run_id` + `cost_id` (`updateCostStatus`), so it covers org AND platform, resolved AND historical rows with no campaign match. **The classification query MUST resolve the OWNING `org_id`/`user_id` for every hold — the runs-service PATCH authorizes on org scope, so a wrong/`'system'` identity is REJECTED and the hold strands as `transient`, healing nothing (this bit v0.62.1: the sweep read org from the caller-campaign join, which is NULL for platform sends → every platform actualize rejected while the sweep looked "successful"). Resolve via a LATERAL fallback to the lead's own campaign row when the caller-campaign join is empty; before trusting a run, verify the plan has ZERO null-org holds against prod (a unit test mocking identity cannot catch a NULL-from-join).** Idempotent (only `status='provisioned'`), resumable, in-cluster. Pure classifier `classifyHold(evidence)` is unit-tested (`tests/unit/reconcile-provisioned-holds.test.ts`); the route does IO. Body `{ dryRun?: boolean (default TRUE), limit?: number }`: dryRun returns the plan counts SYNCHRONOUSLY (read-only), `dryRun:false` → 202 + background mutation (log `reconcile-provisioned-holds: done`). **Wired into the daily reconcile cron (`reconcile-cron.yml`, commit mode)** as the ongoing self-heal — a transient runs-service error during a live actualize, or a platform send that stops, is drained next run. First prod reconcile (2026-07-11): plan actualize 500 / cancel 189 / skip 22,243. Do NOT reintroduce a live sweep that cancels in-flight (SKIP) holds.

## Self-send transport — dispatching our own mail

We are moving the dispatch off Instantly and onto the same mailboxes directly, to drop the **$97/mo** Email Outreach subscription (issue #590). Instantly is now only an SMTP relay, a scheduler that will not disclose its decisions, and a webhook emitter; everything else is already ours — cadence (`delayForGap`), caps (`rampCapForAge` / `dailyLimitForStatus`), account choice (`accountFillOrder`), the cost lifecycle, the silver event log. A large part of this service exists solely to GUESS what Instantly did (`sending-forecast`, `queue-breakdown`, `reconcile` + its snapshot + the drift audit, `retry-stuck`); owning the dispatch turns those projections into facts and deletes the machinery.

**⚠️ SMTP GOES OUT ON 587 WITH MANDATORY STARTTLS, NOT 465 — the host BLOCKS outbound 465 and 25.** Measured from the box itself: `smtp.gmail.com:465` and `:25` time out, `:587` and `imap.gmail.com:993` connect. That is the usual anti-spam policy on a cloud VPS. The credential spike was run from a LAPTOP, where 465 works fine, so the block only surfaced when the deployed code first tried to dispatch — a component proven outside the machine it actually runs on. `requireTLS: true` is set alongside `secure: false`: on 587 an unencrypted session is syntactically valid, so without it a server that failed to offer STARTTLS would silently put the mailbox password on the wire in clear text. **Any future probe of an outbound path must run from the BOX (or inside the container), never only from a laptop.**

**⚠️ ONE credential resolution serves BOTH sending and measuring — `resolveMailboxCredential` (`src/lib/self-send/mailbox-credentials.ts`) reads the MANUAL key-service list first, then Primeforge.** The manual layer (`mailbox-credentials` platform key, a JSON array carrying `address`, `appPassword`, `smtpHost`, `imapHost` and an optional `authUser`) is what makes a NON-Primeforge mailbox usable at all: Gandi and Mailforge do not hand an existing mailbox's password back over an API, so those credentials are hand-entered. Manual wins, so an operator can override a vendor-reported password without waiting on the vendor.

It used to be forked — the seed harness knew about the manual list while the SENDER only read Primeforge — so a Gandi mailbox could be MEASURED and not SENT FROM, which silently capped the self-send transport at the Primeforge subset. Do NOT reintroduce a second resolver: the seed harness now wraps this same resolution in its own BATCH loader (`loadSeedCredentialResolver`) purely to change the shape, for two reasons the sender does not share — it reads each source once for a ~200-account pool instead of re-paginating the vendor per mailbox, and an unresolvable mailbox is SKIPPED there (unmeasured is honest) whereas on the send path it THROWS (a mailbox we cannot authenticate must abort its send, never degrade to another sender). A key-service **404** on the manual key means "none configured"; every other failure propagates, because could-not-read is not the same fact as there-is-none.

**Deliverability does not change.** Instantly already dispatches the Primeforge mailboxes over Google OAuth, so it is Google's outbound IPs either way. Verified live 2026-08-16 on three separate domains: the Primeforge 16-char **`appPassword` authenticates BOTH `smtp.gmail.com:465` and `imap.gmail.com:993`**, with no Workspace admin action and no OAuth grant, and `[Gmail]/Spam` is readable (which is also what makes an in-house placement-test harness possible later). Do NOT use `smtp.google.com`/`imap.google.com` (wrong hosts) or the vendor's `password` field (interactive login password — both hosts reject it). `resolveMailboxCredential` reads it through the **platform** Primeforge key (`resolvePlatformKey("primeforge")`, org-less — the fleet is ours) and the **direct REST** `/mailboxes` pagination; the forge CLI and the MCP wrapper silently return only the first 10 mailboxes.

**TWO `send_transport` columns, and they are NOT redundant (migration `0035`).** `instantly_accounts.send_transport` is the **POLICY** ("new sends assigned to this mailbox go out over X"); `instantly_campaigns.send_transport` is the **DECISION**, frozen at send time from the chosen account's policy. Freezing on the campaign row is load-bearing: a sequence spans days, so reading the account policy live would re-route a lead's followups mid-flight the moment an operator flips that mailbox — and a lead already pushed to Instantly holds no local step bodies to send from, so its followups would simply STOP. Same persist-at-write reasoning as `account_email` (0025). `resolveTransportForSend` (`src/lib/self-send/transport.ts`) resolves anything that is not exactly `'smtp'` to `'instantly'` — a deliberate asymmetry, not a silent fallback: the only way onto the new pipe is an explicit, reversible `UPDATE`, and an unrecognised value must never divert live traffic onto the newer path. **Rollback is `UPDATE instantly_accounts SET send_transport='instantly'`.**

**Layering: we stay B/S/G, and SILVER DOES NOT FORK.** `instantly_events` + `instantly_campaigns` remain the ONE canonical layer and every ingestion source promotes into it through the same `promoteEvent` — exactly as the webhook path and the reconcile-poll path already converge there. Do NOT create a parallel silver: gold would then have to union two shapes, and the dual-run comparison (one account on `smtp` measured against the rest on the same metrics) would mean nothing. What gets created splits across two layers:
- **`sequence_steps` is SILVER, and is the one piece of genuinely new state.** While Instantly dispatches, the step bodies live there and `instantly_campaigns_config_raw` is only our BRONZE mirror of what they hold; once we send, there is nothing upstream to mirror, so the same content moves UP a layer rather than becoming a second bronze beside Instantly's. Everything else reuses what exists — **the queue is already the set of `sequence_costs` rows still `provisioned`**, so there is NO schedule table and no new accumulator.
- **The wire artifacts are BRONZE, a genuinely parallel ingestion source**: raw SMTP dispatch replies, raw RFC822 of inbound replies/DSNs, raw tracking hits. Named for the TRANSPORT (`smtp_dispatch_raw`, `imap_messages_raw`, `tracking_hits_raw`), never `instantly_*_raw` — they are not Instantly payloads.

**`sequence_steps` indexing (load-bearing).** `step` is 1-based, matching `sequence_costs.step`, and a row's `delay_days` is the gap from ITS step to the next — so the gap `k → k+1` is `row(step=k).delay_days`. Ordered by step, the rows are exactly the 0-based array `delayForGap` already indexes, so the self-send scheduler, the fleet forecast and the per-account queue breakdown keep ONE shared cadence source. A NULL (or an absent row) falls back to `STEP_GAP_CALENDAR_DAYS`, same as a missing bronze config delay — a gap degrades, a step is never dropped. `stepsFromSequenceConfig` drops a body-less step and renumbers contiguously: an empty email is not dispatchable, and a hole in the numbering would desynchronise these rows from the `sequence_costs` steps they pair with. Guard: `tests/unit/self-send-foundation.test.ts`.

**⚠️ `POST /orgs/send` BRANCHES on the transport BEFORE the external call, and the ORDER is the whole point.** The account is selected first (`selectSendingAccount`, split out of `sendLeadToInstantly` precisely so it can run on both paths), its policy resolves the transport, and only then does the Instantly path call Instantly. Reading the transport only at phase-2 — which is what shipped in v0.73.1 — meant a flipped account got its lead pushed to Instantly AND picked up by our own dispatch worker, so **every prospect would have received each email TWICE from the same mailbox**. Nothing caught it because every PR up to then was verified INERT rather than traced on the armed path. Guard: the "does NOT create an Instantly campaign when the account is on smtp" test in `tests/unit/send.test.ts`.

**On the self-send transport `instantly_campaign_id` is a LOCAL id, `self:<uuid>`** (`mintSelfSendCampaignId`). There is no Instantly campaign, but the column is `notNull().unique()` and is the join key for `sequence_costs`, the silver event log, the bronze mirrors and the IMAP correlation — so the id stays and simply stops being an Instantly id. **⚠️ THE `reserving:` SENTINEL RULE APPLIES VERBATIM: any sweep that selects `instantly_campaigns` and then calls Instantly per row MUST exclude `self:%`**, or it asks Instantly about a campaign that never existed (`GET /campaigns/self:<uuid>` 400s on the uuid format, exactly as a reservation sentinel does). Excluded in: `reconcileAll` (skips the row entirely — every phase of it is an Instantly call), `selectOneStuckRow` (its own worker owns the catch-up), `cleanup:escaped-newlines` and `cleanup:stacked-signatures`. That last one never had the `reserving:` guard either — a pre-existing gap fixed alongside. `SELF_SEND_CAMPAIGN_LIKE` is kept in lockstep with the prefix by a test.

**`POST /orgs/send` WIRES the transport — without this the whole path is dead code.** Phase-2 does two things beyond attaching the Instantly id: it FREEZES `send_transport` onto the campaign row (resolved through `resolveTransportForSend` AT THE FREEZE POINT, not merely upstream, so no account object from any source can write an unrecognised value onto a campaign), and it persists the step bodies into `sequence_steps` via `stepRowsFromSendPayload`. Rows are written for BOTH transports — the row is cheap, and having it already there is what makes a later flip a data change rather than a migration. **⚠️ THE DELAY SHIFTS BY ONE: the payload's `daysSinceLastStep` is the delay BEFORE its step, while `sequence_steps.delay_days` is the delay AFTER it** (so a row ordered by step drops straight into `delayForGap`). The gap stored on step `k` is therefore step `k+1`'s `daysSinceLastStep`, and the last step stores null; step 1's own `daysSinceLastStep` is discarded (nothing precedes it). Reading it straight through silently doubles or halves every followup gap. Guard: the `stepRowsFromSendPayload` round-trip tests + the "gap to the NEXT step" test in `tests/unit/send.test.ts`.

**The message is built by the EXISTING body pipeline — `buildEmailBodyWithSignature` — not a second copy.** `src/lib/self-send/message.ts` calls it, so a self-sent email and an Instantly-sent one are byte-identical apart from the opt-out link. Reimplementing the signature here would fork the idempotent strip-then-append logic that TWO production incidents exist to protect (72 stacked signatures; a body reduced to a stray anchor), and the copies would drift on the next change to either. Guard: the "stays idempotent" test in `tests/unit/self-send-message.test.ts`. `subjectForStep` prefixes followups with `Re:` (never doubling an existing one) and `In-Reply-To`/`References` thread the sequence, matching what Instantly does.

**Unsubscribe ships with the SENDER, not with tracking — this ordering is forced, not a preference.** The footer carries `{unsubscribe_link}`, Instantly's **server-side** merge variable, which only Instantly resolves; the moment we dispatch, it would ship to the prospect verbatim as a dead link. So the first PR that actually sends must mint the URL itself. Open tracking is genuinely separable (an untracked email is still a valid email); a dead opt-out is not shippable, legally or for deliverability.
- **Stateless + self-authenticating:** `/u/<base64url(campaignId:leadEmail)>/<HMAC-SHA256>` (`src/lib/self-send/unsubscribe.ts`). No token table, no lookup, and the link stays valid for the life of the secret — which is what an opt-out link must do, since prospects act on old mail. Constant-time compare; a bad MAC and an unknown campaign both 404 so the route cannot enumerate campaigns.
- **⚠️ GET does NOT unsubscribe — do NOT "simplify" it to one-click-on-GET.** Corporate link scanners fetch every URL in an inbound email before the human sees it, so acting on GET would opt out prospects who never clicked and silently kill their sequences. GET renders a confirmation with a POST form; POST acts. That is also what RFC 8058 one-click requires (`List-Unsubscribe-Post` is a POST). Both hits are recorded in bronze regardless — a scanner arriving before the human IS the evidence. Guard: the "does NOT unsubscribe" test in `tests/unit/unsubscribe-route.test.ts`.
- **The opt-out reuses `promoteEvent`, adding nothing.** A real `lead_unsubscribed` event through the shared path makes the existing machinery stop the sequence, cancel the remaining provisioned holds and mark the row terminal, for free. Do NOT reimplement any of that in the route.
- **`SELF_SEND_PUBLIC_URL` is deliberately its OWN var, not the service hostname**: this URL ships inside every cold email, and pointing it at a brand domain would put that domain in the cold stream — the exact coupling `instantly_domain_policy` exists to prevent. Give it a neutral domain CNAME'd to this service. It and `SELF_SEND_UNSUBSCRIBE_SECRET` are read LAZILY AT USE, never captured at module load, so a service deployed without them still boots and serves every existing route — only a self-send dispatch fails, and loudly. Capturing at load would turn a missing var into a boot-loop for a feature nobody has switched on.

**Click tracking — links rewritten through our own redirect (`src/lib/self-send/click-tracking.ts`, route `src/routes/click.ts`).** Instantly gets click data by rewriting links through its custom tracking domain; when we send, we do the same. `rewriteLinksForTracking` runs LAST on the built html and skips anything already on our own origin — which is exactly the opt-out link, the one link a prospect must always be able to trust.
- **⚠️ OPENS ARE NOT TRACKED, on either transport.** `open_tracking: false` is set on every campaign we create — the pixel costs deliverability. Do NOT add one "for parity": there is no parity gap, both transports report zero opens by design.
- **⚠️ THE DESTINATION IS INSIDE THE SIGNED PAYLOAD, never a query parameter.** A redirector that forwards to whatever `?url=` says is an OPEN REDIRECT: anyone can borrow the domain to bounce victims at a phishing page, and the domain gets blacklisted — the exact opposite of what a tracking domain is for. The payload is JSON (a target URL can contain any delimiter you might pick), base64url'd, and HMAC'd with the same secret as the opt-out. `isRedirectableUrl` additionally refuses anything but http(s) EVEN with a valid signature, bounding the damage if the secret ever leaks (`javascript:` / `data:` turn a redirect into script execution).
- **Acting on GET is correct here, unlike the opt-out.** Following a link IS the action and the only side effect is recording it. A link scanner that prefetches inflates counts slightly — the same tradeoff every click-tracking redirect makes, and its hit is stored in bronze with its user-agent so it stays visible. 302 not 301: a permanent redirect would be cached and every later click would skip us entirely.
- Without this, `email_link_clicked` never fires on the self-send transport, so **`stop-on-click` would silently never pause a self-sent lead on a visit-first funnel**. Guard: `tests/unit/self-send-click.test.ts`.

**SMTP failures are classified by REPLY CLASS, and an unknown failure is TRANSIENT.** `src/lib/self-send/smtp.ts`: 5xx = permanent (a real rejection), 4xx = transient (greylisting, rate limit) — the same discriminator `isResumableAccountDetail` already uses for account health. Unclassifiable (a dropped socket, no reply at all) defaults to **transient**: calling it permanent would cancel a lead's remaining steps and its holds on what may have been nothing, whereas a genuinely permanent failure simply says so again on the next attempt. A dispatch that leaves any recipient `rejected` is a failure, never a partial success — one message goes to exactly one prospect, so reporting it as sent would fabricate an `email_sent` event. One connection per dispatch, no pool: at ≤50/day per mailbox, setup is not the bottleneck and a pooled socket would sit idle across the long gaps, which is exactly the socket that gets closed underneath you.

**The dispatch worker owns NO scheduling rules of its own.** `POST /internal/self-send/dispatch` (`src/routes/self-send.ts` → `src/lib/self-send/dispatch-worker.ts`, pure decisions in `dispatch.ts`): which step, when, and how many all come from the shared machinery — the queue is the still-`provisioned` cost ledger, cadence is `delayForGap` over the `sequence_steps` delays, and the cap is the same `min(daily_limit, rampCapForAge)` the Instantly path enforces (computed off the CONSTANT, never the live `daily_limit`, or each sweep re-scales its own last output). 202 + background, log `self-send-dispatch: done`. **Idempotent by construction**: a step leaves the due set the moment its hold stops being `provisioned`, which `handleEmailSent` does while promoting `email_sent` — so a worker that dies mid-run re-selects only what never got that far. Wired to `self-send-cron.yml`, **hourly** (a step's due moment is a timestamp, not a date; a daily sweep would hold a 09:00-due step until whenever it runs). Gated by BOTH `SELF_SEND_DISPATCH_ENABLED` (kills the whole sweep in one env change, no account row touched; 409 tolerated by the cron) AND the per-account `send_transport`.
- **⚠️ A STEP DUE BY CADENCE STILL WAITS FOR THE PROSPECT'S BUSINESS HOURS — `selectDueSteps` filters each sequence on `isWithinLocalSendWindow(asOf, timezone)`.** On the Instantly transport the campaign schedule enforces this; here we ARE the scheduler, so without the gate a lead's first email fires at whatever hour the hourly cron happens to run — 03:00 local for anyone far enough east — purely because their mailbox was flipped to this pipe. The zone comes from `instantly_campaigns.timezone` (migration `0046`), which is why that column exists at all: a `self:` campaign has no bronze config to recover it from. Absent → `DEFAULT_LEAD_TIMEZONE`, the same value the Instantly schedule degrades to, so both transports treat such a lead identically. It is STRICTER than the fleet weekend gate below, never looser — a lead whose local window opens while it is still the weekend here is held to the next UTC sending day, so a send arrives on its booked day or after it, never before.
- **⚠️ NOTHING goes out on a weekend — `selectDueSteps` gates the whole run on `isSendingDay(asOf)`.** Every campaign in the fleet is created with a Mon-Fri window, and both transports run on the SAME mailboxes, so sending on a Saturday would change a mailbox's behaviour purely because of which pipe a lead was assigned to. It would also land real volume on top of the weekly placement test, which runs Saturday PRECISELY because mailboxes are otherwise empty and can absorb a ~30-50 seed spike. An overdue step simply stays overdue and drains Monday, most-overdue-first — nothing is lost. Deliberately a gate on the RUN, not a snap on each step's due date: `sending-calendar` is scoped to send SELECTION, and snapping due dates here would drift this module away from the ops projections, which bucket on the raw nominal day on purpose. Guard: the sending-calendar tests in `tests/unit/self-send-dispatch.test.ts`. (Found only because a sibling PR made the divergence visible; both self-send test fixtures had been pinned to a SUNDAY, so the whole suite was quietly asserting weekend sending.)
- **At most ONE step per lead per run.** Not a throughput limit — a followup only means anything after the previous one has had its gap. A never-contacted lead is due IMMEDIATELY (there is no prior step to measure from; anchoring on "now" would invent a delay nobody configured), and a step at or below the last sent one is skipped rather than re-sent.
- **An account with NO capacity row has NO room, not full room.** A missing row means we could not establish that mailbox's limits, and inventing capacity is exactly how a fresh mailbox gets pushed past what Gmail accepts. Most-overdue-first, ties broken on campaign id for determinism.
- **⚠️ A permanent 5xx is NOT automatically a bounce — classify WHO it is about (`classifyPermanentFailure`), or you poison lead data.** `recipient` (RFC 3463 subject `5.1.*` addressing / `5.2.*` mailbox, or a bare 550/551/553) → the address is bad → promote `email_bounced`, stop the sequence. `sender` (everything else: `5.4.5` daily limit, `5.7.x` policy, reputation) → **WE** were refused, the prospect is fine and untested → record it, leave the hold, touch NO lead state; account health owns the mailbox side. Recording a sender-side throttle as a bounce marks a perfectly reachable prospect undeliverable forever on a fact about our own mailbox. This repo already paid for the same confusion in the other direction (a prod audit found 9 of 12 deactivated accounts were refused over `Recipient address rejected: Domain not found` — a list-hygiene problem misfiled as a sender problem). **The enhanced-code separator may be a HYPHEN, not whitespace** — SMTP's multiline form writes `550-5.4.5 Daily user sending limit exceeded`, so a `(?:^|\s)` regex silently classified the single most common Gmail throttle as a recipient bounce. Caught by test, not by review. Guard: the `classifyPermanentFailure` + worker failure-routing tests.
- Unclassifiable → **transient**, retried next run. Fail-loud PER STEP: one dead recipient domain must not stop the fleet's sending for the day, and every outcome — sent, permanent, transient — lands in `smtp_dispatch_raw`. A step with no persisted body is skipped loudly; sending an empty email or guessing at content is worse than not sending.

**Reading what comes BACK — the IMAP poller (`src/lib/self-send/imap-poller.ts`, pure classification in `inbound.ts`).** Once we dispatch ourselves nobody tells us a prospect replied or a message bounced: it lands as mail in the sending mailbox and we read it. **The correlation key is a `Message-Id` we know went out** (in `In-Reply-To`/`References` for a reply, inside the delivery-status report for a bounce). Do NOT match on recipient address — the same prospect can legitimately sit in two sequences, and a prospect frequently replies from a DIFFERENT address than the one we mailed — and do not match on subject, which any client may rewrite.
- **⚠️ THAT KEY HAS TWO SOURCES, AND THE SECOND ONE IS WHAT MAKES A MAILBOX INSTANTLY DISABLED READABLE AT ALL (`src/lib/self-send/instantly-sends.ts`).** `smtp_dispatch_raw` only holds mail OUR dispatcher put on the wire, so on a mailbox whose sequences Instantly sent there is nothing to match and every reply classifies `unrelated` — however carefully we read the inbox. That is not theoretical: a mailbox Instantly has DISABLED stops emitting `reply_received`, and the rescue that moves it onto `send_transport='smtp'` does NOT move the sequences already in flight (they stay frozen on `instantly`, per the persist-at-write rule). So the inbox is read by nobody. `loadKnownSends` therefore ALSO reads what Instantly sent from that mailbox out of bronze `instantly_emails_raw` (`payload->>'eaccount' = <mailbox>`, `ue_type = '1'`), whose payload carries the RFC 5322 `message_id` Instantly actually put on the wire — present on 100% of 112,626 outbound rows measured in prod, so it is an EXACT key, not a heuristic. The lead comes from the campaign JOIN, never the payload (`payload->'lead'->>'email'` is null on inbound). Our own dispatch wins a collision: it is a fact about a send we made, and it additionally resolves the step-0 manual-reply case the mirror knows nothing about. Instantly encodes the sequence position as `<variant>_<stepIndex>_<subStep>`, so `0_1_0` is our step 2 (`parseInstantlySequenceStep`); an unreadable step DROPS the row rather than defaulting it, because the inference rule projects an `email_sent` from whatever step a reply carries and a wrong one fabricates a send. Cost 2026-09-02: a prospect wrote "I would be interested, send me the costs and details" and the only place it existed in the fleet was the owner's personal Gmail — sequence not stopped, step-3 hold still `provisioned`, no forward, no `conversation` trigger. Guard: `tests/unit/imap-known-sends.test.ts`.
- **⚠️ AMBIGUITY IS DECLINED, NOT GUESSED — `correlateSend` (pure, in `inbound.ts`) returns `matched` / `ambiguous` / `none`, and the poller must never `.find()` the first match.** Several referenced ids resolving to the SAME sequence is the normal case (`References` carries the whole thread, so a reply to step 3 names steps 1-3) and the LATEST step wins. Only DISTINCT campaigns are ambiguous, and there the message is stored in bronze, WARNed with both campaign ids, and promoted to nothing. The asymmetry is the reason: a wrong attribution puts a stranger's words on a lead AND stops the wrong sequence, while declining leaves a message a human can still read. Counted as `ambiguous` in the summary.
- **⚠️ THE CORRELATION IS NOT THE BOTTLENECK — THE MAILBOX IS. A prospect reply that was FORWARDED AWAY without keeping a copy is unrecoverable, and no code change reaches it.** Measured 2026-09-03 after the widening shipped, over a 120-day catch-up (`{sinceDays:120}`): 89 accounts polled, **50,725 messages read, 50,461 stored `unrelated` — and ZERO of them carried ANY `In-Reply-To`/`References` at all.** They are ordinary mail (newsletters, notifications, warmup), not replies we failed to match. The 74 `bounce` rows in the same sweep all correlated, which is the positive control proving the key works. So a poll returning `replies: 0` is NOT evidence of a correlation bug — check whether the inbox HOLDS threaded mail before touching the matching logic.
  - The lead that motivated this work is the worked example: `kevin.lourd@marketingagency.network` resolves **456** known-send keys (correlation ready), and its INBOX held **one** message — a retention probe. The mailbox is not Gmail (folders are `INBOX` and `Junk` only, so there is no `[Gmail]/All Mail` to fall back to) and the reply had been forwarded to a personal Gmail without retaining a server copy. It is gone; the fix protects the NEXT reply, not that one.
  - Consequence, and it is an OPS precondition rather than a code gap: **a mailbox on the self-send transport must RETAIN a copy of inbound mail** (forward-and-keep, not forward-and-delete), or the poller reads an empty inbox forever while looking perfectly healthy. Check this BEFORE concluding a mailbox is uncredentialed or the correlation is broken.
  - **Do NOT measure credential coverage from `imap_messages_raw` absence** — the same trap the seed-placement note records for `seed_placement_dispatches`. "Never read" conflates no-credential, empty-inbox and alias fan-out. Measured properly against the credential SOURCES, 88 of 90 smtp accounts are in the `mailbox-credentials` key and the other 2 are Primeforge-resolved: coverage is complete, and 54 of 90 simply had nothing to read. Note also the aliases: five accounts per domain share ONE real mailbox, so `molthost.org` reads the same 3,761 messages four times — waste, not a bug (bronze dedups per `(account_email, message_id)`).
- **⚠️ A HUMAN REPLY ON AN INSTANTLY-TRANSPORT SEQUENCE MUST ALSO STOP THE SENDER — `stopLeadSequence` (`src/lib/stop-lead-sequence.ts`), the SAME helper `manual-qualifications.ts` uses.** `promoteEvent` does our half (marks the row, cancels the remaining holds) and tells Instantly nothing. We only ever read this reply ourselves BECAUSE Instantly could not — its IMAP link to the mailbox is broken, so its own stop-on-reply never fired and it keeps dispatching at someone who already answered. Without this the correlation fix above makes the reply VISIBLE without making it STOP anything, which is half a fix. A `self:` sequence needs nothing extra (no campaign to pause; `promoteEvent` already did both halves). Do NOT re-implement the branch — one helper, three callers (manual qualification, this poller, the inbound-replies backfill).
- **⚠️ AN AUTORESPONDER IS NOT A REPLY, and this is load-bearing.** `reply_received` is in `SEQUENCE_STOP_EVENTS`: it halts the sequence AND cancels the lead's remaining holds. Filing an out-of-office as one would end the outreach — and refund the spend — for a prospect who has not engaged and is back at their desk next week. Silver already has the right vocabulary: **`auto_reply_received`** classifies neutral in `REPLY_CLASSIFICATION_MAP` and is deliberately absent from the stop set. `isAutoReply` keys on RFC 3834 `Auto-Submitted` plus the deployed conventions that predate it (`X-Auto-Response-Suppress`, the `Precedence: auto_reply|bulk|junk` family, vendor `X-Auto*`); any ONE is enough.
- **⚠️ CLASSIFICATION ORDER IS LOAD-BEARING: bounce BEFORE auto-reply BEFORE reply.** Some systems stamp DSNs `Auto-Submitted: auto-replied`, so testing auto-reply first would file a HARD BOUNCE as a harmless vacation notice and leave the sequence hammering a dead address. Guard: the "DSN stamped Auto-Submitted" test in `tests/unit/self-send-inbound.test.ts`.
- **A message referencing none of our sends is `unrelated` and touches nothing.** These are real mailboxes that also receive ordinary mail; acting on an uncorrelated message would attribute a stranger's email to a lead. Every message the poller reads is still stored in bronze INCLUDING the ignored ones — that row is what makes "why was this reply never picked up?" answerable.
- **Idempotent WITHOUT a cursor, on purpose.** Each run re-reads a `POLL_WINDOW_DAYS = 3` window and the unique `(account_email, message_id)` index on `imap_messages_raw` makes the overlap a no-op. `POST /internal/self-send/poll` accepts `{sinceDays}` to widen it for a ONE-SHOT catch-up on a mailbox that has just become readable (a newly credentialed inbox, or one Instantly disabled months ago) — clamped into `[3, 365]` inside `runPoll`, and the cron never sends it. **That override is the ONLY instrument that can reach those replies: Instantly could not log into the mailbox either, so its Unibox never mirrored them and no bronze backfill can find them.** Do NOT build a bronze-side reply backfill for this — measured 2026-09-02, 331 of the 333 campaigns holding an inbound message in `instantly_emails_raw` already carry their reply event and 138 of 141 replied campaigns already carry a reply KIND, so that sweep's candidate set is empty by construction. ⚠️ When measuring it, note `instantly_events.campaign_id` holds the **INSTANTLY** campaign id (`promoteEvent` writes `input.instantlyCampaignId` into it), not the caller's — joining an event to a campaign on `lead_email` alone, or on the caller `campaign_id`, reports hundreds of phantom missing replies. A stored cursor that drifts (clock skew, a failed run, out-of-order delivery) silently LOSES replies, and a lost reply means we keep emailing someone who already answered. The overlap costs a few redundant reads and cannot lose anything.
- **⚠️ The poll runs INSIDE the dispatch run (`runDispatch({pollFirst:true})`), awaited — NOT as an earlier cron step.** Both endpoints answer 202 and work in the background, so a separate poll step would still be running while dispatch selected, and the ordering would be hoped-for rather than real — the same create-then-read-in-one-run trap that made the placement cron ingest week-old results. Reading first means a prospect who replied since the last sweep is already out of the queue. A poll failure is logged and does NOT block the send; the worst case is one extra email inside the window, the same latency the webhook path already carries. `POST /internal/self-send/poll` stays available for a manual read; the cron calls `/dispatch` ONLY.

**Reply QUALIFICATION on this transport is ours, via chat-service (`src/lib/self-send/qualify-reply.ts`).** While Instantly sends, IT classifies inbound replies and we trust that verdict; with no Instantly to ask, the poller classifies the reply itself.
- **⚠️ Qualification does NOT decide whether to stop the sequence.** `reply_received` is in `SEQUENCE_STOP_EVENTS`, so ANY human reply already stopped it and cancelled the remaining holds — positive, neutral or negative — BEFORE this runs. Qualification only decides what the reply MEANS, which drives the forward to the agency inbox and the gold sentiment stats. Do NOT make the stop conditional on a sentiment.
- **The label set is exactly the existing silver vocabulary** (`REPLY_CLASSIFICATION_MAP`), enforced by a lockstep test. `lead_closed` is deliberately excluded even though it is a positive event: a closed deal is an outcome someone records, not something a reply's text can support.
- **An unusable classification promotes NOTHING — it never defaults to neutral.** Asserting a sentiment we did not obtain puts a fabricated judgement into gold, and a wrong "neutral" on a hot reply reads as a real verdict. The reply stays recorded in bronze and the sequence stays correctly stopped; only the sentiment is absent, counted as `unqualified` and logged.
- **LLM spend goes through chat-service, which owns the cost** — this service declares none. The poller is a sweep with no inbound request, so it takes `POST /internal/platform-complete` (platform run, no org balance gate): the reply belongs to our own outreach, not to a customer request we can bill. `deepseek-flash` (DeepSeek V4 Flash), thinking disabled, temperature 0 — a short closed-set classification run once per reply, on the cheapest model in the catalogue that does it reliably. `ChatProvider`/`ChatModel` in `chat-client.ts` carry the `deepseek` slug for it; chat-service accepts it on `/internal/platform-complete` and already holds its catalog prices. Quoted history is stripped first so the model judges what THEY wrote, not our own email quoted back.
- Requires `CHAT_SERVICE_URL` + `CHAT_SERVICE_API_KEY` in this service's env file on the box.

**⚠️ EVERY campaign side effect that "pauses on Instantly" needs a LOCAL equivalent here, and the asymmetry REVERSES.** On the Instantly transport the rule is: pause on Instantly, write NOTHING locally, and let the nightly reconcile's `finish` closure cancel the holds and mark the row — marking it terminal yourself makes `reconcileAll` SKIP it, so the holds leak forever. On the self-send transport there is no campaign to pause AND reconcile skips a `self:` row outright, so nothing downstream will ever discover the stop: both halves MUST happen locally. `stopSelfSendSequence` (`src/lib/self-send/stop-sequence.ts`) does them in order — cancel the holds (the org's refund) THEN mark the row, because a crash between the two should leave a row that still sends over one that has silently lost its refund. Branched in `stop-on-click.ts` and `manual-qualifications.ts`. Guard: the transport-split tests in `tests/unit/self-send-side-effects.test.ts`, which assert the Instantly path still touches NO local state.

**The positive-reply forward rebuilds the thread from BRONZE on this transport** (`src/lib/self-send/thread.ts`). Instantly's `/emails` holds the conversation for its own sends; ours is split across `smtp_dispatch_raw` (what we sent, `outcome='sent'` only — a refused attempt produced no email) and `imap_messages_raw` (what came back, `kind IN ('reply','auto_reply')` only — an `unrelated` row is stored on purpose and must never leak into a thread). Interleaved by time it is the same conversation, emitted in the SAME `ThreadMessage` shape and through the SAME `htmlToText`, so the forwarded email is identical whichever pipe carried it. Without this branch a positive reply would query `/emails`, find nothing, and forward an empty thread.

**The silver table name stays `instantly_events` even for non-Instantly events.** Renaming the service's largest table for zero functional gain, in the middle of changing the send path, is pure churn — revisit only once Instantly is fully gone.

**Not in scope: the separate $47/mo Inbox Placement subscription.** It is independently purchasable ([plans overview](https://help.instantly.ai/en/articles/10273259-instantly-plans-overview)), so it survives cancelling Outreach and is replaced later by our own seed harness. ⚠️ Cancelling Email Outreach also **pauses the Instantly DFY accounts** ("Without the Email Outreach plan, your DFY/Pre-warmed accounts will be paused automatically") — retire that pool BEFORE cancelling, not after; the Primeforge mailboxes are self-connected and unaffected. ⚠️ And `DELIVERY_EVIDENCE_MAX_AGE_DAYS = 16` makes the placement subscription a HARD deadline, not a soft degradation: with no fresh test, every account ages into `delivery_evidence_stale` within 16 days and the whole fleet stops sending.

## Transport A/B — the split is per SEQUENCE, and it counts ASSIGNMENTS

The Instantly Email Outreach subscription is being cancelled, so the two pipes have to be compared on real traffic first. `src/lib/self-send/transport-split.ts` splits NEW sequences between them; `POST /orgs/send` calls `resolveTransportForNewSequence` right after the account is chosen, and the result is frozen on the campaign row exactly as the account policy used to be.

- **⚠️ Per SEQUENCE, never per EMAIL.** Alternating within a sequence pushes the lead to Instantly AND has our worker dispatch it, so the prospect receives every followup TWICE — the bug the transport branch already exists to prevent (#11784b4).
- **⚠️ Do NOT "simplify" this into a per-ACCOUNT split.** Half the mailboxes on each pipe leaves the arms at different positions in `accountFillOrder`, which saturates the head before touching the tail — so one arm can legitimately take nearly all the volume and the other almost none (measured: 32 Gandi accounts at the head of the order sent 0 in 7 days while Primeforge accounts took 200 each). Splitting per sequence on the SAME mailboxes also removes mailbox quality as a confounder, which is what makes the two arms comparable at all.
- **It counts ASSIGNMENTS (campaign rows created in 24h), not emails dispatched.** That is what we control and it is visible immediately; counting sends would let Instantly's queue depth steer our split, since it dispatches on its own schedule. How much each pipe actually manages to send is a RESULT of the experiment, not an input. `reserving:%` sentinels are excluded — an in-flight claim has not frozen a transport yet.
- **Minority-side, not strict alternation.** Two concurrent sends can read the same counts and land on the same side; the next few tip back. A "look at the last row and take the other" rule needs no lock either but oscillates instead of converging. Ties go to `smtp` — the experiment exists to learn about the newer pipe.
- **Precedence:** an account explicitly set to `smtp` stays `smtp` (that column is the manual override AND the rollback lever, so the experiment must not move a pinned mailbox); then experiment-off or an unauthenticable mailbox → `instantly`; otherwise the minority side.
- **A mailbox with no credential stays on Instantly, stated rather than discovered.** `isSelfSendCapable` reads the credentialed set (manual key + Primeforge) through the 60s `getOrSetCachedStats`, because otherwise every send would pay key-service plus a vendor pagination. 68 of the 83 `in_production` accounts are credentialed; the 15 that are not are the Instantly-DFY mailboxes, whose Google Workspace belongs to Instantly (no app password can exist) — and they sent 13 emails in 7 days.
- **Armed by `SEND_TRANSPORT_AB_ENABLED=true`, default OFF**, read at USE so a deploy without it behaves exactly as before. Kill switch is that one variable; no account row is touched by the experiment.

## Account selection — lifecycle-gated (read from silver)

`sendLeadToInstantly` picks the sending account in two stages (`src/lib/send-lead.ts`):

1. **`fetchInProductionAccounts(featureSlug)`** — the eligible pool, read PURELY from silver `instantly_accounts` (NO live `listAccounts` on the send hot-path). An account is sendable ⇔ `lifecycle_status == 'in_production'`. The lifecycle is auto-derived (health==100 AND delivery==100, not a brand/Instantly-deactivated domain) and maintained by `reconcileLifecycle` — see [Account lifecycle](#account-lifecycle--auto-driven-per-account-state-bsg). There is NO `MIN_WARMUP_SCORE` constant, NO `BLOCKED_DOMAINS` constant, and NO manual flag any more. If the pool is empty, `sendLeadToInstantly` returns `no_healthy_accounts_available` (a 500 upstream) — **NO silent fallback to weaker senders**.
   - **Feature carve-out (`instantly_account_feature_policy`, migration `0030`) — the fleet is CARVED, NOT symmetrically partitioned. Import to Instantly uses the mailbox's **`appPassword`** field (16-char Google app-password, spaces stripped) + hosts **`imap.gmail.com`/`smtp.gmail.com`** (the CSV export's `password` = the login password and `imap.google.com`/`smtp.google.com` hosts are BOTH wrong → `IMAP connection failed`).

**Full mailbox list IS retrievable — hit the DIRECT REST API, not the CLI/MCP wrapper (2026-07-10 correction).** The prior note claimed a "hard 10-cap, no pagination, >10 not retrievable" — that is TRUE only for the **forge CLI / MCP `primeforge_list_mailboxes`** (it silently ignores `offset`/`limit`/`domainId`/`search` and returns the first 10). The underlying **direct REST** `GET https://api.primeforge.ai/public/mailboxes?workspaceId=<wks>&limit=100&offset=<N>` (header `Authorization: <PRIMEFORGE_API_KEY>`, raw, NO `Bearer`) paginates correctly and returns ALL mailboxes (verified: 35 mailboxes across 10 domains fetched via `limit=100`, and `offset=10&limit=50` returns rows 10-34). Each row carries `address`, `appPassword`, `status`, `domainId`. So when you need app-passwords for >10 mailboxes, use direct REST — do NOT fall back to the dashboard. Auth key = `PRIMEFORGE_API_KEY` from the `primeforge` skill's `secrets.env` (the `MAILFORGE_API_KEY` 401s on Primeforge). `export_mailboxes` is still broken via the MCP/CLI (needs a nested `platform`+`email`+`password` body the wrapper doesn't pass — use the paginated list instead). `bulk_dns_update` only does DMARC/forwarding (no custom-record add, so no CTD CNAME via API).

**Reconnecting a broken Instantly Google account — diagnose the `status_message` FIRST, don't guess (2026-07-14).** A Primeforge Google account shows as broken in Instantly with two DIFFERENT states that need OPPOSITE fixes — read `GET /api/v2/accounts/{email}`'s `status_message` (`{code, responseCode, response}`) before touching anything:
- **`status:-1` "Needs review" + `autofix_failed:true` = broken Instantly↔Google OAuth link.** The `PATCH imap_* + resume` trick (IMAP creds via Primeforge `appPassword` on `imap.gmail.com`/`smtp.gmail.com`) only flips it to `1` MOMENTARILY then it reverts — Instantly keeps the account `provider_code 2` (an attempted `provider_code` PATCH is accepted-but-ignored, stays 2) and keeps re-testing the dead OAuth. The DURABLE fix is the **native Primeforge → Instantly export** (Primeforge UI: Mailboxes → Export → Instantly, entering the Instantly LOGIN email+password + the case-sensitive workspace name — ours is `GrowthAgency.dev`). That export re-authorizes the Google domain-wide delegation (Instantly's OAuth Client-ID `536726988839-…apps.googleusercontent.com`) server-side. The Primeforge `export_mailboxes` API needs those same `platform`+`email`+`password` login creds (NOT the API key), so it can't be driven with the Instantly API key alone — it's a UI/login-cred action. There is NO Instantly API endpoint to re-mint Google OAuth (probed `/reconnect`,`/reconnect-oauth`,`/reauth`,… all 404); OAuth can only be re-granted by the domain's Workspace admin (= Primeforge for these domains).
- **`status:-3` + `status_message.responseCode:550` `"550-5.4.5 Daily user sending limit exceeded"` = Gmail throttling, NOT a connection/OAuth/export problem.** Instantly deactivates the account because Google rejects the sends. This is caused by OUR sending volume exceeding Gmail's per-user daily limit on (newish) Workspace mailboxes — do NOT chase OAuth/export fixes, and do NOT open a Primeforge refund ticket for it (the raw 550 proves it isn't their export). Fix = lower per-account volume so total (campaign `daily_limit` + `warmup.limit`) stays under the Gmail cap; the block auto-clears after ~24h of reduced sending. 2026-07-14 incident: the whole pre-warmed fleet (~15 accounts) escalated `-1 → -3` on this 550; remediation was capping every Google (`provider_code 2`) + IMAP-Mailforge (`provider_code 1`) account to `daily_limit:45` + `warmup.limit:5` (= 50/day, was 60) via `PATCH /accounts/{email}` (merge `warmup` to preserve `increment`/`advanced`). Repeated `resume` nudges make throttling WORSE — stop nudging once you see the 550. **⚠️ `status:-3` alone does NOT mean "Gmail 550 throttle" — READ the `status_message`.** `-3` just means "Instantly deactivated the account because its last send was rejected"; the rejection can be anything. Prod audit 2026-07-28 found 12 accounts at `-3` and **not one** was a 550: 9 were `450 4.1.2 … Recipient address rejected: Domain not found` (the PROSPECT's domain is dead — a list-hygiene issue misfiled as a sender problem) and 2 were `450 4.7.1 … Too many mail per day for sasl <user>` (the Gandi relay's own cap, not Gmail's). All were `provider_code 1` = the legacy Gandi/Mailforge IMAP fleet, where a Gmail per-user quota cannot apply at all. The actionable discriminator is the **SMTP reply class**: `5xx` = permanent (real throttle/block, do not nudge), `4xx` = transient (safe to resume — this is what `isResumableAccountDetail` keys on).

## Reply kind — what KIND of reply arrived, and nothing about the deal

`src/lib/reply-kind.ts` is the single source of the qualification vocabulary. It answers one question — what did the prospect send back — and deliberately says nothing about how far the deal got.

**The two axes used to overwrite each other, and that is the bug this vocabulary removes.** `lead_meeting_booked` and `lead_closed` are funnel outcomes about a LEAD: channel-agnostic (a meeting booked off an ads campaign is the same fact) and owned by the service that records lead outcomes, which features-service already reads for funnel counts. While they lived in this vocabulary they shared one statement per lead, and gold keeps only the LATEST sentiment per `(campaign, lead)` — so a lead who replied positively and then had a meeting booked read as having no reply sentiment at all. Stating one fact destroyed the other. **Do NOT put a deal-progress value back in this vocabulary**, and do NOT start recording deal outcomes here.

**The vocabulary (10 values).** Positive splits four ways because "positive" alone cannot separate "interested but not the buyer" from "wants a call", which is exactly the distinction the people reading these replies act on:
- `lead_interested` — personally interested. `lead_referral` — not personally interested but relevant; hands us the right person. `lead_info_requested` — wants to know more. `lead_meeting_requested` — wants to book.
- negative, split by whether the "no" is about the MOMENT or about the PERSON: `lead_not_interested` (declines today — a commercial judgement, the lead stays recyclable), `lead_wrong_person` (the mirror of `lead_referral`: not the right contact AND nothing handed back) and `lead_changed_job` (has left the role we were selling to). The last two are DISQUALIFYING — objective facts about the person, permanent for this lead; the first is not. **Do NOT collapse `lead_changed_job` into either sibling**: folding it into `lead_not_interested` is the conflation that turns the negative bucket into a dumping ground and loses recyclable pipeline, and `lead_wrong_person` says we picked the wrong contact, which someone who once HELD the role would read back as false. It stops the sequence like every other human reply; the disqualification lives in the kind, not in the stop.
- neutral: `lead_neutral`. Kept as its own kind — it is the most-used value on the live console (39 of 84 statements in prod) and calling those leads negative would assert something nobody stated.
- automated: `lead_out_of_office`, `auto_reply_received`. Never stops the sequence (RFC 3834 — the prospect is back next week and has not engaged).
- **A lead with none of these has no reply.** "None" is the absence of an event, not a writable value.

**`lead_meeting_requested` is a REPLY fact ("they asked for a call"), NOT `lead_meeting_booked` ("a meeting is on a calendar").** The second one is owned elsewhere. Same word, different axis — do not merge them.

**Legacy values are resolved at WRITE, never at read.** `POST /orgs/manual-qualifications` still ACCEPTS `lead_meeting_booked` / `lead_closed` because the staff console is still sending them; removing them from the write path is a separate, later change once both dashboards ship their new pickers. `resolveReplyKind` maps them to **`lead_interested`** — the domain fact is only "they had by definition replied positively", and resolving to `lead_meeting_requested` would re-encode the deal axis into the reply axis. It THROWS on anything else: a statement we cannot record must not be recorded under a fabricated kind. Bronze `instantly_manual_qualifications_raw.status` keeps the raw human click (append-only, never rewritten); the new `reply_kind` column (migration `0039`) freezes the resolution, so no consumer ever needs a read-time translation of a legacy value. `GET /orgs/manual-qualifications` returns BOTH — `status` is the audit of what a person clicked, `replyKind` is the vocabulary.

**⚠️ A REFERRAL FORWARDS BUT REPORTS NEUTRAL — the forwarding set and the coarse classification map are DELIBERATELY NOT the same set, and a test asserts the divergence rather than equality.** `REPLY_KIND_CLASSIFICATION` projects `lead_referral` to **`neutral`**, while `POSITIVE_REPLY_KINDS` (which drives the agency-inbox forward) still contains it. They answer different questions: forwarding asks "is this worth a human's eyes" (a name to talk to obviously is), the coarse map asks "was this a buying signal we count and price". The coarse value is what reaches email-gateway → lead-service → features-service and becomes the brand's positive-reply count, its cost-per-positive-reply and the learning-threshold gate — so pricing "not me, but talk to X" as sales interest is wrong, and the downstream dashboard already excludes it. Cost 2026-08-29: a customer requalified a lead interested → referral, and the dashboard still read "1 sales interest" for a lead its own leads board correctly showed as merely contacted. **Do NOT restore the lockstep**, do NOT drop `lead_referral` from the vocabulary or from forwarding, and note it still STOPS the sequence like every other human reply. Three surfaces carry the same rule and must move together: `REPLY_KIND_CLASSIFICATION`, `buildRepliesFromDetail` (`repliesPositive`/`repliesNeutral`) and the `timeToFirstPositiveReply` latency SQL. Backfill: migration `0042` re-derives `reply_classification` (campaign row + gold `instantly_lead_status_current`) for every row whose effective non-withdrawn statement is a referral — idempotent, referral-scoped, 2 rows in prod.

**Instantly still reports deal progress, and `promoteEvent` resolves it at the single ingestion choke point** (webhook `lead_meeting_booked`/`lead_closed`, poll `lt_interest_status` 2/3/4 → `lead_interested`). Bronze keeps the raw provider payload; silver carries the new vocabulary only. So `REPLY_CLASSIFICATION_MAP` (now just a re-export of `REPLY_KIND_CLASSIFICATION`), `SENTIMENT_EVENT_TYPES`, `POSITIVE_QUALIFICATION_EVENT_TYPES` and the self-send `QUALIFICATION_EVENT_TYPES` all stay one list, and an event type absent from the map is genuinely not a reply kind.

**Migration `0039` appends, never rewrites.** It adds `reply_kind` (backfilled then `NOT NULL`), and APPENDS a resolved `lead_interested` silver event for each deal-progress statement — the original `lead_meeting_booked`/`lead_closed` event rows stay exactly as they are (audit), but they are no longer in the vocabulary, so without the append those 8 leads would read as having no reply at all. The appended row shares the statement's timestamp and bronze `source_row_id`; the latest-sentiment projection breaks the tie on `created_at DESC`, so the resolved kind wins. Idempotent. Prod scale: 84 statements / 79 pairs, 4 `lead_meeting_booked` + 4 `lead_closed`, and those 8 mirrors were the ONLY deal-progress events in the whole silver log.

**`repliesDetail` gains `referral` / `infoRequested` / `meetingRequested` / `changedJob` (additive) and emits `meetingBooked` / `closed` as a hard `0`.** Those two are REQUIRED fields of the published `email-domain-contract` `RepliesDetail`, so they stay in the shape until contract v2 drops them — the zero is honest (this service records none), not a stale count. `repliesPositive` sums the positive-CLASSIFICATION kinds only — `interested` + `infoRequested` + `meetingRequested` — and a `referral` is counted in `repliesNeutral` (see the divergence rule below).

## Disqualified vs recyclable — the status read carries the reply KIND, not only its coarse class

The reply-kind vocabulary already draws the line the sales canon draws: `lead_not_interested` is a "no" about the MOMENT (the person is still reachable, the lead stays recyclable) while `lead_wrong_person` and `lead_changed_job` are objective facts about the PERSON and permanent. That distinction did not survive the trip downstream — only the coarse `positive | negative | neutral` projection reached the read side, so every negative arrived at lead-service looking identical and every one of them landed in the customer's **Disqualified** column, including the ones that were merely "not right now".

`POST /orgs/status` now emits two ADDITIVE fields on every `StatusScope` (`byCampaign[*]`, `campaign`, `brand`):

- **`replyKind`** — the reply kind currently on record, `null` when none is.
- **`disqualified`** — `true` iff `replyKind ∈ DISQUALIFYING_REPLY_KINDS` (`lead_wrong_person`, `lead_changed_job`), from `isDisqualifyingReplyKind` (`src/lib/reply-kind.ts`).

- **⚠️ `disqualified` is STRICTLY a function of `replyKind`, never an independent aggregate.** A `.some(...)`-style "disqualified in any campaign" would let a brand scope report `disqualified: true` beside `replyKind: 'lead_neutral'` — two fields on one row disagreeing about one person. In brand scope `replyKind` is taken from the SAME campaign row that wins `replyClassification`, for the same reason.
- **⚠️ `REPLY_KIND_CLASSIFICATION` is UNCHANGED and must stay so — all three negative kinds still project to `negative`.** features-service counts stats off the coarse value; this is a finer reading of the same statement, not a re-pricing of it. A consumer that reads only `replyClassification` sees no difference at all.
- **Stored on the gold row (`instantly_lead_status_current.reply_kind`, migration `0047`), derived in `refreshLeadStatusCurrent`.** Precedence mirrors the `reply_classification_source='manual'` pin EXACTLY: a standing human statement wins OUTRIGHT (`ORDER BY (k.source='manual') DESC, k.timestamp DESC, …`), and only with none does the latest automatic reply-kind event answer. Do NOT demote manual to a tie-break — a webhook landing after a human statement would then outrank the human while the coarse column beside it stayed pinned to the human's value, and the two fields would contradict each other. A withdrawn statement (`withdrawn_at`) is skipped, so a withdrawal restores the lead to what the automatic classification says.
- The 0047 backfill is set-based (a `DISTINCT ON` over reply-kind events joined to gold), because migrations run BEFORE the port binds. Measured on prod: 698 candidate events, 397 rows updated, **88ms**.

Guard: the recyclable-vs-disqualified tests in `tests/unit/status.test.ts`, the disqualifying-set tests in `tests/unit/reply-kind.test.ts`, and the precedence / withdrawn SQL-shape tests in `tests/unit/status-gold-reply-kind.test.ts`.

## Recorded opt-out — a person can ask us to stop through a channel that is not the link

A prospect rarely clicks unsubscribe. They send an SMS, they call, they reply to a thread somebody forwarded them, they say it in person — and until now none of that could be recorded, so the only way into the opted-out state was a link nobody had clicked. `POST /orgs/opt-outs` records the statement (`src/lib/lead-optouts.ts`, route `src/routes/lead-optouts.ts`, bronze `instantly_lead_optouts_raw` + `instantly_lead_optout_withdrawals`, migration `0047`).

- **⚠️ NEVER inferred.** A row exists because a named staff member stated that a named person asked to stop, through a named channel. Nothing derives an opt-out from a reply, a bounce, a sentiment or a silence. `channel` is REQUIRED and its vocabulary is closed (`sms`, `phone_call`, `email_reply`, `forwarded_thread`, `in_person`, `web_form`, `other`) — an opt-out nobody can audit later is exactly what a consent record must not be. Who / when / how stay recoverable forever via `GET /orgs/opt-outs`.
- **⚠️ It STOPS THE SENDING, and the second half is the one that is easy to miss.** `promoteEvent` promotes the SAME real `lead_unsubscribed` event a clicked unsubscribe promotes — sequence stopped, remaining provisioned holds cancelled, `delivery_status='unsubscribed'` — but that tells the SENDER nothing. The click path gets the stop at Instantly for free because Instantly served the link; this path cannot, because Instantly never saw the SMS. So it ALSO pauses the Instantly campaign (or, on a `self:` campaign, calls `stopSelfSendSequence`), exactly like [Manual qualification](#manual-qualification--stop-the-sequence-on-both-sides). Recording an opt-out and then continuing to email is the legally dangerous outcome (CAN-SPAM, GDPR).
- **⚠️ SCOPE IS THE PERSON, NOT A CAMPAIGN** — keyed on `(org_id, lead_email)`, applied to every campaign the org holds for that address. Honouring "stop contacting me" in one campaign while another keeps sending is precisely the outcome the law cares about. It is also why the request body carries no `campaign_id`: the board card is a lead.
- **It surfaces where a clicked unsubscribe surfaces.** Same event type ⇒ same gold `unsubscribed` column ⇒ `POST /orgs/status` reports it scoped and global, with no second branch for any consumer to learn.
- **Withdrawable, and the read side actually releases.** `POST /orgs/opt-outs/withdrawals` appends a withdrawal (never deletes), marks ONLY the `lead_unsubscribed` events THIS record promoted (`source='manual'` + `source_row_id`) as `withdrawn_at`, and refreshes gold. `refreshLeadStatusCurrent`'s event join carries `AND (e.event_type <> 'lead_unsubscribed' OR e.withdrawn_at IS NULL)` — **scoped to that one event type on purpose: withdrawing a reply QUALIFICATION deliberately does NOT retract the fact that a reply arrived, so a blanket `withdrawn_at IS NULL` would silently flip `replied` back to false, which no withdrawal ever claimed.** A `lead_unsubscribed` the prospect produced by clicking the link is never touched — nobody withdrew that.
- **⚠️ A withdrawal does NOT resume the stopped sequences.** The holds were cancelled and the campaigns paused; silently restarting outreach at somebody who asked us to stop is the one mistake worth being unable to make by accident. A new send is a new decision. Same posture, and the same reasoning, as the manual-qualification withdrawal scope note.
- **Idempotent both ways**: a standing record writes nothing and fires no side effect; a second withdrawal finds nothing standing and returns 404 `no_standing_optout`. The bronze record IS written even when the org holds no campaign for the address (the response then reports `campaignsAffected: 0`) — refusing to record a consent statement because we have nothing to stop would be the wrong direction to be wrong in. A campaign that cannot be paused is logged and counted in `campaignsStopped` rather than failing the whole record.

Guard: `tests/unit/lead-optouts.test.ts` + `tests/unit/lead-optouts-route.test.ts`.

## Manual qualification — stop the sequence on BOTH sides

A manual qualification (`POST /orgs/manual-qualifications`) exists **precisely because Instantly did NOT detect the reply**, so Instantly's own stop-on-reply can never fire. Cancelling the lead's provisioned holds — which the synthesized `reply_received` does through `promoteEvent` — refunds the spend but tells Instantly nothing, so it keeps dispatching the remaining steps to a prospect who already answered. `applyManualQualificationSideEffects` therefore ALSO **pauses the lead's Instantly campaign** (`pauseSequenceOnInstantly`, `src/lib/manual-qualifications.ts`). Do NOT remove the pause on the grounds that the holds are already cancelled: the holds are OUR ledger, the pause is the only thing that stops the actual email.

- **ONE predicate gates BOTH halves — `isSequenceStoppingQualification`**, which resolves the statement to a reply kind first and defers to `isSequenceStoppingReplyKind` (`SEQUENCE_STOPPING_REPLY_KINDS` = every positive + negative + `lead_neutral`; the two legacy deal values resolve into it). **`lead_out_of_office` and `auto_reply_received` are deliberately EXCLUDED** — an autoresponder is not a reply (RFC 3834), the prospect is back next week and has not engaged, so stopping would end the outreach AND refund the spend for someone who never answered. Same reasoning that keeps `auto_reply_received` out of `SEQUENCE_STOP_EVENTS` (`silver-promote.ts`) and out of the self-send inbound classifier. Gating only ONE of the two halves is the bug this section exists to prevent: holds refunded locally while Instantly keeps sending, or a pause with the spend still held. Guard: the stopping/non-stopping + "no status left unhandled" tests in `tests/unit/manual-qualifications-side-effects.test.ts`.
- **MINIMAL, exactly like [stop-on-click](#stop-on-click--pause-when-brand-maximizes-signups-v0501): the side effect ONLY pauses on Instantly.** No local `status='paused'` write, no cost-cancel, no contact-delete inline — the nightly reconcile discovers the paused Instantly status and its `finish` closure does all three. **If you mark the local row terminal here, `reconcileAll` SKIPS it → the finish closure never runs → any residual provisioned hold leaks forever.**
- **Fail-soft** (key-service / Instantly errors swallowed + logged, `sequence continues on Instantly`): the bronze row is already committed when this runs, so throwing would 500 a qualification that did land. Org-scoped — the route is `requireOrgId`, so `orgId` is always present and is threaded into the input.
- **Prod remediation 2026-08-18:** the pause was missing since the feature shipped. 73 manual qualifications existed, 31 whose local row was still `active`; **20 still had un-dispatched steps on an Instantly-ACTIVE campaign** (3 `lead_interested`, 17 `lead_neutral`) and were paused by hand. The 2 most recent were 1-3 days from their next followup.

## Withdrawing a manual qualification — a statement supersedes downward, nothing is erased

A person who states a reply kind and gets it wrong must be able to take it back, so the lead reads exactly as it did before anybody said anything. `POST /orgs/manual-qualifications/withdrawals` (`{campaign_id, email, notes?}`, org-scoped, `x-user-id` required) withdraws the STANDING statement for one (campaign, lead) pair.

- **A correction, NOT an erasure — the append-only bronze posture is right, the gap was that nothing could supersede a statement DOWNWARD.** No row is ever deleted and no `none`/`unset` member enters the reply-kind vocabulary (it is not a kind of reply, and every consumer would have to learn to render it). The statement row stays byte-identical in `instantly_manual_qualifications_raw`; a row is APPENDED to `instantly_manual_qualification_withdrawals` (migration `0041`, bronze, `qualification_id` UNIQUE) recording that it no longer stands, by whom and when. Both halves stay readable.
- **The STANDING statement is the latest bronze row with NO withdrawal pointing at it** (`findStandingManualQualification`) — NOT simply the latest row, which is still the withdrawn one. Keying the withdrawal on the STATEMENT ID rather than on a timestamp watermark is what leaves a later re-statement unaffected, and what makes a second withdrawal of the same statement a no-op at the unique index instead of at a read-then-write race.
- **`insertManualQualification`'s idempotency now compares against the STANDING statement.** Same semantics as before (idempotent on the current value), corrected for the fact that a withdrawn statement is not current — otherwise re-stating the kind you just withdrew would be swallowed as a no-op and the lead could never get that kind back.
- **Silver is MARKED, not deleted — `instantly_events.withdrawn_at` (migration `0041`).** The withdrawn statement's manual mirror event keeps its row (silver is the audit of what was asserted) and the gold current-sentiment CTE (`latestSentimentCteBody`, `analytics.ts`) filters `e.withdrawn_at IS NULL`, so the counters a manual statement moved stop counting it. Only a `source='manual'` row can ever be withdrawn; the column is NULL everywhere else, so no other reader changes behaviour. Silver is derived and rebuildable, which is what makes marking it legitimate where mutating bronze would not be.
- **The pin is RELEASED, which is the whole point of the AC.** `reply_classification` is recomputed from the latest surviving (non-withdrawn) reply-kind event under the SAME latest-wins ordering gold uses, and `reply_classification_source` returns to `'auto'` — so `updateReplyClassification`'s manual-wins short-circuit stops firing and a subsequent webhook is free to classify the reply as it normally would. Nothing left ⇒ `reply_classification` is **NULL**: nothing at all, never a fabricated neutral.
- **Refuses distinguishably, and is idempotent.** Nothing standing → **404** `code: "no_standing_qualification"` with no write (this covers the second withdrawal of the same statement); pair not in this org → **404** `code: "campaign_not_found"`. A caller tells the two apart, and both apart from a 500. Fail loud otherwise — a withdrawal that cannot release the pin must not report success.
- **`GET /orgs/manual-qualifications` returns withdrawn statements too, carrying `withdrawnAt` / `withdrawnBy` (null while standing).** Hiding them would destroy the audit; a consumer that renders a row with a non-null `withdrawnAt` as the lead's current kind is showing a kind nobody stands behind.
- **⚠️ SCOPE, stated rather than papered over: this withdraws the KIND and its pin, NOT the fact that a reply arrived.** A sequence-stopping statement synthesized a `reply_received` event, which stopped the sequence, cancelled the remaining holds and paused the campaign at Instantly — real, already-taken, irreversible actions. Un-asserting the reply while its consequences stand would be incoherent, and re-opening a sequence would re-contact a prospect. The resulting state (a reply on record with no kind attached) is exactly the state of an auto-detected reply nobody has qualified — coherent, not a contradiction. Do NOT "complete" this by retracting the reply event.

Guard: `tests/unit/manual-qualification-withdrawal.test.ts` (marks-not-deletes, pin released to `auto`, null-when-nothing-left, surviving-auto-classification restored, gold-identical ordering + `withdrawn_at IS NULL`, gold refresh, fail-loud), the withdrawal route tests in `tests/unit/manual-qualifications.test.ts`, and the `e.withdrawn_at IS NULL` SQL-shape assertion in `tests/unit/stats.test.ts`.


## Stop-on-click — pause when the CAMPAIGN's funnel opens on a website visit

On a REAL `email_link_clicked` event, if the **campaign** runs a funnel whose first leg is a website visit, the lead's Instantly campaign is PAUSED. The prospect is on the landing page; the conversion happens there, so more cold emails only distract.

**⚠️ The gate is the CAMPAIGN's `funnel_key`, read from campaign-service — NOT the brand's `current_goal`.** It used to read `brands.current_goal === 'signup'` via brand-service, which was wrong on both axes and was corrected 2026-08-19:
- **GRAIN.** A funnel belongs to a campaign. Two campaigns of the same brand can legitimately run different funnels, so a brand-level answer is not an answer to the question asked — it paused sequences that should have kept running and missed ones that should have stopped.
- **SIGNAL.** `current_goal` is a goal in the middle of being retired (campaign-service migration `0042_campaign_funnel_from_goal` rewrites stated goals into stored funnels, and its goal route now runs values through `toRetiredGoal`). `campaigns.funnel_key` is the fact that replaced it.

**The key encodes the funnel's FIRST leg, and that is the whole rule** (`funnelStopsOnClick`, `src/lib/campaign-client.ts`): `visit_form` and `visit_signup` open on a visit → a click means the prospect is already there → STOP. `reply_meeting` opens on a REPLY → a click says nothing → keep sending. A **NULL** funnel does NOT stop — campaign-service's own rule is "a funnel is a fact, never a guess", and pausing a live sequence on an unknown is the wrong direction to be wrong in. A **platform send** (`campaignId` null) belongs to no caller campaign, runs no funnel, and no-ops without calling out.

**A REPLY is entirely separate and unconditional.** `reply_received` is in `SEQUENCE_STOP_EVENTS`, so ANY human reply stops the sequence and cancels the remaining holds — positive, neutral or negative, whatever the funnel or goal. Only an autoresponder is exempt (`auto_reply_received`, deliberately absent from the stop set). Do NOT make the reply stop conditional on anything; this section is about CLICKS only.

- **MINIMAL BY DESIGN — the side effect ONLY pauses on Instantly. Do NOT add cost-cancel / contact-delete / local-terminal-mark inline, and do NOT write local `status='paused'` here.** The existing machinery handles everything downstream, for free: (a) retry-stuck's live-status preflight sees the paused Instantly campaign and SKIPS redispatch (never resurrects it); (b) the nightly reconcile discovers the paused Instantly status → its `finish` closure cancels the lead's remaining provisioned holds (credit refund), deletes the contact (quota reclaim, if `DELETE_FINISHED_CONTACTS_ENABLED`), and marks the local row terminal. **If you mark the local row terminal in the webhook, `reconcileAll` SKIPS it → the finish closure never runs → the provisioned holds leak forever.** Leave the local row `active`; let reconcile discover and heal it.
- **Fail-soft, never throws into the webhook.** Any campaign-service / key-resolution / Instantly-pause error is swallowed + logged (`console.warn`, "sequence continues"). A thrown error would 5xx the webhook and Instantly auto-pauses webhooks after repeated 5xx.
- **Always-on — NO env kill-switch.** Gated only by the campaign's funnel and fail-soft availability of campaign-service: a click on a reply-first funnel is a natural no-op.
- Requires `CAMPAIGN_SERVICE_URL` + `CAMPAIGN_SERVICE_API_KEY` in this service's env file on the box. **`BRAND_SERVICE_URL`/`BRAND_SERVICE_API_KEY` are no longer read by this service** — `src/lib/brand-client.ts` was deleted with this change, since stop-on-click was its only consumer.

## Forward positive replies to the agency inbox

Instantly paywalls its Unibox/CRM, so a positive reply can no longer be seen/actioned from the Instantly UI without paying. The V2 API still exposes replies AND Instantly's OWN qualification, so instantly-service owns the "surface positive replies" loop with **zero dependency on the paid CRM**. When Instantly qualifies an inbound reply positive/interested, silver promotion forwards the **full conversation thread** (every message in order, from/to/date, the lead email, the campaign) to `kevin@distribute.you` (`ADMIN_NOTIFICATION_EMAIL`) via the production transactional-email path (Postmark under the hood). Pure logic in `src/lib/forward-positive-reply.ts`; unit-tested `tests/unit/forward-positive-reply.test.ts`.

- **Trust Instantly's OWN qualification — do NOT build a separate sentiment classifier.** "Positive" = exactly the events that flip `reply_classification='positive'` in silver-promote's `REPLY_CLASSIFICATION_MAP`: `lead_interested` / `lead_meeting_booked` / `lead_closed`. `POSITIVE_QUALIFICATION_EVENT_TYPES` mirrors that set and a unit test asserts the two never drift. `lead_meeting_completed` (interest 3) is deliberately EXCLUDED (not `positive` in the map). Do NOT add a heuristic/LLM classifier and do NOT widen the set without updating the map + the lockstep test.
- **Fired as a fail-soft side effect from `promoteEvent` (`silver-promote.ts`), on REAL (non-inferred) events only** — mirrors stop-on-click. Both the webhook path (`event_type=lead_interested…`) and the reconcile-poll path (`lt_interest_status` → the same event types) converge on it, so a positive qualification observed by EITHER ingestion path forwards once.
- **Exactly-once via an atomic claim on `instantly_campaigns.positive_reply_forwarded_at` (migration `0028`), NOT a webhook-dedup assumption.** The first positive event claims the column (`UPDATE … SET positive_reply_forwarded_at=now() WHERE instantly_campaign_id=$1 AND positive_reply_forwarded_at IS NULL RETURNING`) BEFORE the external send; a webhook retry, a reconcile re-poll, OR a re-qualification (interested→meeting_booked→closed each promote as distinct positive events) find it non-null and no-op. This is load-bearing because the SAME positive signal legitimately arrives via multiple paths + re-qualifications — a `COUNT`/webhook-first-insert guard alone would forward 2–3×. Do NOT replace the claim with "promoteEvent only fires on first insert" (that dedups a single event_type, not the cross-path/re-qualification case).
- **Claim released on send FAILURE (`positive_reply_forwarded_at = NULL`) so a later retry re-attempts** — at-most-once send, biased against the duplicate (the explicit no-go) while still self-healing a transient key/Instantly/email error. On send SUCCESS the claim stays. Do NOT release on success.
- **Thread = `GET /emails?campaign_id` (1 campaign = 1 lead = 1 thread), rendered PLAIN TEXT into `<pre>{{thread}}</pre>`.** The Instantly email object carries `body:{text,html}` + `from_address_email` + `to_address_email_list` on both list + get. Bodies are tag-stripped (`htmlToText`) and rendered plain-text so the template's `{{thread}}` is robust whether or not the engine HTML-escapes. Empty thread (reply not yet synced to `/emails`) still forwards the notification (lead + campaign + qualification) rather than blocking. The `positive-reply-forward` template is deployed at startup in `index.ts`.
- **Fail-soft, never throws into the webhook** (a 5xx makes Instantly auto-pause webhooks). No cost/runs declaration — same as the `campaign-error` admin notification (transactional-email-service owns its own send).
- **Org-scoped v1: platform sends (`orgId` null — e.g. journalist price-requests) are a documented follow-up**, not handled (distinct key path). Reuses `TRANSACTIONAL_EMAIL_SERVICE_URL` + `TRANSACTIONAL_EMAIL_SERVICE_API_KEY` + `ADMIN_NOTIFICATION_EMAIL` — **no new env vars**.

## Answering a sales interest — ask the campaign that was bought for it to run NOW

A reply used to be classified and then nothing ran. campaign-service schedules everything on a clock, so the campaign a customer funded to answer an interested buyer waited for its next tick: a prospect who says "yes, interested" heard nothing for a day, which is precisely the problem that leg was bought to solve. campaign-service shipped the entry point (`POST /internal/campaigns/trigger-for-step`) and nothing in the fleet was asking it. This service is where the reply ARRIVES and where it is QUALIFIED, so this is where the ask belongs — `src/lib/trigger-sales-interest-campaign.ts`, fired from `promoteEvent` beside the agency-inbox forward (unit-tested `tests/unit/trigger-sales-interest-campaign.test.ts`).

- **The ask names a SCOPE and a STEP, and decides nothing else.** `{brandId, offerId, funnelKey, step}` + `x-org-id`. Which leg leaves the step (features-service's published `GET /public/channels` → `legs[]`), which campaign states that leg, and whether it may spend are all campaign-service's — the run starts at `gate-check` like any other, so the affordability gate is untouched. Do NOT resolve a leg, parse a funnel or select a campaign here.
- **The scope is READ off the caller campaign** (`getCampaignTriggerScope` → the same `GET /campaigns/{id}` `getCampaignFunnelKey` already made, now one shared `fetchCampaign`). Nothing is inferred: a campaign stating no brand, no offer or no funnel — and a platform send, which has no caller campaign at all — cannot have a leg resolved for it, so the ask is simply not made. That is an ordinary absence, not a failure.
- **⚠️ The step is `conversation`** — features-service's key, labelled "Sales interest": *a buyer answers and a conversation opens*. Carried VERBATIM; campaign-service matches it against the catalogue and refuses a step nobody publishes.
- **⚠️ The gate is `REPLY_KIND_CLASSIFICATION === 'positive'`, NOT `POSITIVE_REPLY_KINDS` — the divergence is deliberate and a test asserts it.** The forward-to-the-agency-inbox set additionally contains `lead_referral`, because "not me, but talk to X" is worth a human's eyes. It is NOT this person opening a conversation, and firing a funded meeting-booking campaign at someone who just said they are the wrong person is the exact mistake that map exists to prevent (see [Reply kind](#reply-kind--what-kind-of-reply-arrived-and-nothing-about-the-deal)). Do NOT restore a lockstep with the forward set.
- **A brand with no responsible campaign is the COMMON case, not an error.** Most brands buy one leg of one funnel, so campaign-service answers 200 with an empty `legKeys` or a NAMED skip (`unfunded`, `run_in_flight`, `no_workflow` = a channel the customer's own team operates). Those are logged as the ordinary answers they are; only an unexpected failure warns.
- **Fail-soft, and it can never change the qualification's outcome.** Qualifying the reply is the primary job; the trigger is a consequence of it. Every failure is swallowed and logged loudly — a throw here would also 5xx the webhook, and Instantly auto-pauses a webhook that keeps failing.
- **NO queue and NO retry on this side.** sales-lead-service already holds a due-date follow-up queue a scheduled sweep drains, and the campaign reaches the lead on its own next tick regardless — a missed trigger costs latency, never the answer. Do NOT add a claim column or a replay sweep: side effects only fire on the FIRST promotion of an event, so a webhook retry or a reconcile re-poll does not re-ask, and campaign-service skips a run already in flight anyway.
- Reuses `CAMPAIGN_SERVICE_URL` + `CAMPAIGN_SERVICE_API_KEY` (already read by stop-on-click) — **no new env vars**.

## Replying to a lead who replied — same thread, same mailbox, same persona

A cold sequence exists to make someone write back, and until v0.76.0 nothing in the fleet could write back to them. `POST /orgs/replies` (org-scoped, `x-user-id` required) closes that loop. Logic in `src/lib/reply-to-lead.ts` (pure `selectReplyTarget` / `replySubject` unit-tested in `tests/unit/reply-to-lead.test.ts`); the route does IO dispatch only. Body `{campaign_id, email, body_html}` → `{success, reply: {transport, instantlyCampaignId, leadEmail, accountEmail, from, subject, messageId, inReplyTo}}`.

- **⚠️ THE SENDING IDENTITY IS RESOLVED HERE AND IS NOT A CALLER INPUT.** Which mailbox answers is a fact about what already happened — `instantly_campaigns.account_email` (persisted at send time, migration `0025`), with the mailbox Instantly recorded on the inbound message as the fallback for a pre-0025 row. The persona (From display name + signature) follows that same account through `buildFromHeader` / `buildReplyBodyWithSignature`. Do NOT add a `from` field to the request body: a caller-supplied sender lets a reply arrive from a mailbox this prospect has never heard from, on a domain that never contacted them, which is the exact failure the endpoint exists to prevent. Unresolvable → **409 `sending_account_unresolved`**, nothing sent.
- **⚠️ THREADED OR NOTHING — there is no fresh-email fallback.** The anchor is the prospect's **LATEST** inbound message (they expect the answer under what they said last), never one of ours (`ue_type` 1/3/4 would open a second branch of the conversation). No inbound at all → **409 `no_reply_to_thread`**. Every refusal is an explicit status plus a named `code` (`campaign_not_found` 404, the three 409s, `reply_dispatch_failed` 502) so a caller branches on the reason; nothing is swallowed and nothing degrades into a cold email.
- **Transport-aware, because the fleet runs two pipes** — resolved from the campaign row's frozen `send_transport`, the same DECISION every followup already reads. Instantly: `POST /emails/reply` with `reply_to_uuid` = the inbound email's id (`replyToEmail` in `instantly-client.ts`). Self-send: we dispatch it ourselves with `In-Reply-To` = the prospect's Message-Id and `References` = the whole conversation (our `smtp_dispatch_raw` sends interleaved with their `imap_messages_raw` replies, oldest first) — a mailbox we hold no credential for → **409 `mailbox_credential_unavailable`**, never a send from somewhere else.
- **The body is signed HERE, and deliberately WITHOUT the unsubscribe footer.** `buildReplyBodyWithSignature` (`send-lead.ts`) is the same strip-then-append as `buildEmailBodyWithSignature` — same `stripAccountSignature`, same `<p>--</p>`, same per-account signature, same `f(f(x))===f(x)` idempotency the two stacked-signature incidents exist to protect — minus `UNSUBSCRIBE_FOOTER_HTML`. That footer carries `{unsubscribe_link}`, Instantly's SERVER-SIDE merge variable, which only resolves on a campaign send: on a one-to-one reply it ships to the prospect verbatim as a dead link. And a bulk opt-out footer under a personal answer reads as a mail-merge. The RFC 8058 `List-Unsubscribe` pair on the original outreach is untouched; the self-send reply carries no `headers` of its own for the same reason.
- **⚠️ A self-send reply is recorded in bronze `smtp_dispatch_raw` at `step = 0` (`MANUAL_REPLY_STEP`) — NOT a sequence step, and NOT a `sequence_steps` row and NOT a hold.** Sequence steps are 1-based everywhere (`sequence_costs.step`, `sequence_steps.step`), so 0 is unambiguously "outside the sequence" and the row can never enter the dispatch queue. The row must exist for two reasons: `imap-poller`'s `loadKnownSends` correlates the prospect's NEXT answer through its Message-Id, and `fetchSelfSendThread` reads our reply back out of it (which is why that query now falls back to `d.payload->>'subject'` / `->>'bodyHtml'` when the `sequence_steps` join misses). **`loadKnownSends` maps a step-0 row to the campaign's MAX sent step**, because attributing an answer to step 0 would put a step that does not exist into silver and the inference rule would then project a step-0 `email_sent` nobody sent. A refused attempt is recorded too (`outcome='transient'`), same evidence trail the dispatch worker leaves.
- **`loadStepContent`'s `References` now order by `dispatched_at` alone, not `step, dispatched_at`** — chronological is what RFC 5322 wants, it is identical to step-order for pure sequence dispatches, and a step-0 reply must not sort ahead of step 1.
- **Declares NO cost**, exactly like the sequence sends: the mailbox estate is a fixed cost we absorb rather than rebill, so a zero-priced row would assert something false (see [Sending declares NO cost](#sending-declares-no-cost--the-mailbox-estate-is-a-fixed-cost-we-absorb-migration-0038)). It also promotes NO silver event — a reply we sent is not one of the sequence's `email_sent` steps, and minting one would corrupt step accounting, the per-account queue attribution and the re-contact window.
- **It does NOT restart anything.** The lead's reply already stopped the sequence and cancelled the remaining holds; answering them is a conversation, not a resumed sequence.

## Inbound-replies backfill — bronze holds the words, silver never heard about them

`instantly_emails_raw` mirrors Instantly's Unibox, prospect replies included. Silver records only THAT a lead replied, and it learns that from a WEBHOOK. So the two can legitimately disagree — a webhook Instantly never delivered (it disables the subscription after repeated failures; see [Webhook ingestion](#webhook-ingestion--post-webhooksinstantly-never-answers-non-200)), an inbound the Unibox backfill mirrored long after the fact — and in every such case the prospect's words sit in bronze while the sequence keeps running.

`POST /internal/audit/inbound-replies-backfill` (platform-scoped) promotes what is already mirrored. Logic in `src/lib/inbound-replies-backfill.ts` (pure `looksLikeAutoresponderSubject` + `promoteCandidate` unit-tested). Reads NOTHING from Instantly and sends nothing — a promotion of facts we already hold, so it declares no cost (the LLM spend is chat-service's, as always).

- **⚠️ THE CLASSIFICATION DECIDES WHETHER TO STOP — the OPPOSITE order from the live poller, and the difference is forced by the evidence available.** The poller reads a real RFC 5322 message, so `isAutoReply` rules an autoresponder out from `Auto-Submitted` and friends BEFORE `reply_received` is promoted. Instantly's stored payload carries no headers at all — a subject, a body, its own `ue_type`. Here the reply KIND is the only discriminator, so NOTHING is promoted until it is known. Promoting `reply_received` first and correcting after is not available: it stops the sequence and cancels the lead's remaining holds, and most of this backlog is out-of-office. Safe direction, stated: when in doubt, do NOT stop.
- **`dryRun` DEFAULTS TO TRUE and answers SYNCHRONOUSLY with the plan counts** — the hand-written candidate SQL is exactly what a unit test cannot check (mocks validate the transform, never the row SET), so the row set is readable against prod before anything is written. `dryRun:false` → 202 + background (`inbound-replies-backfill: done`); `limit` bounds a batch, **live sequences first** (`ORDER BY (status='active') DESC`) because those are the ones still emailing someone who already answered.
- **Idempotent by construction**: a promoted candidate gains the very event the candidate query excludes, so a second run selects it no more and reports zero.
- **The candidate gate excludes BOTH `reply_received` AND `auto_reply_received`.** A campaign already carrying the auto event has been classified — by Instantly's own webhook, which saw the real headers — and re-deciding it here from a subject and a body would be this service overruling better evidence with worse.
- **Silver source is `emails_backfill`, deliberately NOT `poll_emails`.** Both read the same table, but the reconcile poll carries Instantly's OWN verdict while this sweep carries our classifier's read of the body. The two disagree about where the judgement came from, and that is what the `source` column is for.
- **⚠️ MEASURED AGAINST PROD 2026-09-02 IT FINDS ZERO, AND THE BRIEF THAT ASKED FOR IT HAD MISREAD ITS OWN SAMPLE — record this before someone "fixes" the gate.** The claim was "239 campaigns hold an inbound with no `reply_received`", which is literally true (238), but the reason is that they DO hold `auto_reply_received`: Instantly's webhook already classified them, correctly, as autoresponders. **Campaigns holding an inbound with NEITHER event: 0.** Two of the three leads named as "genuine human replies never qualified" were autoresponders on inspection — an Italian out-of-office, and a canned "I need to protect deep-focus time" reply — and the third had no bronze row at all. So the sweep ships as a standing self-heal for the webhook-loss case, not as a repair of a known backlog. **A dry run returning 0 is the expected result, not a broken query.** Do NOT widen the gate to `reply_received`-only to make it "find" the 238: that would re-file 238 correctly-classified autoresponders as human replies, stopping 61 live sequences and refunding spend that was correctly spent — the precise failure the classification order exists to prevent.

## Reading a conversation — the words, not just that a reply happened

`POST /orgs/replies` could already ANSWER a prospect; nothing could READ what they wrote. A caller could learn THAT someone replied (delivery status, reply classification, reply kind) and nothing about WHAT they said, so a worker drafting the answer was reduced to a template — the exact failure the reply path exists to avoid. `GET /orgs/conversations?campaign_id=&email=` (org-scoped, `x-user-id` required) returns the exchange. Logic in `src/lib/lead-conversation.ts`; the route does IO dispatch only.

- **⚠️ SAME IDENTITY, SAME LOOKUP AS THE REPLY.** It takes the exact `(campaign_id, email)` pair `POST /orgs/replies` takes and resolves the sequence through the SAME exported `loadCampaign` — so a caller that can answer a lead can read the thread it is about to answer, with nothing extra. Do NOT add a second lookup: two answers to "which sequence is this" is how a worker reads one conversation and answers into another.
- **Both transports, one response shape.** The consumer cannot know which pipe carried a given prospect (exactly as the reply endpoint cannot): Instantly's Unibox via `listEmails` + `selectThreadMessages`, or bronze via `fetchSelfSendThread`. Both already produce the SAME `ThreadMessage`, which is what makes one shape honest for both.
- **⚠️ It does NOT start at the prospect's first reply, unlike the positive-reply forward.** `messagesFromFirstReply` is right for a human reading the newest part (the reply quotes the rest beneath it) and wrong here — half of what the prospect is responding to is OUR words, and a worker drafting an answer needs them.
- **⚠️ ABSENT IS NOT EMPTY.** A pair this org holds no record of is **404 `campaign_not_found`**; a sequence that exists with nothing exchanged is **200 with `messages: []`**; a thread we hold but cannot READ is **502 `thread_unavailable`**. Returning an empty list for either failure would claim the prospect said nothing, which is a claim we cannot make.
- **Org scope is in the lookup itself** (`org_id = <caller>`), so another org's campaign reads as absent, never as a thread. The response echoes the STORED lead-email casing, not the caller's — the match is `lower()` on both sides, same normalization as the re-contact window.
- **`text` is markup-stripped through the SAME `htmlToText` the forward uses**, so a message reads identically wherever it surfaces. No truncation is applied here; note a self-send inbound body was stored as the first 4000 characters at IMAP ingestion (`imap-poller.ts`), which is a property of the mirror, not of this read.
- **Sends nothing, declares no cost** — a read of what already happened.

Guard: `tests/unit/lead-conversation.test.ts` + `tests/unit/lead-conversations-route.test.ts`.

## Finding the leads worth reading — `GET /orgs/engaged-leads`

`GET /orgs/conversations` returns what a prospect wrote, but only for ONE `(campaign_id, email)` pair the caller must already know. A dashboard holds a LEAD, not a campaign id, and had no way to tell which of an org's ~47k contacted leads ever engaged — so the conversation read was reachable only by someone who already knew the answer. This is the discovery half. Logic in `src/lib/engaged-leads.ts`; the route does IO dispatch only.

- **⚠️ THE GATE LIVES IN THE LIST, NOT IN THE CONVERSATION READ.** Making `/orgs/conversations` refuse a lead that has not engaged would put the display policy in one call, and would make an endpoint lie about a thread it holds — the exchange with a silent prospect exists, is readable, and a worker drafting a follow-up legitimately wants it. A list is the right home for "which of these deserve attention"; the read stays pure.
- **The gate is `(replied AND NOT unsubscribed) OR clicked`.** Any human reply counts whatever its sentiment: a negative reply is still a conversation someone should read, and a "not right now" is recyclable pipeline (see [Disqualified vs recyclable](#disqualified-vs-recyclable--the-status-read-carries-the-reply-kind-not-only-its-coarse-class)). An unsubscribe request is the one answer that is explicitly a request to stop.
- **Autoresponders need NO exclusion clause, and a test guards the reasoning rather than the output.** `auto_reply_received` / `lead_out_of_office` are distinct event types that never set `replied`, so an out-of-office cannot reach this list — a property of the silver vocabulary, not of this gate. The test asserts those strings are ABSENT from the SQL, so if someone ever makes an auto-reply set `replied`, the gate does not silently start selling vacation notices as sales interest.
- **⚠️ `clicked` is a click on a link WE sent — the only visit signal this service has.** Both transports converge on `email_link_clicked` (Instantly's webhook; our own `/c` redirect on self-send). An anonymous website visit that never went through one of our links is invisible here by construction. Do NOT relabel this field as "visited the site" — that belongs to PostHog, not to this service.
- **⚠️ NO `engagementKind` SCALAR, deliberately — and do not add one.** A lead who clicked Monday and replied Friday has ONE engagement start and TWO signals; a single enum forces either a label that disagrees with its own timestamp or a timestamp that disagrees with its label. `engagedAt` is the EARLIEST of the two, the `replied`/`clicked` booleans say which signals exist, and `firstRepliedAt`/`firstClickedAt` say when each happened. Nothing can contradict anything.
- **Read from GOLD (`instantly_lead_status_current`), never re-aggregated from the event log.** That row already carries the manual-statement precedence, the withdrawn-statement skip and the reply-kind resolution, all of which a fresh aggregate would have to re-implement and would eventually re-implement differently. `disqualified` is derived STRICTLY from `replyKind` via the shared `isDisqualifyingReplyKind` — the same function `POST /orgs/status` uses — so the two surfaces cannot disagree about the same person.
- **Flat read, no cache, no pagination.** Prod `EXPLAIN ANALYZE`: 192 rows in **33ms** for the largest org (seq scan over 47,450 gold rows). The population is small by construction — **863 engaged leads across 33 orgs**, max 192 for one org — so a silent `limit` default would hide the tail; `limit` exists only for a caller that explicitly wants a preview. This route is NOT on the email-gateway send path, so the `getOrSetCachedStats` rule does not apply.
- **Fail loud.** A read failure is a 500, never an empty list — "this org has nobody worth talking to" is the one wrong answer that looks exactly like a correct one. An engaged lead with no engagement timestamp throws rather than being emitted (the boolean/timestamp invariant is verified: 0 violations in prod).
- **Consumer gap, stated:** api-service proxies NEITHER `/orgs/conversations` NOR `/orgs/engaged-leads` today, so the dashboard has no path to either. Both need a gateway hop before a panel can be built.

Guard: `tests/unit/engaged-leads.test.ts` + `tests/unit/engaged-leads-route.test.ts`.

## Mirroring the Unibox on a schedule — the cron, and why it carries NO cursor

`emails-backfill` was manual-only, and it showed: of 112,999 mirrored emails, **99,454 arrived in a single hand-run on 2026-08-29 and 4 in the six days after**. Coverage followed whoever remembered to run it, while Instantly's cancel dialog permanently deletes every conversation a cancelled mailbox carried. `.github/workflows/emails-backfill-cron.yml` runs it **daily at 04:00 UTC** (after the 03:00 reconcile, before the 05:00 infra sync).

- **⚠️ NO CURSOR IS PERSISTED, and adding one would be a regression.** The sweep walks the workspace **newest-first** and its insert conflicts on `instantly_email_id` and does nothing — so a bounded run from the top is incremental BY CONSTRUCTION: everything new since yesterday is on the first pages and everything older is a no-op re-read. A stored cursor would add state to solve a problem the ordering already solves, and a cursor that drifts silently stops mirroring. `{startingAfter}` stays on the endpoint for resuming a FULL historical sweep by hand; the cron never sends it.
- **`maxPages: 60` is sized, not guessed.** Measured volume is ~580 emails/day ≈ 6 pages at 100/page, so 60 is ~10× headroom and runs ~3.5 min at the mandated 3.5s `/emails` pacing — comfortably inside a deploy window, unlike the ~75-minute full sweep that a deploy killed three times in 70 minutes. If a run ever reports `reachedEnd: false` with 60 pages of NEW rows, daily volume has outgrown the cap: **raise `maxPages`, do not add a cursor.**
- **The body is built with `printf`, never a language runtime.** `node` exists only INSIDE the service containers, so a `$(node -e ...)` body would be an empty string in a GitHub runner — which the endpoint reads as "no bound" and dispatches the unbounded sweep the cap exists to avoid. The step also refuses a non-integer `max_pages` rather than sending it.
- Spends nothing metered (a read against a flat subscription), same as the placement tests and the infra sweep.

## Answering a lead on the Instantly transport — the reply is recorded locally too

`POST /orgs/replies` writes a bronze `smtp_dispatch_raw` row at `step = 0` (`MANUAL_REPLY_STEP`) on **both** transports. The self-send branch always did; the Instantly branch returned without persisting anything, so a reply we sent existed **only** in Instantly — the one place a cancellation deletes. Both outcomes are recorded: `outcome='sent'` with the body, `outcome='transient'` with the error, mirroring the self-send evidence trail so a refused reply is not invisible on either pipe.

- **⚠️ `message_id` IS DELIBERATELY NULL ON THE INSTANTLY BRANCH — do NOT "fix" it by storing Instantly's id there.** On the self-send branch that column holds the RFC 5322 `Message-Id` we put on the wire, and `loadKnownSends` correlates a prospect's next answer against it through `In-Reply-To`/`References`. Instantly returns its own email UUID, which appears in no mail header and could therefore never match — storing it in that column plants a correlation key that looks usable and silently never fires. The anchor query already filters `message_id IS NOT NULL`, so NULL keeps the row honestly out of correlation while preserving what we wrote. Instantly's id lives in `payload.instantlyEmailId`, where it is labelled for what it is.
- **The success path fails loud; the failure path swallows.** A reply we cannot record is a reply whose text exists only in Instantly, which is the exact gap this closes. On the failure path the caller is already about to throw the real dispatch error, and losing that cause to a bookkeeping error would be worse.
- `payload.transport` distinguishes the two, and `bodyHtml` is stored only when the message actually went out — nothing left the building on a refusal, so there is no body to keep.

Guard: the four Instantly-branch retention tests in `tests/unit/reply-to-lead.test.ts`.

## Cross-campaign duplicate audit — read-only

`POST /send` dedups on `(campaign_id, lead_email)` (`instantly_campaigns_campaign_lead_idx`), **not** on `(org_id, lead_email)` or `(brand, lead_email)`. So the same person reached by two **different** logical campaigns of the same org/brand creates two separate active Instantly campaigns — the same prospect gets double-contacted. DIS-77 healed this once (Phase A cancelled 6 same-wave dups, Phase B cancelled 51 re-contacts) but its **root-cause prevention in `POST /send` was never shipped**, so duplicates re-accumulate.

`npm run audit:dupes -- <orgId>` is the standing read-only check for this:

- **Duplicate fact = Instantly API, authoritative.** Lists all campaigns (active = status `1`), sweeps all leads via `POST /leads/list`, groups by email, flags any email in ≥2 active campaigns. The local DB is deliberately NOT consulted for the fact — it can be stale.
- **Brand/org = local DB, label only.** Instantly has no brand field; `instantly_campaigns.brand_ids` / `org_id` are joined on `instantly_campaign_id` purely to classify each collision:
  - `same-brand` — ≥2 active campaigns share a brand. True redundant outreach (the dangerous case).
  - `cross-brand` — ≥2 active campaigns, all brands known, none repeated.
  - `unknown-brand` — ≥2 active campaigns but a campaign has no DB row (DB gap; duplicate still real).
- Pure detection logic lives in `src/lib/audit-duplicates.ts` (`findDuplicateContacts` / `summarizeDuplicates`), unit-tested in `tests/unit/audit-duplicates.test.ts`. The script `scripts/audit-cross-campaign-dupes.ts` does only the Instantly + DB IO.
- **Read-only — never PATCH/pause/cancel.** This audits; it does not heal. The healing pass is `heal:dupes` (below); the deferred `POST /send` prevention is separate work.

The **heal** (`scripts/heal-pause-dupe-campaigns.ts`, `npm run heal:dupes`):

- For each email in ≥2 active campaigns, **keep the oldest by `timestamp_created`** (NOT `created_at` — the `/campaigns` list does not return `created_at`; relying on it silently falls back to id-sort and keeps the wrong campaign) and **pause** the rest via `POST /campaigns/{id}/pause`. Collapses retry stacks AND distinct logical campaigns → one active per person.
- Selection logic is pure + unit-tested in `src/lib/heal-duplicates.ts` (`selectCampaignsToPause`); the script does only Instantly IO.
- **Pause, not delete** — reversible. **Dry-run by default**; `--commit` to act; `--limit N` to batch (~110ms/call ⇒ ~75 min for the full ~41k backlog). Idempotent + resumable: re-runs re-sweep live state, so already-paused campaigns leave the active set and are never re-touched.
- **Instantly-only.** No cost refund / local-DB `delivery_status` write — the script talks to Instantly and nothing else; the refund path (`handleCampaignError` → runs-service) is a service-to-service call this laptop-side CLI never makes. Cost reconciliation is a follow-up (DIS-148).
- **Order matters:** deploy the retry-stuck fix (DIS-148) BEFORE running `--commit`, else the worker re-spawns duplicates faster than the heal clears them.
- **Running it locally against prod.** The script runs on your laptop and needs two things it cannot resolve on its own: (1) `INSTANTLY_API_KEY` set directly — this bypasses key-service, which the laptop does not reach; the key you export decides which workspace is audited (the platform key audits the shared workspace); (2) `INSTANTLY_SERVICE_DATABASE_URL` for the brand labels. Both live in this service's env file on the box (`/root/distribute/env/instantly-service.env`) — read them from there and export them into the shell you run `npm run audit:dupes` in. The brand-label DB lookup is chunked + uses `inArray` (drizzle expands `ANY(${jsArray})` into a ROW expression that trips Postgres' 1664-entry limit; never pass a large JS array to `sql\`= ANY(...)\``).

## Finished-contact cleanup — reclaim quota

Instantly's plan limit (e.g. 25,000 "uploaded contacts") counts contacts **currently stored** across all campaigns (active, paused, completed, draft), NOT a lifetime cumulative — **deleting leads from a campaign frees the quota** (~5-10 min sync; confirmed [help.instantly.ai/articles/7918680](https://help.instantly.ai/en/articles/7918680-uploaded-contacts-limits)). Two important facts: the delete MUST be **campaign-level** (`DELETE /leads {campaign_id, delete_list}`) — deleting from "Lists" does not free quota; and **each duplicate counts separately** (same email in 2 campaigns = 2 contacts), so the cross-campaign dupe backlog also costs quota.

Each of our sends is its own per-lead campaign, so once a campaign is **finished** its contact is deletable with no data loss — all engagement history lives in our **local silver DB** (`analytics.ts`/`status.ts` read silver, never Instantly live). "Finished" = Instantly status **paused (2)** (e.g. operator paused after the prospect replied off-Instantly — Instantly never saw that reply) or **completed (3)** (sequence ran out). **Active (1) is never touched. No pause grace period** (locked option A — a pause means "done"; if you ever pause-to-edit-and-resume, the contact gets deleted).

Two paths:

- **One-shot** `npm run cleanup:finished-contacts` — the standing backlog sweep. Pure selection in `src/lib/cleanup-finished.ts` (`selectContactsToDelete` / `countDeletions`, `FINISHED_STATUSES = {2,3}`), unit-tested in `tests/unit/cleanup-finished.test.ts`; the script `scripts/cleanup-finished-contacts.ts` does only Instantly IO (paginated `listAllCampaigns` + `listAllLeads`, then `DELETE /leads` per contact). Dry-run by default; `--commit`, `--limit N`, `--json`. Idempotent/resumable; a 404 delete (already gone) is counted, not fatal. Instantly-only — no local DB write.
- **Recurring** (reconcile) — see [Recurring finished-contact deletion](#recurring-finished-contact-deletion-reconcile) once shipped: the nightly reconcile reads each campaign's Instantly status (already fetched in Phase 0, previously discarded) and, for paused/completed campaigns, deletes the lead **after** the read phases (1-3) backfill all current state, then marks the local row terminal so reconcile stops re-polling it.

**Running it locally against prod** — same as `audit:dupes`/`heal:dupes`: export `INSTANTLY_API_KEY` directly (bypasses key-service, which a laptop does not reach), taking the value from `/root/distribute/env/instantly-service.env` on the box, then `npm run cleanup:finished-contacts`. Run the dry-run first and read the counts before `--commit`.

### Recurring finished-contact deletion (reconcile)

The nightly reconcile (`reconcileAll` → `reconcileOneCampaign`, `src/lib/reconcile.ts`) deletes finished contacts on an ongoing basis so quota doesn't re-accumulate. Decision logic is pure + unit-tested in `src/lib/finished-contacts.ts` (`tests/unit/finished-contacts.test.ts`); reconcile is the IO glue.

- **Signal, zero extra API calls:** Phase 0 already fetches `GET /campaigns/{id}` for `not_sending_status`. It now also reads `config["status"]` (`parseInstantlyStatus`) — the campaign lifecycle code (1 active / 2 paused / 3 completed). Previously fetched and discarded.
- **ORDERING INVARIANT (load-bearing):** the status is *read* in Phase 0 but the delete *executes last*, via the `finish(result)` closure wrapping every return of `reconcileOneCampaign`. So the delete happens AFTER Phases 1-3 (analytics + `/leads/list` + `/emails` backfill) have captured all current state — a late reply/bounce is never dropped by the delete. Do NOT move the delete into Phase 0.
- **What it does** (`deleteFinishedContact`): for a finished campaign (`isFinishedInstantlyStatus` → status 2 or 3), campaign-level `deleteLeads(apiKey, instantlyCampaignId, [leadEmail])` (frees quota), then sets the local `instantly_campaigns.status` to `completed` (3) / `paused` (2) (`localTerminalStatus`). The leadEmail comes from our own row (1 campaign = 1 lead), not a live fetch.
- **COST-CANCEL INVARIANT (load-bearing — prevents the provisioned-hold leak):** in the same `finish` closure, when `isFinishedInstantlyStatus(instantlyStatus)`, reconcile FIRST calls `cancelRemainingProvisions` (exported from `silver-promote.ts`) to cancel the lead's still-`provisioned` `sequence_costs` (refund the org), THEN deletes the contact. A finished (paused/completed) campaign never sends its remaining steps and emits no `SEQUENCE_STOP_EVENT` for the un-sent steps, so without this cancel the provisioned holds leak forever (never actualized via `email_sent`, never cancelled, and the locally-terminal row is then SKIPPED by `reconcileAll` so never revisited). The cancel is **independent of `DELETE_FINISHED_CONTACTS_ENABLED`** (the credit leak exists whether or not quota is reclaimed) and idempotent (only touches `status='provisioned'`). Do NOT gate the cancel on the delete switch, and do NOT move it out of the post-read-phases `finish` closure (a real reply/bounce backfilled in Phases 1-3 must actualize/cancel its steps before this blanket cancel runs). Fixed 2026-06-27 (PR #334, issue #335) after prod showed ~12k provisioned rows stranded on paused/completed campaigns. The **pre-fix backlog** of already-terminal rows is NOT auto-healed (skipped by `reconcileAll`) — drained by the one-time **`POST /internal/campaigns/refund-stranded-holds`** endpoint (`src/lib/refund-stranded-holds.ts`): selects locally-terminal (paused/completed) campaigns that still carry `provisioned` holds and cancels them via the same `cancelRemainingProvisions`. Idempotent + resumable; mirrors `/reconcile` (202 + background, optional `{limit}`). Watch logs for `refund-stranded-holds: done`.

**Triggering `/internal/*` ops endpoints (reconcile, accounts-sync, refund-stranded-holds, actualize-orphaned-sends, placement-test/*) — POST the service's PUBLIC URL from your LAPTOP; do NOT try to run the request from inside the container.** These handlers make outbound service-to-service calls (runs-service / key-service) that only resolve where the service itself runs — but the HANDLER runs there regardless of where the HTTP request ORIGINATED, so `curl -X POST -H "x-api-key: $KEY" https://instantly.distribute.you/internal/...` from a laptop works: the request reaches the running service, and its internal calls resolve on that side. **Confirm the public host rather than hardcoding one from memory** — it MOVED from `instantly.mcpfactory.org` to `instantly.distribute.you` (2026-07-28), and requests to the stale host failed TLS with `CERTIFICATE_VERIFY_FAILED ... Hostname mismatch`, which reads like an outage but was only the wrong name. Key = `INSTANTLY_SERVICE_API_KEY`, read from `/root/distribute/env/instantly-service.env` on the box (take the whole value — a truncated key fails as a 401 and looks like a permissions problem). The genuinely different case is the LOCAL CLI scripts (`npm run audit:dupes` / `heal:dupes` / `cleanup:finished-contacts`): those run node ON the laptop, so they cannot reach key-service at all — export `INSTANTLY_API_KEY` directly to bypass it. Verified 2026-07-08 (accounts-sync trigger, PR #423).

**A script that needs one of this service's own dependencies must run from `/app` INSIDE the container, not from `/tmp` — `docker exec … node /tmp/x.mjs` dies on `ERR_MODULE_NOT_FOUND` for `nodemailer`/`imapflow` because node resolves `node_modules` upward from the script's directory.** `docker cp` the probe to `/app` and run it with `docker exec -w /app <container> node /app/x.mjs </dev/null`. The `</dev/null` is the separate, already-documented hazard (a `docker exec -i` with unredirected stdin swallows the rest of the enclosing heredoc); both bite in the same command.

**Never measure "do we hold a credential for this mailbox" from `seed_placement_dispatches` — that table's population is gated on the TESTABLE POOL (`in_recovery` + `in_production`), so a `deactivated_by_instantly` account is absent from it whether or not we hold its password.** Reading it as a credential inventory reports every disabled account as uncredentialed, which is exactly backwards for the one question worth asking about a disabled account (can we rescue it onto our own pipe?). Measured 2026-09-02: that join said 0 of 29 disabled accounts were credentialed; the `mailbox-credentials` key itself already held 9 of them. The authoritative read is the credential SOURCES — the manual `mailbox-credentials` platform key plus the Primeforge `/public/mailboxes` pagination, i.e. what `loadCredentialedMailboxes` actually reads. Same family as the global "an aggregate is not a mechanism" rule: a derived table inherits its own selection gate, so it can only answer questions inside that gate.

**Probing `api.instantly.ai` directly from a laptop — you MUST send a `User-Agent` header or every request 403s.** A Python `urllib` / bare-`fetch` probe with only `Authorization: Bearer <key>` gets `HTTP 403 Forbidden` on EVERY endpoint (list AND single-account), which reads exactly like a bad/wrong-workspace API key and sends you hunting for the right key. It is not auth — Instantly's edge rejects the default `Python-urllib/3.x` UA. Adding `User-Agent: Mozilla/5.0` (any browser-ish string) makes the same key work first try. The in-service client is unaffected (Node's `fetch` sends its own UA). Also URL-encode the email in `/accounts/{email}` (`urllib.parse.quote(e, safe='')`). Platform key: `GET /keys/platform/instantly/decrypt` on key-service (org-agnostic, works through the api-registry `call_api`). Cost 2026-07-28: 2 wasted probe rounds diagnosing a 403 as a key problem.
- **Skip terminal rows:** when deletion is enabled, `reconcileAll` filters out rows already locally terminal (`isLocallyTerminal` → status paused/completed) so a deleted contact is never re-polled — kills the nightly log noise. When disabled, every row is scanned (unchanged).
- **Kill-switch, default OFF:** gated by env `DELETE_FINISHED_CONTACTS_ENABLED` (`isDeleteFinishedEnabled` — exactly `"true"`, anything else incl. unset = OFF). Merge is safe with the var absent (reconcile stays read-only); enable after staging soak. Mirrors the `RETRY_STUCK_WORKER_ENABLED` convention.
- **Fail-loud, 404-tolerant:** a `DELETE /leads` 404 (lead already gone) is tolerated (`isLeadAlreadyGone`) — idempotent. Any other Instantly error propagates → the per-campaign wrapper counts it `failed` and retries next run. No cost/runs declaration (deleteLeads spends nothing).

**⚠️ LIVE IN PROD — `DELETE_FINISHED_CONTACTS_ENABLED=true` (production + staging, 2026-06-13, v0.42.0).** The recurring delete is ARMED. Operational consequence of locked **option A (no pause grace period)**: the instant a campaign is paused — including a **manual pause to edit-then-resume**, or an Instantly auto-pause (bounce/quota) — its contact is **deleted on Instantly at the next reconcile** (daily 03:00 UTC cron), irreversibly. Only pause when you mean "done". To disarm, set `DELETE_FINISHED_CONTACTS_ENABLED=false` in `/root/distribute/env/instantly-service.env` on the box; the deploy cron picks the change up on its next cycle (it is a runtime env var, so no rebuild is needed).

- **`sentYesterday`** (#440) — SAME query/provenance as `sentToday` (`fetchSentYesterdayByAccount`), window bounded to the full previous UTC day `[date_trunc('day',now)-1d, date_trunc('day',now))` so it excludes both today and older days. Honest `0` when the account sent nothing yesterday. When adding another day-window sent-count, mirror this exact bounded form — do NOT reuse the open-ended `>= today-midnight` shape of `sentToday`.
- **`warmupLimit`** (#440) — the account's daily WARMUP send volume (`account.warmup.limit`), read DIRECTLY off the account object, DISTINCT from `dailyLimit` (the max-send cap; e.g. warmup 10/day vs cap 50/day). **`GET /accounts` (LIST) DOES carry a `warmup` object per item — but ABBREVIATED to `{ limit }` only; the full `{ limit, increment, advanced }` appears solely on single-account `GET /accounts/{email}`** (why `setWarmupDailyLimit` GETs the single account before a warmup PATCH — to preserve increment/advanced). So `warmupLimit` needs no extra IO (it's on the list row), but do NOT read `warmup.increment`/`warmup.advanced` off the list — they are not there. `null` when Instantly reports no warmup config.
- **`queuedFirstUnsentSequences`** — never-contacted leads on the account, i.e. how many FIRST emails are actually due. This is the quantity SEND SELECTION counts toward today's load; the sibling `queuedFirstUnsent` counts every remaining STEP of those same sequences and so over-states "today" by the whole future sequence. **An ops "queued today" figure MUST be `queuedFirstUnsentSequences + queuedNextToday` compared against `dailyLimit`** — that is the number the selector decides on. Rendering the step total instead makes a healthy account read as saturated (102 against a 45 cap) while the selector, seeing ~32, correctly keeps assigning it leads — two surfaces contradicting each other about the same account. Both fields stay exposed (the step total is still the right input to the step-partition invariant).
- **`queueSize`** — queued-but-not-sent step count per account (`fetchQueueSizeByAccount`): still-`provisioned` `sequence_costs` holds on active campaigns (reuses the EXACT `loadPendingLeads` gate — active + `delivery_status IN ('contacted','sent')`), collapsed to distinct un-sent steps, then attributed to the campaign's sending account via `COALESCE(persisted account_email, observed email_sent account)` (1 campaign = 1 lead = 1 account). The account is persisted on the campaign row at send time (migration `0025`), so a campaign pushed but **not yet sending IS attributed** from the `contacted` moment — the former "no observed account until first send" gap is closed. Only a historical row (NULL `account_email`) that also never emitted a real `email_sent` is unattributable → excluded, never fabricated.
- **`accountType`** — Instantly `provider_code` via `mapProviderCode` (**1→`imap`, 2→`google`, 3/4→`microsoft`**, else `null`). ⚠️ This line used to state the mapping INVERTED (`1→google, 2→microsoft`), contradicting both the code and prod: the 185 `provider_code 1` accounts are the `growthagency.*` Gandi/Mailforge IMAP relay fleet, and the 81 `provider_code 2` ones are the Google mailboxes. Still do NOT re-add a "provisioning class from the account object" path — it does not exist there. Guard: `tests/unit/account-health.test.ts` (`mapProviderCode` + injection cases) + `account-health-route.test.ts`.

**`queueSize` (pending STEPS) is PARTITIONED by a per-account queue BREAKDOWN over STEPS (#440 → #442 → step-partition, `src/lib/queue-breakdown.ts` pure + `fetchQueueBreakdownByAccount` IO).** Four `account-health` date buckets split each account's queued STEPS (every remaining un-sent email across all its queued sequences) by the projected send date of EACH step, and PARTITION `queueSize`: `queueSize === queuedFirstUnsent + queuedNextToday + queuedNextTomorrow + queuedNextLater` (the ops table's four bucket columns add up to the queued-STEPS total). A separate `queuedSequences` (a SEQUENCE / lead count, 1 Instantly campaign = 1 lead = 1 sequence) is ALSO exposed — a DIFFERENT granularity, kept side by side; only the bucket partition is per-step. **`queuedOverdue` (`breakdown.nextOverdue`) is a SUBSET COUNTER of `queuedNextToday`, NOT a fifth bucket — steps whose nominal due date is STRICTLY BEFORE today, i.e. backlog. `queuedOverdue <= queuedNextToday` always, and it must NEVER be added into the four-bucket sum (it re-counts steps already in `queuedNextToday`; doing so breaks the partition invariant).** It exists because `nextToday` merges "due today" with "owed days ago and never dispatched", and only the second half answers the operational question a saturated account raises — is Instantly draining this mailbox, or is it falling behind what we assign? A `queuedOverdue` that grows week over week is the tell. **`queueSize` on the account-health row is sourced FROM the breakdown's step total (`breakdown.steps`) so the invariant holds by construction (same provisioned-step set); the send-path `fetchQueueSizeByAccount` is unchanged.** Inputs are all LOCAL: the distinct un-sent (provisioned) steps + last-sent step/timestamp from the cost ledger (`sequence_costs`), and the FULL per-step `delay` array from the campaign's LATEST bronze sequence config (`instantly_campaigns_config_raw.payload->'sequences'->0->'steps'`). **Delay indexing (load-bearing): cost steps are 1-based, the config `steps` array is 0-based, and the gap from cost-step `k` to `k+1` = `steps[k-1].delay` — resolved via the SHARED `delayForGap(fromStep, stepDelays)` helper exported from `sending-forecast.ts` (the same per-gap resolver + `STEP_GAP_CALENDAR_DAYS` fallback the fleet forecast uses; NOT a second copy). Projecting step `s` off last-sent `k` at `lastSentAt` CHAINS the hops: `projected(s) = lastSentAt + Σ_{hop=k..s-1} delayForGap(hop, stepDelays)` — every remaining step, not just the immediate next (the pre-step-partition bug bucketed only the next step, so the four buckets summed to SEQUENCES, not steps).**
- **The projected send date is a NOMINAL-CADENCE LOWER BOUND that COMPOUNDS across steps.** Instantly exposes no per-lead scheduled-send timestamp (only PAST timestamps + a business-hours window — probed live). We project `lastSentAt + Σ chained delays`; the ACTUAL dispatch slips LATER under daily-limit saturation / throttling / pauses (observed: a nominal 3-day gap actualizes at ~7.6d during the current backlog), and a step two hops out sums two nominal gaps so its lower bound is SOFTER than the next step's (the drift compounds). So `queuedNextToday` reads as "step DUE today-or-overdue", not "will certainly send today"; later steps in a sequence carry progressively softer dates. Honest framing — do NOT relabel as an exact schedule.
- **A never-contacted sequence (no first email sent) has NO `lastSentAt` anchor — all its un-sent steps are counted under `queuedFirstUnsent` ("not started yet"), never date-projected** (anchoring on "now" would fabricate a date for a sequence Instantly hasn't started).
- **v1 modeling (deliberate):** per-campaign non-sending-day windows (`campaign_schedule.days`/timezone) are NOT modeled — projection is the raw nominal UTC date (many campaigns send 7d/wk, so a weekday-only snap would be wrong here). Missing config → each hop's delay falls back to `STEP_GAP_CALENDAR_DAYS` (via `delayForGap`) so a step is never dropped from the partition, but **bronze config covers the entire projected set in practice (verified prod 2026-07-11: 4,926/4,926 contacted queued sequences have config, 0 null hop delays → fallback never fires).** An unattributable queued step (no persisted/observed account) is excluded, never fabricated — same as `queueSize`.
- **Coherence note (cadence RESOLVED v0.57.6, PR #445 + step-partition; DAY-BUCKETING coherence resolved by dropping the forecast weekend snap):** the fleet `sending-forecast` and this per-account breakdown share ONE cadence model — both CHAIN the same real per-step bronze delays via the shared `delayForGap` resolver (same path + 0-based indexing + `STEP_GAP_CALENDAR_DAYS` per-gap fallback) — AND now share ONE day-bucketing model: `scheduleLead` computes the SAME nominal date as `projectStepDate` (`lastSentAt + Σ delayForGap`), buckets it on the raw nominal UTC day with NO weekend snap, and clamps a past-due nominal slot to asOf — which mirrors the breakdown's `projKey <= todayKey ⇒ nextToday`. TWO former forecast-only behaviors caused the weekend disagreement (chart's today/tomorrow read 0 while this breakdown's `nextToday`/`nextTomorrow` counted the step) and were BOTH removed: (1) the weekend forward-snap (pushed a weekend-due step to Monday); (2) the base-clamp (`baseDate = max(lastSentAt, asOf)` then re-add the full gap — over-shot the nominal date whenever `lastSentAt < asOf`, i.e. always, and mis-bucketed overdue steps as future instead of today). With both gone, a step this breakdown counts as due today/tomorrow lands on the SAME UTC day in the forecast series → the forecast's per-day `scheduledCount` reconciles with the fleet-aggregated `nextToday`/`nextTomorrow`. Do NOT reintroduce a weekend snap or a base-clamp. The only remaining orthogonal difference: never-contacted leads (the forecast projects them from asOf; this breakdown keeps them in `firstUnsent`) — immaterial because the forecast's pending-lead gate is `delivery_status IN ('contacted','sent')`, so its leads are always contacted. Guard: `tests/unit/queue-breakdown.test.ts` (chained-projection + steps-sum invariant) + the breakdown cases in `account-health.test.ts` / `account-sending-stats.test.ts`, and the `sending-forecast.test.ts` cadence-coherence + raw-nominal-day + weekend-AC tests.

## Account lifecycle — auto-driven per-account state (B/S/G)

The manual "rest an account" blacklist is GONE (endpoint `POST /internal/audit/account-blacklist`, `src/lib/account-blacklist.ts`, the `instantly_accounts.manually_blacklisted` columns, the `classifyAccountBlock`/`filterHealthyAccounts`/`isBlockedDomain` send-lead helpers, the `BLOCKED_DOMAINS` constant, and the old `AccountBlockReason` enum all deleted). Pure derivation in `src/lib/account-lifecycle.ts` (`deriveLifecycle`, unit-tested `tests/unit/account-lifecycle.test.ts`); IO glue in `src/lib/account-lifecycle-sync.ts` (`reconcileLifecycle`, unit-tested `tests/unit/account-lifecycle-reconcile.test.ts`).

**The 4 states — `deriveLifecycle`, FIRST MATCH WINS (do NOT reorder):**
1. `domain ∈ instantly_domain_policy` (a DB table, NOT a code constant) → **`deactivated_by_user`**. Warmup 30/day, NO new sends, NEVER auto-promoted. The table is SEEDED with EXACTLY the 3 brand/product domains: `distribute.you`, `growthagency.dev`, `arcadiaquest.org` (pulled from cold so cold-email reputation never touches them). The legacy shared-IP fleet is NOT in this table — it falls to `in_recovery` automatically via delivery below the 90% pooled bar.
2. `instantlyStatus <= 0` **[instantly transport only]** → **`deactivated_by_instantly`**. NO new sends; warmup NOT touched (Instantly disabled the account — we don't fight it).
3. `healthScore < 90` **AND the account is not ALREADY `in_production`** **[instantly transport only]** → **`in_recovery`** (reason `health_below_bar`). Warmup 30/day + campaign `daily_limit` capped to **20** (total 50/day), NO new sends beyond that drain. See the ASYMMETRY note below — health gates ENTRY, never continued membership.
4. delivery below the 90% pooled bar (INCLUDING never-placement-tested), **or its evidence older than 16 days** → **`in_recovery`** (reason `delivery_below_bar` / `delivery_evidence_stale`). Same 20/30 targets. This is the ONLY demotion path out of `in_production`.
5. otherwise → **`in_production`** (reason `passed`). Warmup **0/day**, campaign `daily_limit` opened to **50** (total 50/day), new sends ALLOWED.

- **⚠️ RULES 2 AND 3 ARE INSTANTLY-OWNED SIGNALS AND ARE SKIPPED WHEN `instantly_accounts.send_transport = 'smtp'` — `deriveLifecycle` therefore takes `sendTransport` and is NOT a pure function of the scores alone (second such input, after `currentStatus`).** Neither is a fact about a mailbox WE dispatch: rule 2 is Instantly's decision not to send, and rule 3 is its rolling 7-day measure of ITS warmup pool, which a self-send mailbox does not participate in (so the score is structurally 0). Inheriting them would make every self-send account permanently ineligible for the pool it exists to feed — exactly backwards, since the point of owning the pipe is that the vendor's verdict stops binding. **Rules 1 and 4 are NOT skipped, and that asymmetry is the entire safety story: the domain policy protects a brand's reputation whichever pipe carries the mail, and DELIVERY is the only input that is MEASURED rather than asserted** — whether real mail from this mailbox reaches an inbox is equally true on either transport. So a dead mailbox moved onto `smtp` still lands `in_recovery` and still sends nothing; it has merely stopped being excluded for a reason that no longer applies, and now has to earn its place on the measurement. Do NOT "simplify" the branch away, and do NOT extend it to rule 4. Guard: the "two Instantly-owned gates are skipped on smtp" tests in `tests/unit/account-lifecycle.test.ts` + the smtp cases in `account-lifecycle-reconcile.test.ts` (which assert the below-bar mailbox still lands `in_recovery`, and that a non-exact value like `"SMTP "` resolves to `instantly`).
- **Consequence — an `smtp` account gets NO Instantly-side PATCH at all: `warmupDailyForStatus` / `dailyLimitForStatus` take the transport and return `null`, and `selectLifecycleLimitPatches` skips the account wholesale (`isInstantlyEnforced`), slow ramp included.** Not merely pointless — actively harmful: Instantly does not dispatch this mailbox (our own worker owns the cap via `rampCapForAge` / `IN_PRODUCTION_DAILY_LIMIT`), the mailbox is frequently one Instantly DISABLED, and `reconcileLifecycle` PATCHes BEFORE it persists and skips the persist on error — so a doomed PATCH would block the lifecycle flip from ever landing. `enable_slow_ramp` is skipped for the same reason: it is an Instantly campaign setting with no effect on a sequence Instantly never sends.
- **⚠️ DO NOT gate `fetchTestablePoolEmails` on `instantly_status > 0`. Added in #621 and reverted the next day (#622) — the weekly Instantly placement test is the ONLY deliverability measurement a disabled mailbox gets, so excluding it strands that mailbox at a frozen score forever.** The premise ("a disabled account cannot dispatch its seeds") is not supported by prod: all 13 disabled accounts carry a recent test with **`missing_count = 0`** — every seed was delivered somewhere, so the mail went out, and one was measured while sitting at `status -3`. In practice these accounts also FLAP (the hourly `reactivate-accounts` resumes them, Instantly disables them again within the hour), so at test-selection time they are routinely back in a sendable state; that churn is ugly but it is what keeps them measurable. The asymmetry that settles it: a wasted seed costs a slice of a FLAT monthly subscription, while an unmeasurable mailbox can never leave `in_recovery`. **Corollary: there is NO need for an in-house placement harness to measure self-send mailboxes — the Saturday Instantly test still reaches them.** The 16-day `delivery_evidence_stale` expiry therefore stays a live, refreshable gate on the `smtp` transport too; do NOT freeze or exempt it.

**Every state's total daily send (campaign `daily_limit` + `warmup.limit`) is pinned to 50** — under Gmail's per-user daily sending limit. Running at 60/day tripped `550-5.4.5 Daily user sending limit exceeded` fleet-wide (2026-07-19); the pairing (in_production 50+0, in_recovery 20+30, deactivated_by_user 30 warmup) keeps every account ≤ 50.

- **⚠️ THE HEALTH BAR IS ASYMMETRIC — it gates ENTRY into `in_production`, never CONTINUED MEMBERSHIP (2026-08-12). `deriveLifecycle` therefore takes `currentStatus` and is NOT a pure function of the scores alone. Do NOT "simplify" it back to a symmetric bar — that breaks the whole fleet within a week.** An account already `in_production` is never demoted for a low warmup score; only delivery can put it back. This is what makes `IN_PRODUCTION_WARMUP_DAILY = 0` possible: Instantly computes `stat_warmup_score` over a **rolling 7-day window of warmup activity**, so an account that stops warming has its score **RESET TO 0**, not frozen at its last value ([help.instantly.ai](https://help.instantly.ai/en/articles/13939939-warmup-health-score); verified in prod — `kevin@growthagency.cloud` went 100 → 44 → 0 in 48h with `warmup_status: 1` still set, because its sends were failing). Under a symmetric bar every production account would demote itself every 7 days, permanently. The trade is deliberate: the warmup score is a PROXY (does the warmup pool see us?), the weekly placement test is the REAL measurement (does Gmail see us?), and the test does NOT depend on warmup — it sends its own seeds from the mailbox, so a production account keeps being graded weekly on the signal that matters. Guard: the "health is an ENTRY bar" tests in `tests/unit/account-lifecycle.test.ts`.
- **Delivery evidence EXPIRES after `DELIVERY_EVIDENCE_MAX_AGE_DAYS` = 16 (reason `delivery_evidence_stale`).** Since delivery is the sole demotion path, a passing-but-ancient result would otherwise pin an account in production forever if the placement cron silently stopped producing (it has — the `run`/`sync` chaining bug left results up to 7 days stale). **Do NOT tighten this to 7 days:** tests run exactly 7 days apart AND ingestion lags the run by 40 min to 3 days (the test takes hours; `sync` is daily), so the freshest evidence legitimately reaches **~10 days** old just before a new cycle lands — a 7-day cap would demote the whole fleet every Sunday morning. 16 = two consecutive missed Saturdays. `fetchLatestDeliveryByAccount` carries `testedAt` for this; `reconcileLifecycle(apiKey, asOf?)` takes an optional clock so the tests are deterministic.
- **Both bars are 90 (`PRODUCTION_HEALTH_BAR` / `PRODUCTION_DELIVERY_PCT_BAR`), and delivery is POOLED across ESPs — `Σinbox / Σseeds`, one score per test.** Both were 100 until 2026-07-28, then 95, then **90 (2026-08-12)**. The 95 → 90 move was a **QUANTIZATION** fix, not a loosening: a test seeds ~38-40 mailboxes, so the achievable pooled scores bracketing 95 are 36/38 = 94.7 and 37/38 = 97.4 — **nothing exists between 94.9 and 97.4**. A "95" bar therefore meant "at most ONE seed in spam", and 7 accounts sat blocked at 94.7-94.9 (2 spam seeds) while 4 accounts already IN production sat at exactly 95.0. **⚠️ Pooling blends a strong Outlook leg into a weaker Gmail one, so the bar and the pooled form are a PAIR — re-measure before moving either.** Measured against the live fleet 2026-08-12 at the 90 bar: **37 accounts qualify** (28 under 95); the **worst GMAIL leg admitted is 88.9%** (vs 92.3% under 95); the ~187 shared-IP Gmail-spam accounts the gate exists to catch stay excluded — the best of them pools to **89.7%**. Residuals, both accepted: the margin under the bar is thin (89.7 vs 90), so test noise will oscillate accounts across it week to week; and a seed split skewed toward Outlook (max observed share **83%**) could in theory pass a bad Gmail leg — no account admitted today has one (all are 29-40% Outlook). Do NOT lower `PRODUCTION_DELIVERY_PCT_BAR` further without re-running that Gmail-leg distribution.
- **`healthScore`** = Instantly `stat_warmup_score`, entry gate is `>= 90`. **Delivery** (`isDeliveryAtBar`) sums `inbox_count` and `seed_total` over ALL `(account, ESP)` silver rows of the account's LATEST placement test and requires `Σinbox * 100 >= Σseeds * 90`. There is NO per-leg gating and NO seed floor — `MIN_GATED_ESP_SEEDS` / `isGatedEspRow` are deleted. `fetchLatestDeliveryByAccount` still returns one row per (account, ESP) (silver keeps the per-ESP grain — it is the raw data, and it is what surfaced the Gmail-spam-vs-Outlook-fine finding) and the pooling happens in JS. Delivery unknown (never tested) → `deliveryAtBar: null` → treated as below bar → an untested account DEFAULTS to `in_recovery` (it must earn a >= 90% pooled test to promote). Do NOT fabricate a delivery number for an untested account.
- **`lifecycle_reason` in silver is REFRESHED even when the status does NOT flip.** Reconcile writes the event + Instantly PATCH only on a transition, but it previously wrote the REASON only there too — so an account that entered `in_recovery` on `health_below_bar` and later recovered its health (still held back by delivery) kept displaying `health_below_bar` next to a health of 100, a self-contradictory ops row (observed on `kevinlourd@clawdhost.tech`, frozen since 2026-07-22). A status-unchanged run now updates `lifecycle_reason` alone (counted as `reasonsRefreshed`), writes NO lifecycle event, makes NO Instantly PATCH, and deliberately does NOT touch `lifecycle_updated_at` (`reactivate-accounts` reads it as the "deactivated ≥ 24h" proxy). A stored `reactivated` is legitimately overwritten by the derived reason — silver answers "why is it in this state NOW", the event table keeps "how it got here".
- **Instantly PATCH on a state FLIP:** WARMUP (via `setWarmupDailyLimit`) — into `in_production` → warmup daily **0**; into `in_recovery` / `deactivated_by_user` → **30**; into `deactivated_by_instantly` → do NOT PATCH. `setWarmupDailyLimit` (prod-verified shape) GETs the account, merges `warmup.limit`, and PATCHes `{ warmup: {...current, limit} }` WITHOUT `daily_limit` (preserves `increment`/`advanced`). Do NOT send `daily_limit` in the warmup PATCH. CAMPAIGN `daily_limit` (max send, via `setDailyLimit` → `PATCH {daily_limit}`) — set to **50 on a flip into `in_production`** and **20 into `in_recovery`** (`dailyLimitForStatus`, `IN_PRODUCTION_DAILY_LIMIT` / `RECOVERY_DAILY_LIMIT`), pairing with warmup for a 50/day total; `deactivated_*` states leave `daily_limit` untouched so an off account keeps draining its already-queued sequence at its current cap. Ordering is load-bearing (warmup + daily-limit PATCH BEFORE persisting the event/silver — a PATCH failure aborts, next run retries); summary counts `warmupPatched` + `dailyLimitPatched`. **⚠️ reconcile PATCHes warmup + `daily_limit` ONLY on a state FLIP (`if (status === currentStatus) continue`) — it NEVER re-asserts the target while the status is UNCHANGED. Two prod symptoms of this ONE gap (2026-07-21): (a) `in_recovery` accounts that sat in recovery since before the targets became 20/30 never re-flipped → stuck at old 45/5 or 45/50; (b) `magnolia@saviolabsco.com` was correctly flip-PATCHed 45/5 into `in_production`, but Instantly RESET it to 50/10 on its own 550-throttle reactivation and reconcile never re-imposed → drifted back to 50/10. Both fixed by `POST /internal/audit/lifecycle-limits-sync` (`src/lib/sync-lifecycle-limits.ts`): idempotent ENFORCEMENT, every run, of BOTH warmup AND `daily_limit` to the target for each account's CURRENT lifecycle state (in_production 50/0, in_recovery 20/30) — reads the LIVE `listAccounts` (for the actual values: `daily_limit` + abbreviated `warmup.limit`) + silver lifecycle STATUS (`fetchLifecycleByEmail`), PATCHes only drifting fields (`selectLifecycleLimitPatches`), warmup-before-daily, fail-loud per account, optional `{limit}`, 202 + background, log `lifecycle-limits-sync: done`. `deactivated_*` states are LEFT UNTOUCHED (targets null). It SUPERSEDES `daily-limit-sync` (which covered only `daily_limit` for `in_production`; kept for back-compat but no longer wired). Wired as step 2 of the HOURLY `lifecycle-cron.yml` (alongside `accounts-sync` step 1 + `reactivate-accounts` step 3) — hourly so an account whose limits Instantly resets on its own reactivation is re-imposed within the hour, not the day. Do NOT move enforcement back into the reconcile flip logic (reconcile reads silver, which has no `warmup.limit` column — the sweep reads live).**
  - **The `daily_limit` target is additionally capped by the AGE ramp: `min(dailyLimitForStatus(status), rampCapForAge(timestamp_created, IN_PRODUCTION_DAILY_LIMIT, asOf))`.** The lifecycle STATE sets the policy ceiling (50 / 20), the account's AGE sets the physical one — a fresh Google mailbox's real Gmail per-user quota is far below 50 for its first ~4 weeks (the `550-5.4.5` trigger), independent of inbox placement. Whichever binds first wins: a 14-day-old `in_production` account targets **25**, a 1-day-old `in_recovery` one targets **5** (the ramp floor, under the 20). This is the Instantly-side twin of the send-selection cap — selection decides how many leads we ASSIGN, this decides how many Instantly will DISPATCH, so a fresh account stays protected even against followups from sequences queued before it was ramped. **Computed off the CONSTANT `IN_PRODUCTION_DAILY_LIMIT`, never off `account.daily_limit`** — reading the live value would re-scale the sweep's own previous output every hour (50 → 25 → 13 → 7 …). Guard: the fresh-cap / no-re-scale / in_recovery-floor tests in `tests/unit/sync-lifecycle-limits.test.ts`. `syncLifecycleLimits(apiKey, limit?, asOf?)` takes an optional clock so those age-driven targets are deterministic in tests.
- **Campaign slow ramp is NO LONGER force-disabled fleet-wide — the enforcement was REMOVED 2026-07-22.** The former invariant was `enable_slow_ramp == false` on EVERY account (all lifecycle statuses), enforced by the `slow-ramp-sync` sweep wired as step 3 of the daily reconcile cron. **It was removed because forcing slow ramp off pushed full daily volume onto NEW / low-trust Google mailboxes on day one → Gmail `550-5.4.5 Daily user sending limit exceeded`.** A fresh Workspace account's REAL per-user Gmail send quota is far below the 50/day fleet cap during its first ~2-4 weeks, INDEPENDENT of inbox placement — this is the send-side twin of "Health 100 ≠ Gmail-ready": the lifecycle promotes to `in_production` (50/0) on delivery-at-bar (>= 90% inbox pooled, a placement/inbox test) but that says nothing about Google's SENDING trust, so a 12-day-old account promoted to the full daily cap trips the 550 at low volume (observed 2026-07-22: ~29 accounts in `status -3` on the 550, incl. fresh `*distribute.com` Google + aged Gandi). Slow ramp is now **AGE-DRIVEN** — the replacement for the removed fleet force-off. `slowRampForAge(timestamp_created, asOf)` (`account-lifecycle.ts`): fresh (created < `MATURE_AGE_DAYS`=28) → `true` (ramp gently), mature → `false` (full volume), undatable → `null` (leave untouched until the timestamp backfills). **The enforcement home is the HOURLY `lifecycle-limits-sync` sweep** (`selectLifecycleLimitPatches` now also emits an `enable_slow_ramp` drift patch, state-INDEPENDENT — every account, every lifecycle status), NOT the reconcile flip: an account crossing the 4-week line does NOT flip lifecycle state, so only a per-run age check turns its ramp off. `src/lib/sync-slow-ramp.ts` + the `POST /internal/audit/slow-ramp-sync` endpoint REMAIN (manual-only, to force a specific batch off) but are **not wired to any cron.** `reconcileLifecycle`'s flip PATCH still does NOT touch slow ramp. **DFY-order runbook sets `enable_slow_ramp:true`** (line ~194) so fresh DFY orders arrive ramping. A one-time remediation set the ~29 throttled (`status -3`) + ~59 fresh (<4wk) accounts to `enable_slow_ramp:true` (2026-07-22).
- **AGE-GATE (Issue #511) — SHIPPED, TWO parts, both keyed on `MATURE_AGE_DAYS`=28 via `timestamp_created` (silver migration `0029`):** (1) **send selection** scales a fresh account's daily assignment CAP down with its age (`rampCapForAge`), and ranks every account on `load ÷ cap` — so a fresh account always gets a proportional share, bounded by what a young Gmail mailbox will accept (see [Account selection](#account-selection--lifecycle-gated-read-from-silver)). **The original #513 form of this — a mature-before-fresh TIER ORDER, fresh as overflow-only — was REPLACED because its fresh branch was unreachable and starved 25 mailboxes for weeks; do NOT restore it.** (2) **slow ramp** age-driven above. A fresh account stays `in_production` (NOT demoted to in_recovery — deliberately: it should still send, just at a ramped volume); the day-one full-cap risk is removed by the CAP + ramp, not by a lifecycle state change. `deriveLifecycle` takes no age input and has no `too_fresh` state — a fresh account is bounded by the CAP, not by its lifecycle state.

The next accounts-sync sees `status > 0` and reconcile re-derives the lifecycle.

Do NOT re-add the health/delivery gate here, and do NOT "fix" the deadlock by adding `deactivated_by_instantly` to the testable pool (a deactivated account cannot send the seed mail — it would burn Growth-sub quota on dead senders).

An account with no `timestamp_created` (not yet backfilled) counts as old enough. Guard: `tests/unit/testable-pool.test.ts`. **Bootstrap-deadlock rationale (load-bearing):** an `in_recovery` account MUST be testable to EARN the delivery-at-bar (>= 95%) that promotes it to `in_production`; seeding from `in_production` only would deadlock (untested accounts default to `in_recovery` and would never get a test). Google+Outlook recipients. **WEEKLY FULL-POOL ON SUNDAY (load-bearing):** a placement test sends ~30-50 seeds/account, and a mailbox's safe daily volume is ~50 (already used by 40 send + 10 warmup — MailReach 2026), so it CANNOT run on top of a normal sending day. Instead the WHOLE testable pool is tested ONCE PER WEEK, on **Saturday** — a send-free day: the campaign send window is **Mon-Fri** (`instantly-client.ts`, Saturday `"6": false` + Sunday `"0": false`) and warmup is weekday-only, so on Saturday each mailbox is otherwise empty and absorbs the seed spike safely; if the spike overflows the per-account daily send cap, the overflow finishes on **Sunday** (also send-free). `runOneTimeFleetPlacementTest` seeds `emails` from the FULL `fetchTestablePoolEmails()` result — **NO per-account rotation, NO cursor/bucket state** (the former `selectDailyTestBatch` 1/7 daily rotation + its `fetchLastPlacementTestByAccount` last-tested read were REMOVED when the cadence moved off "daily 1/7" onto "weekly full-pool"; do NOT reintroduce them). Cron is **`0 6 * * 6`** (Saturdays 06:00 UTC). Empty pool → `created:0`, no Instantly call (no fabricated result). Gated behind `PLACEMENT_TESTS_ENABLED=true` (409 when off). Recurrence comes from OUR cron, NOT Instantly's server-side scheduler. **If the Growth Inbox Placement sub can't absorb one full-pool test/week, the lever is to widen the interval or shrink the pool — NOT to reintroduce daily rotation (that spikes seeds on live sending days).**
- `POST /internal/audit/placement-test/ensure` — the **type-2 (automated, server-side-scheduled)** variant. ⚠️ **Automated tests require an Instantly HyperGrowth plan** — on the Growth sub this **402s** (`Automated tests are only available for HyperGrowth plans`). Kept for if we ever upgrade; the LIVE path is `/run` (type-1). Same gate/prefix.
- `POST /internal/audit/placement-test/sync` — polls tests + analytics → bronze → silver. Read-only (no quota), 202 + background (`placement-sync: done`).

Type-2 also needs `schedule` = `{ days: OBJECT `{"0"..."6":bool}` (NOT array), timing:{from,to} (both), timezone: fixed enum — `America/Chicago` accepted, `Etc/UTC` rejected }`. **To rediscover/extend the body, PROBE the live API directly** — one throwaway `fetch` against `api.instantly.ai` with the platform key (resolvable from key-service with `x-api-key` + `X-Caller-Service/Method/Path` headers, or read straight out of the env file on the box) — rather than N prod hotfixes: one probe run beats one deploy-cycle-per-field, because each missing field is a separate 400 and you only learn the next one after fixing the last. Send a browser-ish `User-Agent` (see the 403 note below).
- **`placement-prime-cron.yml` runs 30 min BEFORE the Saturday test (`30 5 * * 6`) and exists to widen the pool that test seeds.** It POSTs `reactivate-accounts`, waits, then `accounts-sync` — in THAT order, because the sync is what carries the resumed status into silver and runs `reconcileLifecycle`, which is what actually moves a mailbox to `in_recovery` and therefore INTO `fetchTestablePoolEmails`. Reversed, it primes nothing. **It is a SEPARATE schedule, not two more steps in `placement-cron.yml`** — both endpoints answer 202 and work in the background, so chaining them just before `run` would race the pool read against the writes it depends on (the same create-then-read-in-one-run trap that decoupled `sync` from `run`). Why it matters: a large part of the fleet FLAPS (hourly `reactivate-accounts` resumes it, Instantly disables it again), so whether a mailbox is measured at all came down to which side of that cycle it sat on at 06:00 — and a mailbox that keeps missing the test sits on a frozen score, ages past the 16-day evidence limit, and is pinned in `in_recovery` for good, not because it delivers badly but because nobody looked. Over-seeding is the cheap direction: seeds come out of a FLAT subscription and every sender seeded so far produced results (198/198 and 36/36 on the two largest tests). Spends no Instantly quota (a resume plus a read); a 409 from an unarmed `REACTIVATE_ACCOUNTS_ENABLED` is tolerated.
- **Recurring driver = `.github/workflows/placement-cron.yml`** (mirrors `reconcile-cron.yml`), on TWO schedules. **⚠️ `sync` is DECOUPLED from `run` and fires DAILY — do NOT re-chain it after `run` (load-bearing, fixed 2026-07-28).** An Instantly placement test takes HOURS to finish; when `sync` ran as the next step of the same weekly job it polled the test created ~4 minutes earlier (`status:1`, zero analytics rows) and therefore NEVER ingested it, so results only reached silver at the NEXT week's sync. Effect: every account's `delivery` was up to **7 days stale**, and a mailbox created mid-week waited **~2 weeks** (test Saturday → results the following Saturday) before it could ever leave `in_recovery` — which is what made `kevinlourd@clawdhost.tech` look "never tested" when its test had in fact already run. Proven in prod 2026-07-25: test `019f9856` (230 senders) sat in bronze at `status:1` with 0 silver rows while the 07-19 test only landed at that same 07-25 sync. Schedules now: **`0 6 * * 6`** (Saturday) → `accounts-sync` + `run`; **`0 7 * * *`** (daily) → `sync` ALONE, bounding result latency to ≤ 24h. The weekly-only steps are gated `if: github.event.schedule != '0 7 * * *'`, a form that is TRUE for the weekly cron AND for `workflow_dispatch`, so a manual run still does the full sequence. `run` 409 is tolerated (dormant until armed); `sync` + `accounts-sync` are safe/idempotent (read-only against Instantly, no quota). **Scheduled runs fire from the DEFAULT branch (`main`) only.** Same GH secrets as reconcile-cron. **LIVE in prod: `PLACEMENT_TESTS_ENABLED=true`** (armed 2026-07-05, v0.51.5). Disarm: set `PLACEMENT_TESTS_ENABLED=false` in `/root/distribute/env/instantly-service.env` on the box (picked up on the deploy cron's next cycle).

All of it was DELETED 2026-07-29 — the weekly test already covers a new account within ≤7 days, which is the intended cadence, and the extra path carried its own suppression-window state plus a weekday seed spike. Do NOT reintroduce an immediate/hourly test path: if a new account must be covered sooner, move the weekly cron, do not add a second one.

(2) **type-2 schedule** — moot: automated (type-2) tests are HyperGrowth-gated (402), so we use type-1 one-time tests on our own weekly Saturday cron instead. **Cost:** placement runs on the FLAT Growth Inbox Placement subscription (not per-unit metered to us) → no runs-service cost declared, consistent with other flat-sub external calls. ## In-house seed placement — measuring deliverability without the paid test

The Instantly **Growth Inbox Placement** subscription ($47/mo) buys one thing: a set of receiver inboxes to send seeds to. Everything else in a placement test we already own — dispatch (`self-send/smtp.ts`), reading a Gmail folder including `[Gmail]/Spam` (`self-send/imap-poller.ts`), and the aggregation into a per-account percentage (`placement-promote.ts`). `src/lib/seed-placement/` supplies the missing piece from mailboxes we already have, at **$0/mo**.

**⚠️ IT WRITES INTO THE EXISTING SILVER, and that is the entire integration.** `instantly_placement_results` is keyed on `(test_id, account_email, recipient_esp)` where `test_id` is plain text — nothing in it is Instantly-specific. Seed rows promote into it under a **`seed:<uuid>`** test id (mirroring the `self:` / `reserving:` sentinel convention), so the lifecycle delivery gate (`fetchLatestDeliveryByAccount` → `deriveLifecycle`), account-health gold and the history series all read them with **zero code change**. Do NOT add a parallel silver table or a second gate — the whole design rests on there being one.

- **Two bronze tables, because the measurement has two independent halves** (migration `0044`): `seed_placement_dispatches` (the DENOMINATOR — a seed we sent) and `seed_placement_observations` (the NUMERATOR — a seed we found, and in which folder). **`missing` is dispatched-minus-observed.** Deriving the denominator from the observations instead would score a mailbox whose every seed vanished as `0/0` → null → **"untested"**, which is how a black hole gets promoted to a passing grade. A single results table could not represent "sent and never arrived" at all.
- **A FAILED dispatch is recorded but does NOT count.** Only `outcome = 'sent'` reaches the aggregation. A seed that never left the building says nothing about where our mail lands, and scoring an SMTP refusal as a missed inbox blames placement for a credential problem.
- **First observation wins** (unique on `(receiver_email, message_id)`). Gmail can reclassify after delivery; where the seed landed AT DELIVERY is the question being asked, so a later move must not overwrite it. This also makes a re-read a no-op — the poller is idempotent **without a cursor**, same reasoning as the self-send IMAP poller (a drifting cursor loses observations, and a lost observation is indistinguishable from a missing seed, i.e. it silently penalises a healthy mailbox).
- **⚠️ ONLY A MAILBOX ON A CONSUMER-RELEVANT ESP CAN BE A RECEIVER, and the ESP is read off the resolved IMAP HOST, never the domain name.** Every mailbox in this fleet sits on a custom domain, so the address tells you nothing: `kevin@growthagency.bio` is Gandi and `k.lourd@growdistribute.com` is Google Workspace, and they look identical. `espForReceiverHost` returns **null** for a host it cannot attribute (Gandi, the Mailforge relay) and `selectSeedReceivers` skips it. Null is NOT "assume Google" — the first version defaulted custom domains to Google and, in its very first prod run, labelled six Gandi receivers as *Gmail* placement. A placement score is a claim about a specific ESP, and claiming the wrong one is worse than declining to claim. A Gandi/relay mailbox stays a perfectly good SENDER (measuring whether ITS mail lands is exactly what the shared-IP question needs) — it just cannot grade. Zero gradeable receivers ⇒ the run logs and stops rather than sending mail nobody can score.
- **Aliases: `authUser` is the SMTP/IMAP login when it differs from the address (`loginFor`).** A Gandi domain is ONE real mailbox plus several aliases, and Instantly holds an account per alias — measured, **175 Instantly IMAP accounts sit on 44 Gandi mailboxes**. So `klourd@pressbeat.ai` sends as itself and authenticates as `kevin@pressbeat.ai`, the only mailbox on that domain. Conflating address and login makes every alias unauthenticable; all three auth sites (`smtp.ts`, `imap-poller.ts`, seed `sync.ts`) go through `loginFor`. Absent ⇒ the address IS the login, which is the Primeforge case.
- **Receivers are picked for DOMAIN DIVERSITY, at most one mailbox per domain, capped at `MAX_SEED_RECEIVERS` (10), deterministic.** A verdict is a property of the (sender, receiving-domain) pair, so ten seeds to ten domains says more than fifty to two — and every extra receiver multiplies the volume each sender carries on test day. Deterministic ordering is what makes week-over-week scores comparable; a moving receiver set would destroy the only thing a placement history is for.
- **A mailbox never seeds itself** (`planSeedSends` excludes it). A self-send is delivered locally and crosses no filter, so counting it would inflate every sender that is also a receiver — which, under this receiver set, is most of them.
- **The seed is deliberately ORDINARY and does NOT go through `buildEmailBodyWithSignature`.** That pipeline appends the signature and the unsubscribe footer carrying `{unsubscribe_link}` — a merge variable only Instantly resolves, so it would ship unresolved — and routes links through the click redirect. A seed must measure the mailbox, not the footer: plain, link-free, no pixel, no machine-looking subject. Correlation rides on the RFC 5322 `Message-Id`, not on a body marker (one more thing a filter can score).
- **Only folders that carry a verdict are read.** `classifySeedFolder` maps INBOX and the spam folders; everything else returns null — including **`[Gmail]/All Mail`, which MIRRORS both and would double-count**.
- **Auth flags: an absent mechanism is `null`, never `false`.** "The receiver did not report on SPF" and "SPF failed" are different facts, and the silver columns are nullable precisely so the difference survives.

**Credentials — a MANUAL layer sits in front of Primeforge (`seed-placement/credentials.ts`).** `resolveMailboxCredential` (self-send) reads app passwords from Primeforge's REST API, which covers every mailbox the self-send transport dispatches. The seed harness measures the whole testable pool, which contains mailboxes on vendors whose API does **not** hand back an existing mailbox's password — Gandi and Mailforge both. The live case is **`klourd@pressbeat.ai`**: `in_production`, head of the sending fill order, and unmeasurable without this. So a `mailbox-credentials` **platform key in key-service** holds a JSON array of hand-entered credentials (`address`, `appPassword`, `smtpHost`, `imapHost` — hosts in the payload, because the point of the layer is that these are not on Google), consulted BEFORE Primeforge. **A missing key is a legitimate state, not an error: only a key-service 404 yields "none configured"; a 401/5xx/malformed payload throws** — those mean we could not READ the credentials, which is a different thing from there being none.

**⚠️ THE POOL IS NARROWED TO WHAT WE CAN AUTHENTICATE, BEFORE PLANNING — and `loadSeedCredentialResolver` loads every source ONCE.** `fetchTestablePoolEmails` returns the whole fleet (~200 accounts: `in_recovery` + `in_production`), but credentials exist only for Primeforge plus the manual key. `resolveMailboxCredential` re-reads the key AND re-paginates the vendor's entire mailbox list on every call, and THROWS for a mailbox that vendor does not host — so resolving per-seed against a ~200-account pool fanning out to 10 receivers would mean thousands of vendor paginations per run and ~1,900 meaningless failure rows, almost all of them for mailboxes that were never going to resolve. Two reads up front, then pure lookups; an unresolvable mailbox is **skipped** (counted as `skippedNoCredential`), which is a normal expected outcome and not an error. Receivers are then drawn from the SENDABLE set, because a receiver must be read over IMAP with the same credential — a mailbox we cannot authenticate is no more readable than it is sendable. Effective volume is therefore ~25 senders × 10 receivers ≈ 250 seeds, not 2,120.

**Cadence — `seed-placement-cron.yml`, BOTH steps DAILY, and the run step decides for itself whether a test is due (`decideSeedTestDue`, `seed-placement/due.ts`).**

**⚠️ THE CADENCE LIVES IN THE DATA, NOT IN THE SCHEDULER — do NOT "simplify" this back to a weekly cron.** GitHub Actions silently delays and skips scheduled workflows under load: on 2026-08-29 the 06:00 Saturday placement job never fired at all and the 05:30 prime job ran at 11:45. So a weekly cron does not mean weekly, it means *most* weeks — and the cost of a miss here is not a late report. `DELIVERY_EVIDENCE_MAX_AGE_DAYS` is 16, so TWO consecutive misses age every account into `delivery_evidence_stale` and **the whole fleet stops sending**. Calling daily and asking the data ("when did we last measure?") makes a skipped tick free, because the next day asks again.

Rules, in order: never tested ⇒ **always due** (waiting for a preferred weekday would leave an unmeasured fleet unmeasured for a week); evidence ≥ `SEED_EVIDENCE_URGENT_AGE_DAYS` (12) ⇒ **due on ANY day**, weekday spike being the lesser evil against the fleet ageing out; inside `SEED_TEST_INTERVAL_DAYS` (6) ⇒ not due; interval elapsed on a **sending day** ⇒ wait for the weekend; otherwise ⇒ due. The interval is 6 rather than 7 so a run that lands a few hours late does not silently drift the cadence to 8 days and then 9. So the send still LANDS on a weekend in the normal case, and a skipped Saturday is picked up by Sunday — both are send-free. `force: true` on the endpoint bypasses the check for a manual run; the cron never sets it.

**⚠️ Do NOT chain the read onto the send** — both endpoints answer 202 and work in the background, so a chained read races the writes it depends on. That exact shape is what made `placement-cron.yml` ingest week-old results for months. Read runs on its own daily 09:00 tick.

**Armed by `SEED_PLACEMENT_ENABLED=true`, default OFF** (409 on `/run`, tolerated by the cron). The `/sync` route is NOT gated — it is read-only and idempotent, and with the run disabled there is simply nothing pending. Reconcile runs after a sync only when `silverRows > 0`, so a no-op sync never churns the fleet's lifecycle.

**⚠️ FIDELITY CAVEAT — this bounds what the score MEANS, and it is why the paid subscription is still running.** The receivers are our own Google **Workspace** mailboxes, and Workspace inbound filtering is more permissive than consumer `gmail.com`. A mailbox can score well here and still land in a real prospect's spam. So the two tests run **in parallel** and the $47 is cancelled only once their scores agree — in particular, only once the shared-IP accounts still score badly here. If instead the harness scores everything ~100%, it discriminates nothing and is **not a gate**; the fix is then consumer seed inboxes (free to create — a few `gmail.com` / `outlook.com` / `yahoo.com` with app passwords, read over the same IMAP path, no code change beyond the receiver list), **NOT lowering `PRODUCTION_DELIVERY_PCT_BAR`**. Compare the two by `test_id` prefix; the gate itself takes whichever test is newest per account (`DISTINCT ON (account_email) ORDER BY tested_at DESC`), so during the parallel run they alternate — read them apart, do not infer agreement from the gate.

**Scope limit: only mailboxes we hold a credential for get measured — but that set is EXPANDABLE, and saying otherwise blocks the one test that validates the harness.** Out of the box it is every Primeforge mailbox plus whatever the manual key lists. The ~187 legacy Gandi/Mailforge accounts are absent because their passwords are not in any API we read — **not because they are unobtainable**: Gandi's API can SET a mailbox password (so reset one and add an array entry, exactly as `klourd@pressbeat.ai` was added), Mailforge exports the whole fleet's credentials as a CSV from its UI, and Instantly itself holds them (these are `provider_code 1` IMAP imports) but does not return them on its account object — verified, there is no `imap_*` / `smtp_*` / `password` field on the Instantly account type.

⚠️ **This distinction is load-bearing for validating the harness at all.** The accounts that would PROVE it discriminates are the shared-IP ones that land in Gmail spam — so if you record them as unmeasurable, the only available comparison is Primeforge mailboxes that already pass, both tests agree "fine", and that agreement is equally consistent with a good gate and with a rubber stamp. **The cheap validation is a NEGATIVE CONTROL: load ONE known-Gmail-spam legacy mailbox into the manual key and run once.** It scores badly → the harness discriminates → the paid test can go. It scores ~100% → the Workspace receivers are too permissive → keep paying and switch to consumer seed inboxes.

An account that genuinely stays unmeasured ages into `delivery_evidence_stale` within `DELIVERY_EVIDENCE_MAX_AGE_DAYS` (16) and drops out of the sending pool — the correct outcome for the legacy fleet, and the reason `klourd@pressbeat.ai` (`in_production`, head of the fill order) needed its credential loaded.

## Provider infrastructure inventory — the layer UNDERNEATH the account

The fleet buys domains and mailboxes from FOUR vendors — **Gandi** (3 organisations), **Mailforge**, **Primeforge** and **Instantly DFY** — and until issue #555 only Instantly existed in code, and only at the ACCOUNT grain. There was no domain entity at all: a domain was `split_part(email,'@',2)`, and `instantly_domain_policy` is a 3-row config table, not a registry. Measured at the time: 66 domains owned, 250 live Instantly accounts across 58 of them, **8 domains paid with zero sending accounts**, and 10 ghost account rows.

`POST /internal/infra/sync` (`src/lib/infra-sync.ts`, platform-scoped, same `serviceAuth` tier as `/internal/audit`) polls all four into bronze, upserts silver, and flags rows a vendor stopped reporting. Driven by `infra-cron.yml`, daily at 05:00 UTC. Provider clients live in `src/lib/providers/` with the pure normalisers exported and unit-tested (`tests/unit/provider-clients.test.ts`).

- **`(provider, domain)` is the primary key, NOT `domain`.** A domain can legitimately be reported by two vendors at once (Gandi registers it while the mailboxes live elsewhere). Collapsing them in storage would bake a precedence guess into the table; the per-domain rollup is derived on read. Do NOT add a `primary_provider` column.
- **Rows are flagged absent, never deleted.** A domain disappearing IS the fact worth keeping — it lapsed, or it was transferred away. Same for `instantly_accounts.absent_since`, which the accounts-sync now sets for accounts Instantly no longer lists. ⚠️ The first prod run flagged **13 of 266**, and **none of them was `in_production`** — so, contrary to what the PR that shipped this said, they were NOT inflating `dailyCapacity` (which sums `in_production` only). They inflated the INVENTORY and total counts. Keep the distinction: a ghost in a non-sending state is a counting error, not a capacity error.
- **The absence sweep runs ONLY for a vendor whose fetch SUCCEEDED**, and for Gandi it is scoped to the reporting organisation. A transient vendor outage must never flag that vendor's whole estate as gone. It keys on `last_seen_at`, never a `NOT IN (…)` list — a per-domain bind list grows with the estate and eventually trips Postgres' 65,534-parameter ceiling.
- **A single vendor failing does not stop the others** (counted in `failures`, logged); the run throws only when EVERY vendor failed, so a run that ingested nothing never reads as green. An empty Instantly account list likewise throws rather than letting the sweep flag the whole fleet.
- **Spends nothing metered** — every call is an inventory read against a flat subscription, so no run/cost is declared (same reasoning as the placement tests).
- **Keys:** five NEW platform keys in key-service — `gandi-org1`, `gandi-org2`, `gandi-org3`, `mailforge`, `primeforge` (Instantly already exists). Gandi issues one token per organisation and a token sees only its own domains, hence three rows. `resolvePlatformKey(provider)` in `key-client.ts` is the generalised resolver; `resolvePlatformInstantlyApiKey` is now a wrapper over it.

**Vendor API gotchas (all probed live 2026-08-02 — the docs and the skills were wrong on two of them):**

**`GET /dfy-email-account-orders` closes the "provisioning class is not exposed" gap this file used to record as permanent.** It is not on the ACCOUNT object (`provider_code` is the connection PROTOCOL: 1=IMAP, 2=Google — note the `mapProviderCode` table quoted elsewhere in older notes had these inverted; the CODE is right), but it IS on the ORDER. A cancelled order keeps its row with `cancelledAt` set — a dead domain is still a cost.

**Cost lives HERE, and since the rebill stopped it is the ONLY place the cold-email spend is measured.** `infra_price_rates` holds what the vendor actually charges US, with `source` (`api` vs `rate-card`), currency and `effective_from` (non-retroactive: a rate change ADDS a row, never edits one). costs-service prices what we RE-BILL, and it no longer prices any of this — the per-email figure there was always a fiction (`instantly-account-email-sent` derived from "domain $20/yr ÷ 5 accounts ÷ 5,040 emails" while Gandi alone charges EUR 38.38/yr for `growthagency.dev`), which is part of why the rebill was dropped. **Cost per email is now `/internal/infra/spend` ÷ real `email_sent` events, NOT a catalog lookup** — and a per-org cost stat that shows zero Instantly spend is correct, not a regression.

**Two price sources coexist and must stay distinguishable.** A vendor-reported PER-DOMAIN price lives on `infra_domains.price_cents` (per-domain because it depends on the TLD); the rate card covers vendors with no billing API. `monthlyCostForDomain` prefers the vendor's own price, treats it as YEARLY (both Mailforge and Gandi quote a renewal), and adds `mailbox-month × the VENDOR's mailbox count` — not the Instantly account count, since we pay the vendor for what IT hosts and the two genuinely differ. **Primeforge is priced from its PUBLISHED PAGE, not its API** (every billing path 404s): migration `0034` mirrors the page into bronze (`provider_account_raw`, scope `pricing-page`) and seeds the rate from it — $14/yr per domain, **$4.50/mo per SLOT** on monthly billing. The bronze row is the point: a rate typed straight into a seed is unauditable the moment the vendor changes it. Two invariants: (a) it seeds the MONTHLY list rate, not the discounted annual one ($3.75 with 2 months free), because nothing we can reach says which billing period the subscription uses — overstating a cost is the safe direction, understating it flatters every derived cost-per-email; (b) the unit is a **slot, not a live mailbox** — Primeforge bills capacity, so a deleted mailbox keeps costing until the slot is released. If the subscription turns out to be annual, ADD a row with a new `effective_from`; never edit one. **Do NOT seed a rate for a vendor you have not sourced** — an invented rate silently becomes the fleet's cost-per-email denominator, which is worse than an empty column. A cancelled domain also prices to `null` — we stopped paying — so it is never counted as "unpriceable".

**Gold reads (all cached via `getOrSetCachedStats`, per the aggregation rule above):** `GET /internal/infra/domains` (per (provider, domain), with vendor mailboxes and Instantly accounts side by side), `/waste`, `/spend`. Three invariants worth keeping:
- **`/waste` is REPORT-ONLY** and must stay so. It never cancels an autorenew and never schedules a deletion: a false positive costs a domain, and several flagged ones are brand domains held on purpose.
- **`/spend` totals stay PER CURRENCY.** Gandi bills EUR, the rest USD; blending needs an FX rate this service does not own, and that would be one more unsourced number on a page whose whole point is provenance. Cost-per-email is therefore a FLOOR while `unpricedProviders` is non-empty — say so, do not hide it.
- **Sends are counted per DOMAIN, not per inventory row.** A domain reported by two vendors has two rows carrying the same send count; summing rows would double the denominator and halve every cost-per-email.
- **`/domains` reports the cost TWICE on purpose: blended (`monthlyCostCents`) and split by WHEN cancelling saves it (`recurringMonthlyCents` / `renewalCents` + `renewalAt`, `splitDomainCost`).** "What do I save by turning this off" has two answers: the mailbox subscription stops immediately, while the registration is already paid until its expiry and is only avoided at the NEXT renewal. One blended number makes a Gandi domain paid up until next May look as urgent as a Primeforge slot bleeding monthly — the opposite of the decision. Note `renewalCents` stays YEARLY (it is not divided by 12) while `monthlyCostCents` divides it; do not "fix" that inconsistency, they answer different questions. The admin delete list consumes the split.

**Cron consolidation (same issue):** `/internal/audit/accounts-sync` used to fire from THREE schedules — `accounts-sync-cron.yml` (every 2h), `lifecycle-cron.yml` (hourly) and `placement-cron.yml` (weekly) — ~37 runs/day of one job. `lifecycle-cron` hourly strictly supersedes the others, so `accounts-sync-cron.yml` was deleted and the placement-cron step removed. **`lifecycle-cron.yml` is now the SOLE caller** — do not re-add it elsewhere.

## Webhook ingestion — `POST /webhooks/instantly` NEVER answers non-200

**Every path in the handler returns 200. There is no 4xx and no 5xx branch, and adding one disables the webhook fleet-wide.** Instantly counts a **4xx exactly like a 5xx** toward its delivery-failure threshold, and on that threshold it DISABLES the webhook — not the single event, the whole subscription — after which we receive nothing at all until someone re-enables it. An unusable payload therefore answers `200 {success:true, degraded:true, degradedReason:"…"}` and is logged; it is never rejected.

The subscription is **`all_events`** (verified live: `GET /api/v2/webhooks`, one hook on `https://instantly.distribute.you/webhooks/instantly`), so we receive event types this service has never modelled — including **account-level events that carry no `campaign_id` at all**. Bronze keys on a non-null `instantly_campaign_id`, so such an event genuinely cannot be stored: it is logged under `missing_campaign_id` and dropped. Dropping ONE unattributable event is cheap; being disabled loses EVERY event.

Degraded reasons, all 200: `invalid_payload` (no `event_type`), `missing_campaign_id`, `unknown_campaign_id` (matches no local row nor `metadata.redispatchHistory[*].from` alias), `campaign lookup failed: …`, `bronze failed: …`, `silver failed: …`. **The campaign-lookup `db.select` is inside a try/catch** — `src/index.ts` installs no global error handler, so an uncaught throw there is an Express default **500**, i.e. a delivery failure on every request for as long as the DB is unhappy.

**⚠️ Re-enabling a disabled webhook is NOT possible via `PATCH` — `status` is server-managed.** `PATCH /api/v2/webhooks/{id}` accepts only `name` / `event_type` / `target_hook_url` and answers `400 {"message":"No valid updates provided"}` for `{status:1}`; patching the other fields returns 200 and leaves `status:-1` untouched. Read the live state with `GET /api/v2/webhooks` — `status:-1` plus a `timestamp_error` is the disabled shape.

**The recipe that works, verified 2026-08-25 (new id `01a037f9-…`, `status:1`): DELETE then POST, in that order, and DELETE must NOT carry a `Content-Type` header.** Two traps, each of which looks like something else:
- **`POST /api/v2/webhooks` UPSERTS on `target_hook_url`** — creating while the disabled hook still exists returns the EXISTING row verbatim, `status:-1` included, with a **200**. It reads as "created, still disabled" when in fact nothing was created. So the delete has to come first; there is no safer create-then-swap ordering available.
- **`DELETE /api/v2/webhooks/{id}` 400s `{"code":"FST_ERR_VALIDATION","message":"body must be null"}` when the request carries `Content-Type: application/json`** — Fastify then expects a body and rejects the bodyless request. Reusing ONE shared `{Authorization, Content-Type}` header object across every call is what causes it; send DELETE with `Authorization` + `User-Agent` only.

Capture the full config (`name`, `target_hook_url`, `event_type`, `headers`) BEFORE deleting and POST it back — `headers.Authorization` is a shared secret Instantly echoes to us on every delivery and is NOT recoverable once the row is gone. The window between delete and create costs nothing while the hook is disabled, since a disabled hook delivers nothing.

Incident 2026-08-25: disabled at **07:47:08 UTC**, last ingested event 07:45. Prior incident 2026-05-20 (a `promoteEvent` bug → 6 days of webhook silence) produced PR #228, which hardened the BODY of the handler to always-200 and left these two entry guards returning 400 — the recurrence came in through exactly that gap. Guard: the three "never 4xx / never 5xx" tests in `tests/unit/webhooks.test.ts`, and `grep -nE 'res\.status\(' src/routes/webhooks.ts` must match only the `/instantly/config` route.

## Data layering — Bronze / Silver / Gold

Three layers, doctrine per `~/.claude/skills/data-layering/SKILL.md`:

- **Bronze** — raw external mirrors, append-only, never mutated. Tables: `instantly_webhook_payloads_raw`, `instantly_analytics_raw`, `instantly_emails_raw`, `instantly_leads_raw`, `instantly_campaigns_config_raw`, plus the provider-inventory mirrors `provider_domains_raw`, `provider_mailboxes_raw`, `provider_account_raw`. Each row = one payload from Instantly (webhook OR reconcile poll) or from an infrastructure vendor.
- **Silver** — canonical event log `instantly_events` + state row `instantly_campaigns`, plus the infrastructure inventory `infra_domains` / `infra_mailboxes`. Derived from bronze via `src/lib/silver-promote.ts` and `src/lib/infra-sync.ts`. Rebuildable.
- **Gold** — stats views in `src/routes/analytics.ts`, `status.ts`. Read silver only.

### Reply-sentiment gold = CURRENT sentiment (latest event per lead), NOT raw event counts

A reply's sentiment can be **re-qualified**: a webhook auto-classifies a reply `lead_interested`, then an operator manually re-qualifies it `lead_not_interested` via `POST /orgs/manual-qualifications` (which inserts a NEW silver event + pins `instantly_campaigns.reply_classification='negative'`, source `manual`). The silver event log keeps BOTH rows — that is the correct append-only audit trail, NOT a bug. So a lead's **current** sentiment is the LATEST of the 8 mutually-exclusive sentiment events per `(campaign_id, lead_email)`, manual winning ties — NOT every sentiment event ever recorded.

Gold reply-sentiment counts (`repliesPositive/Negative/Neutral`, `repliesDetail`) MUST therefore be derived from the latest-sentiment-per-lead, NEVER from `COUNT(*) FILTER (WHERE event_type = 'lead_interested')` over raw events. The raw-count form never drops the stale positive when a reply is later re-qualified negative, so model/brand/workflow positive-reply totals stay frozen after a manual reclassification (reported 2026-06-13). The 9 reply kinds are `SENTIMENT_EVENT_TYPES` in `src/routes/analytics.ts` (mirrors `REPLY_CLASSIFICATION_MAP` in `silver-promote.ts` — see [Reply kind](#reply-kind--what-kind-of-reply-arrived-and-nothing-about-the-deal)).

- **Implementation:** `queryGroupedSentiment` / `querySentiment` (`analytics.ts`) run a `DISTINCT ON (campaign_id, lead_email) … ORDER BY timestamp DESC, (source='manual') DESC, created_at DESC, id DESC` CTE, then count by the winning type. `queryGroupedStats` + `queryStats` merge this into `repliesDetail`. Both routers (`analytics.ts`, `analytics-public.ts`) reuse these, so the fix covers model + brand + aggregate on both. `unsubscribe` stays an event count (separate signal, not a reclassifiable sentiment).
- **Pure gold fix — silver/bronze untouched.** The event log faithfully keeps the full reclassification history; only the gold *projection* reads the latest. Do NOT "fix" this by deleting/mutating silver rows on reclassification.
- **Per-step sentiment = current sentiment on the LAST step.** A reply is ONE outcome per lead for the whole sequence, not a per-step event. `queryStepSentiment` (`analytics.ts`) attributes each lead's CURRENT sentiment EXACTLY ONCE, to its **last reached step** = `MAX(step)` of the lead's `email_sent` events. So a reply re-qualified negative shows up only as negative on the last step — NEVER as a stale positive on the step where the original auto `lead_interested` event fired. Step-level *email* metrics (sent/opened/clicked/bounced/unsubscribe) stay genuinely per-step; only the reply *sentiment* is collapsed to the last step. Both routers' `stepStats` blocks use this. (Sequence stops on reply, so last sent step ≈ the auto reply step; for a manual negative Instantly never saw, it is simply the last step reached.)
- Guards: the latest-sentiment SQL-shape + re-qualified-reply unit tests in `tests/unit/stats.test.ts` / `stats-public.test.ts`, and the DB-backed `tests/integration/sentiment-reclassify.test.ts` (interested → manual not_interested ⇒ positive 0 / negative 1).

### `groupBy=day` timezone — bind the PRIMARY IANA name, never the caller's spelling

`localDayKey` buckets with `TO_CHAR(... AT TIME ZONE $tz, 'YYYY-MM-DD')`, so the zone name is resolved **by Postgres against the tzdata installed on the DB host** — not by Node. Debian splits the tz database: the base `tzdata` package carries the primary names, and **`tzdata-legacy` carries the backward-compat links** (`Asia/Saigon`, `Asia/Calcutta`, `Europe/Kiev`, `America/Buenos_Aires`, `Asia/Rangoon`, `Asia/Katmandu`, `US/Pacific`, `Japan`, `Poland`, `Israel`, `Egypt`, `Turkey`, `Cuba`, `Iran`, `Singapore`, `PRC`, `NZ`, `Eire`, `GB`, `Hongkong`, `Asia/Macao`, `Asia/Dacca`, `America/Godthab`, `Asia/Ulan_Bator`). On a host without it, `AT TIME ZONE '<link>'` throws `time zone "X" not recognized` (SQLSTATE 22023) while the SAME zone's modern spelling works.

**Every accepted spelling is therefore canonicalized to its primary name before it reaches SQL** — `canonicalIanaTimezone` (`src/lib/timezone.ts`), applied in `localDayKey` AND at both `/stats` handlers (so the stats cache key collapses aliases too: same zone ⇒ same buckets ⇒ one entry). `Intl` ALONE IS NOT ENOUGH — ECMA-402 deliberately leaves recently-renamed zones uncanonicalized (`Asia/Saigon` → `Asia/Saigon`) while mapping older ones (`Japan` → `Asia/Tokyo`), so the explicit `LEGACY_IANA_TIMEZONE_ALIASES` table is the source of truth and `Intl` only the fallback. Do NOT pass `parsed.data.timezone` straight into a day-bucket query.

**Two diagnostic tells this cost a fortnight of a customer's Overview chart (2026-08-08):** (a) the failure is **DATA-DEPENDENT** — `AT TIME ZONE` is evaluated per ROW, so the same zone with a filter matching nothing returns 200 and only a request that actually aggregates rows 500s; (b) it is **not** a validation bug — the zone is valid IANA and passes the schema's `Intl` refine, so it is a 500 from the handler catch, not a 400. Chain: instantly `/orgs/stats` 500 → email-gateway → features-service `/pipeline-activity` → dashboard 502 (a chart that never loads) for whole timezones (Vietnam, Ukraine, India, Argentina, Myanmar, Japan, US/*). A residual unknown zone now returns **400 naming `timezone`**, and any other aggregation failure carries `detail` in the 500 body — the opaque body is what kept this undiagnosed. Guard: `tests/unit/timezone.test.ts` + the legacy/primary-pair and 400/500-shape tests in `tests/unit/stats.test.ts`.

### Campaign-fact gold (`contacted`/`notSending`/`cancelled`) — bucket the SAME rows the cumulative count uses

`contacted` is a campaign-table fact (one `instantly_campaigns` row = one lead pushed), NOT an event — cumulative non-day `contacted` = `COUNT(*)` over `instantly_campaigns` (`queryCampaignAggregates`). For `groupBy=day`, `queryGroupedCampaignAggregates` buckets those SAME rows by `localDayKey(c.created_at, tz)` (`campaignGroupColumn`), so **day-sum == cumulative `contacted` by construction**. `created_at` IS the contacted timestamp (CLAUDE.md: `firstContactedAt = MIN(c.created_at)`). Do NOT re-source per-day contacted from a different table (`instantly_lead_status_current.first_contacted_at` etc.) — a different row set risks count drift vs the cumulative number. **`queryGroupedStats` UNIONs aggregate-only keys into the groups for EVERY grouping dimension — `audienceId`, `campaignId`, `featureSlug`, `workflowSlug`, `brandId`, `leadEmail`, `day` — not just `day`.** The grouped result set is built from the EVENTS table, so a key whose leads were pushed but for which Instantly has not yet emitted a single event had no group at all, and every downstream consumer (email-gateway → features-service → dashboard) read that absence as `contacted = 0`. Leads are pushed minutes-to-hours before the first send event, so this hit any freshly-started audience: the dashboard Audiences table showed "Outreach 0" beside a "Remaining" column already decremented from the serve-time suppression list — two surfaces contradicting each other for the same audience. A synthesized group carries the real campaign-derived counts (`contacted`/`notSending`/`cancelled`) and **zero for every event-derived metric** — nothing fabricated. Do NOT re-gate the union on `groupBy === "day"`. Note the aggregates query reads `instantly_campaigns` and has NO `e` alias, so its group column comes from `CAMPAIGN_GROUP_BY_COLUMNS` (identical to `GROUP_BY_COLUMNS` except `leadEmail → c.lead_email`); borrowing the events column made `groupBy=leadEmail` 500 with `missing FROM-clause entry for table e`. Historic bug (v0.46.1): day mode hard-coded the aggregates to an empty Map → every day bucket showed `contacted=0` → dashboard "Pipeline activity" Outreach=0 despite real outreach. Guard: the groupBy-day tests in `tests/unit/stats.test.ts` (3-call order [events, aggregates, sentiment]; day-sum==cumulative; contacted-but-no-events day surfaces) plus the zero-event `audienceId`/`featureSlug` and `leadEmail`-column tests beside them.

**Emit the parameterized `localDayKey` fragment EXACTLY ONCE per query — name it `group_key` in a CTE, then reference the alias everywhere else. NEVER interpolate `${groupCol}` more than once (and NEVER inside a `--` comment).** For `groupBy=day`, `groupCol` is `localDayKey(...)`, which carries the `${timezone}` bind. drizzle's `sql` tagged template re-emits that bind on EVERY `${groupCol}` interpolation — **including ones textually inside a `--` SQL comment** (drizzle builds the param list from interpolations; it does not parse SQL, so a comment is NOT inert). Two distinct failure modes from re-interpolation:

- **`42803`** — `${groupCol}` in both SELECT (`$1`) and `GROUP BY` (`$N`): Postgres matches grouped columns by exact expression incl. param position, so the mismatched placeholders trip `column "c.created_at" must appear in the GROUP BY clause`.
- **`08P01`** — `${groupCol}` in a `--` comment: drizzle binds the extra param but Postgres strips the comment before execution, so the executed SQL has N placeholders while N+1 params are bound → `bind message supplies N+1 parameters, but prepared statement requires N`.

The `GROUP BY 1` ordinal fix (v0.46.2, ab85fdc) dodged `42803` but its own explanatory comment still interpolated `${groupCol}` → `08P01` → every `/orgs/stats?groupBy=day` 500'd → features-service pipeline-activity 502'd (v0.46.3). The robust fix (v0.46.3): all three grouped day queries — `queryGroupedStats` (events), `queryGroupedSentiment`, `queryGroupedCampaignAggregates` — now use the SAME CTE shape: `SELECT ${groupCol} AS group_key ...` once inside a CTE, then `GROUP BY group_key` on the alias. No inline repetition, no ordinal hack, no comment interpolation. Non-day groupings keep the inline form (`groupCol` is `sql.raw(col)`, param-free, byte-identical every interpolation). Unit tests mock `db.execute` so they CANNOT catch param-drift at runtime — the guard is the static-SQL assertions in the day tests (`aggregateSqlText` contains `AS group_key` / `FROM grouped_campaigns c` / `GROUP BY c.group_key`, and `not.toContain("GROUP BY 1")` / `not.toContain("GROUP BY TO_CHAR")`). Any NEW grouped day query needs the same CTE shape + assertions.

### Silver inference (synthetic predecessors)

When a "downstream" event lands (e.g. `email_opened`) without a preceding "upstream" event (e.g. `email_sent`), silver promotion synthesizes the missing predecessor deterministically. Rules:

| Trigger | Inferred predecessors |
|---|---|
| `email_opened` step N | `email_sent` step N |
| `email_link_clicked` step N | `email_opened` step N + `email_sent` step N |
| `reply_received` step N | `email_sent` step N |
| `email_bounced` step N | `email_sent` step N |
| `lead_unsubscribed` step N | `email_sent` step N |
| `email_sent` step N | `email_sent` steps 1..N-1 (sequence cascade) |

Synthetic rows carry `inferred=true`, `source='inferred'`, `inferred_from_event_id` (audit), and `inferred_rule` (rule name). Timestamp = trigger event timestamp.

**One-shot upgrade:** for at-most-1-per-step event types (`email_sent`, `email_bounced`, `lead_unsubscribed`, `reply_received`), partial unique index `instantly_events_one_shot_dedupe_idx` enforces that. When a real webhook arrives after inference projected the event, the synthetic row is upgraded in place (`inferred=true → false`, real timestamp wins). Side effects fire because this is the first time the real signal is observed.

**Side effects on inferred events:** SKIPPED. Synthetic events are projection-only. `delivery_status` / `cost lifecycle` / `reply classification` update only when real external signals arrive.

**Backfill:** `npm run backfill:inferences` re-projects predecessors for every existing real silver event. Idempotent. CLI only — must not run in boot path.
