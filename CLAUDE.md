## Architecture

- `src/index.ts` Express entry · `src/schemas.ts` Zod (source of truth for validation + OpenAPI) · `src/zod-setup.ts` extends Zod with `.openapi()`, import BEFORE any `.openapi("Name")` schema · `src/routes/` handlers · `src/middleware/serviceAuth.ts` · `src/lib/instantly-client.ts` · `src/lib/runs-client.ts` · `src/db/schema.ts` Drizzle · `openapi.json` auto-generated, never edit · `tests/{unit,integration,helpers}`.
- **Gold stats are derived-on-read from silver** (`analytics.ts`/`status.ts`). NO `analytics_snapshots` table; do not add a snapshot TABLE cache.
- **RULE: any route that live-aggregates the silver event log AND is called by email-gateway on the send/retry path MUST wrap its DB work in `getOrSetCachedStats`** (`src/lib/stats-cache.ts`, 60s, per replica, in-flight dedup). email-gateway retries on its ~10s abort and the abort does NOT cancel the server query, so each retry stacks another heavy aggregation on the pool (max 20): the `timeout exceeded when trying to connect` flood. Cached today: GET `/stats`, GET `/public/stats`, POST `/orgs/status` (key orgId+brandId+campaignId+sorted emails), GET `/internal/audit/sending-forecast` (key `sending-forecast`). Audit every email-gateway-hit aggregation route before adding one; call `clearStatsCache()` in a new route's unit-test `beforeEach`.
  - Supporting: `instantly_events_stats_covering_idx (campaign_id, event_type, lead_email, step)` (index-only scan on filtered `/orgs/stats`); `queryStats`/`queryGroupedStats`/per-step block parallelise with `Promise.all`; **`work_mem='32MB'` per pool connection** (`src/db/index.ts`): at the pg default 4MB the `COUNT(DISTINCT lead_email)` sort spills to disk and starves the pool. Do NOT lower it; worst case `max:20 x 32MB` on a DB host shared fleet-wide.
- **Pool (`src/db/index.ts`)**: `max:20`, `idleTimeoutMillis:60_000`, `keepAlive:true`, `connectionTimeoutMillis:5_000` (was 15s: a starved acquire blocked the next request the full 15s before `withConnectRetry`). Do NOT raise it back.
- `src/lib/stop-lead-sequence.ts`: the ONE "stop sending for this lead", branching on transport (Instantly pause vs `stopSelfSendSequence`). Callers: manual qualification, IMAP poller, inbound-replies backfill (all learn about a reply Instantly did not see). Fail-soft: the reply is already recorded, a failed pause is logged.
- `src/routes/audit.ts`: staff ops, platform-scoped (no org). `GET /internal/audit/sending-forecast`; `POST /internal/audit/accounts-sync` (snapshot accounts to bronze/silver + `reconcileLifecycle`, 202 + background, first step of the placement cron); `GET /internal/audit/capacity-history?days=N` (1-365) reconstructed from `instantly_accounts_raw` + lifecycle events. Each day = RAMPED per-MAILBOX capacity AS-OF that day, every day emitted even at zero; points before 2026-09-05 read lower on purpose (no warmup/seed mail yet). Guard `capacity-history.test.ts`.
- `src/lib/account-lifecycle.ts` pure `deriveLifecycle` (4-state, first-match-wins); `account-lifecycle-sync.ts` `reconcileLifecycle` IO (PATCH warmup on flip, insert lifecycle event, update silver).
- `src/lib/sending-window.ts` pure: which UTC day a send books on a mailbox via the LEAD's own Mon-Fri 08:00-17:00 local window (`nextLocalSendInstant`, `sequenceFootprintDays`, `isWithinLocalSendWindow`). Used by send selection, capacity snapshot, self-send dispatcher; NEVER by ops projections.
- `src/lib/scheduled-replies.ts` + `scheduled-replies-worker.ts`: what is left of the waiting room for answers held before 2026-09-25 (`planScheduledReplies`: draft <=15 min send now; older automated draft superseded and lead re-queued in lead-service; a human's words sent). Drained from `runDispatch`; nothing enqueues any more.
- `src/lib/self-send/` and `src/routes/unsubscribe.ts` (public HMAC opt-out `/u/:payload/:signature`, GET renders confirmation, only POST unsubscribes): see the nested CLAUDE.md.

## Shared contract and code-level traps

- **Shared contract**: cross-provider shapes (`StatusScope`, `RecipientStats`, `EmailStats`, `StepStats`, `RepliesDetail`, `ChannelStats`, `ProviderStatus`, `GlobalStatus`, `ReplyClassification`) come from `@shamanic-technologies/email-domain-contract` (pinned `^1.1.0`); re-export via `src/schemas.ts`, never redeclare. `cancelled` and `notSending` are optional in v1 but always emitted here. **The 8 first-occurrence MIN timestamps** (`firstContactedAt, firstSentAt, firstDeliveredAt, firstOpenedAt, firstClickedAt, firstRepliedAt, firstBouncedAt, firstUnsubscribedAt`) are populated on every StatusScope by `POST /orgs/status` (`src/routes/status.ts`); `first*At = MIN(event ts in scope)`, null iff boolean false; brand = MIN across campaigns; `firstContactedAt = MIN(c.created_at)`; `firstDeliveredAt` = sent AND NOT bounced. Set locked to the contract: do not rename or add a 9th. Guard: "First-occurrence (MIN) timestamps — DIS-229" in `tests/unit/status.test.ts`.
- **Zod 4**: contract schemas instantiated before `extendZodWithOpenApi` do not gain `.openapi()`; re-export them without `.openapi(name)` so the generator inlines them. Local schemas after `import "./zod-setup"` keep tagging.
- **`db.execute` returns a `QueryResult` (`{rows,...}`), NEVER an array** (node-postgres; postgres.js returns arrays). Read through a private `rowsOf(result)` or `.rows`; do NOT cast a result to an array type. Unit mocks of `db.execute` must return the real driver shape (`pgResult()` helper in `tests/unit/transport-split.test.ts`), else suites pass against code that cannot run. Cost 2026-08-30 (v0.75.1): an array cast threw `rows is not iterable` on every `POST /orgs/send` for 13 h after the lead was already generated and paid for; sending restored by disarming `SEND_TRANSPORT_AB_ENABLED`.
- **node-postgres returns non-int arrays as RAW TEXT** (`numeric[]` -> `"{3,7,0}"`, truthy, so `?? []` does not catch it): return `COALESCE(jsonb_agg(expr ORDER BY ...), '[]'::jsonb)`, guard non-array sources, and `Array.isArray(x) ? x : []` in mappers. Mocked tests cannot catch it; validate array SQL against the real DB (`docker exec distribute-postgres-1 psql -U postgres -d instantly_service`). Cost: `loadPendingLeads` 500'd the fleet forecast (v0.59.1).
- **Instantly client pagination**: any helper returning "all of X" MUST paginate via `next_starting_after` (like `listAccounts`, `listLeadsFull`, `listEmails`), `limit=100` (larger silently returns empty; default page is 10). Each needs unit tests for multi-page traversal, termination on `next_starting_after=null` and on empty `items` (`tests/unit/instantly-client.test.ts`). Caller-driven `skip`/`limit` helpers need a stated reason. Cost 2026-05-28: unpaginated `listAccounts` left 146 of 156 senders idle.

## Account selection (`src/lib/send-lead.ts`, lifecycle-gated, read from silver)

Two stages. **1. `fetchInProductionAccounts(featureSlug)`**: eligible pool read PURELY from silver `instantly_accounts` (no live `listAccounts` on the send hot path); sendable iff `lifecycle_status == 'in_production'` (auto-derived, see Account lifecycle). No `MIN_WARMUP_SCORE`, `BLOCKED_DOMAINS` or manual flag exists. Empty pool = `no_healthy_accounts_available` (500 upstream), NO fallback to weaker senders.
- **Feature carve-out** (`instantly_account_feature_policy`, migration `0030`): `x-feature-slug` scopes the pool via LEFT JOIN; a RESERVED slug (present in the table) draws only its accounts, a non-reserved or null slug draws the UNRESERVED accounts. Reserved set derived from the table, no constant. **The table is currently EMPTY** (migration `0031` removed the `sales-crm-email-outreach` reservation 2026-07-28): every feature and a null slug draw the WHOLE `in_production` fleet (six cold-email features share it). Carving a feature out is a data change. A reserved slug with no reserved account in production fails loud, never falls back to the shared pool. The `::text` cast on the bound slug is required. Guards: feature-pool tests in `send.test.ts`.

**2. `pickSequentialFillAccount(accounts, capacityByEmail, asOf?)`**: saturate the FIRST account of a fixed order before touching the second (first account of `accountFillOrder` whose `load < cap`). The tail going idle is the OBJECTIVE (the fleet is over-provisioned, an even spread means nothing can be cancelled); do NOT restore the fill-ratio policy (#543). Lineage: random, `pickLeastLoadedAccount`, capacity tiers (#513), fill-ratio (#543), sequential fill. The age/ramp cap still applies, `in_production` gate and carve-out unchanged, an account absent from the snapshot has full room, `daily_limit` 0 is skipped. Followups are NOT re-selected (the tail keeps dispatching for a sequence length; the delete signal is "no real `email_sent` for N days").

- **Tier order is INCREASING COST, so expensive tiers go silent and become cancellable** (`providerFillRank(provider, vendorPrewarmedAt)`, `PROVIDER_FILL_RANK` constant with cost rationale beside it): 0 `gandi` (registration only) / 1 `mailforge` ($14/yr domain) / 2 `primeforge` own domain ($4.50/mailbox/mo) / 3 `primeforge` PRE-WARMED ($9/mailbox/mo, discriminator `vendor_prewarmed_at`, migration `0052`, tiers ONLY primeforge) / 4 `instantly-dfy` ($10/mailbox/mo AND tied to the $97 Outreach plan) / 5 unknown (no `infra_domains` row) LAST, never fabricate. **A freshly bought batch is rank 5 until the daily infra sync (05:00 UTC)**: `POST /internal/infra/sync` is part of importing a batch.
- **`accountFillOrder` = vendor ASC, domain acquisition date ASC, domain NAME ASC, `timestamp_created` ASC, `email` ASC; undatable domain last within vendor, unattributed vendor last overall.
