# Warmup mesh (`src/lib/warmup/`: `plan.ts` pure pairing + reply decision, `message.ts` body per email, `run.ts` send, `poll.ts` read/rescue/reply)

Our own mailboxes keep each other warm (replaces Instantly's bundled warmup pool). Bronze `warmup_dispatches` + `warmup_receipts` (migration `0050`). Routes `POST /internal/audit/warmup/{run,poll}`, `warmup-cron.yml` two daily schedules (07:00 send, 12:00 read). Armed by `WARMUP_MESH_ENABLED=true`, default OFF (409, tolerated by the cron). Nothing promotes to silver (a warmup email is not outreach; an `email_sent` would corrupt step accounting, queue attribution and the re-contact window). Honest scope: ~200 mailboxes in a closed mesh is a weak signal; the seed placement score (receivers the mesh never touches) is how we know whether it works.

- **Production data (2026-09-06, Gandi fleet) shapes the constants**: 0 real sends/30d = 94 accounts, mean seed score 15.9%; 50-199 = 28 accounts, 48.6%; 200+ = 7, 28.6%. Uniform warmup on an idle mailbox buys almost nothing (94 accounts warmed 30/day for six weeks, health 95.6, flat 34-36%), so the mesh is MODEST (`WARMUP_PARTNERS_PER_DAY = 4`), not a volume replacement. Correlational, not causal.
- **The measurement RECEIVERS are held out of the mesh (`partnerCandidates`): the invariant the design rests on.** Rescuing a message from a receiver's spam trains its filter, so a receiver that both grades and rescues returns a verdict it was trained to give (score drifts optimistic and the delivery gate stops catching anything). Never let seed receivers double as warmup partners.
- **`loadRoom` does NOT filter `absent_since`; restoring it turns a mailbox receive-only** (`absent_since` = left the Instantly workspace; the mailbox and its credential still exist). `partnerCandidates` draws on the credential map while the room query would drop it (`kevin@distribute.you`: 67 received, 0 sent). The genuine ghost is excluded for free (`if (mailbox === undefined) continue`). Guard `warmup-room.test.ts`.
- **A different body PER EMAIL, never one per day** (identical bodies are the bulk signal); `topicFor` rotates a topic seed per (day, sender, receiver). Spend is chat-service (`deepseek-flash`, thinking off), none declared here. **The LLM fallback is a real path, not degraded** (nothing is asserted; an outage must not abort the send; the fallback still varies per edge).
- **Warmup spends the same daily quota as outreach and BOTH sides enforce it**: `runWarmupMesh` room = `capForAccount(...) - (real sends today + warmup today)`; `loadSendingAccounts` adds `warmup_dispatches` of the UTC day into `sentToday`. Both at real-MAILBOX grain. A REPLY is a send recorded in `warmup_dispatches`.
- **Every warmup subject carries a constant `WRM` token** (so a human can `subject:WRM`-filter mail pulled into a personal Gmail via POP/catch-all forwards), a deliberate bounded trade against varied bodies (three letters in a reference-like suffix with a varying code). If mesh deliverability looks worse than the seed harness predicts, suspect it first; better fix is upstream (stop pulling fleet mail into a personal inbox).
- **The budget counts the DAY, not the run** (seeded from what warmup already sent today per mailbox; 2026-09-06 three runs put 17 sends on a budget of 4; the real cap held). **A silenced mailbox stops sending but keeps receiving (`selectSilencedSenders`)**: >= 3 failures with ZERO successes in 7 days (`kevin@growthagency.cloud` 20 failures, `550 5.7.1 Blacklisted user`); self-healing; `skippedSilenced`. **A failed reply costs its message, never the mailbox** (`repliesFailed`).
- **The poll asks the server for OUR messages (`SEARCH HEADER Message-ID`), never walks the mailbox**, receivers at `WARMUP_POLL_CONCURRENCY` 8; **fetches the envelope, never the source** (the same rule governs `self-send/imap-poller.ts`; `source: true` read 6 of 361 messages in 20 min). **Distinct mailboxes in parallel, a mailbox's aliases in sequence (`POLL_MAILBOX_CONCURRENCY` 8, grouped by `loadMailboxLogins`; the unit is the SASL login, never the address)**; the dispatch poll is on the critical path of every send (45-80 min sequentially on 249 accounts). Guard: per-login peak 1 in `imap-known-sends.test.ts`.
- **The receipt existing is NOT the message having been acted on**: the receipt is written BEFORE the rescue, so the skip is keyed on the ACTION (already in inbox = nothing to do, already rescued = done, else retry; `\Seen` and move are idempotent). **The observation is frozen BEFORE the rescue** (receipt unique on `(message_id, receiver_email)`, first-observation-wins; reversed, every message would look like it arrived in the inbox).
- **One address per real mailbox, warmup takes a FRACTION of the cap**: `partnerCandidates` collapses aliases to one deterministic participant (5.7 sends per mailbox instead of 4); `warmupBudgetFor` caps at `WARMUP_MAX_SHARE_OF_CAP` (30%) floored at 1 (402 of 784 edges lacked room on the first run).
- **Pairing (`planWarmupPairings`)**: deterministic per (UTC day, mailbox) (re-run plans the same edges, unique index = idempotent with no cursor); never reciprocal the same day (warmup-ring shape); never same-domain; graph changes daily. `shouldReplyTo` keyed on message id, ~1/3 (answering everything is a pattern).
- **Do NOT chain the poll onto the run** (both 202; five hours apart; poll re-reads a 3-day window). Weekends NOT excluded (silence two days a week is a pattern; the Saturday seed test uses a different receiver population).
