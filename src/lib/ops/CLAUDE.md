## Per-account throughput columns on `account-health` (`account-sending-stats.ts`, pure map in `account-health.ts`)
All derived from OUR data or the Instantly account object, honest `0`/`null`, never fabricated.
- `sentToday` = `COUNT(*)` of REAL (`inferred=false`) `email_sent` events today UTC by `account_email` (`fetchSentTodayByAccount`). `sentYesterday` same provenance, window bounded to the full previous UTC day `[date_trunc('day',now)-1d, date_trunc('day',now))`; mirror that bounded form for any new day window, not the open-ended `sentToday` shape.
- `warmupLimit` = `account.warmup.limit` off the list row (distinct from `dailyLimit`). `GET /accounts` LIST carries `warmup` ABBREVIATED to `{limit}`; `increment`/`advanced` only on single-account `GET /accounts/{email}` (why `setWarmupDailyLimit` GETs first).
- **`queuedFirstUnsentSequences`** (never-contacted leads = first emails due) vs `queuedFirstUnsent` (every remaining STEP of those sequences). **An ops "queued today" figure MUST be `queuedFirstUnsentSequences + queuedNextToday` against `dailyLimit`** (the number the selector decides on; the step total makes a healthy account read 102 against a 45 cap). Both stay exposed.
- **`queuedFirstOverdueSequences`** = STUCK subset of `queuedFirstUnsentSequences` (never-sent first email whose campaign `created_at` UTC day < today; `isOverdueFirstEmail`). `queuedFirstDueTodaySequences` = unsent minus stuck (served, consumers never subtract; selector load still counts stuck ones, they are owed today). **`newSequencesToday`** = campaign rows CREATED today per `account_email` (any state, `reserving:` excluded; `fetchNewSequencesTodayByAccount`), NOT a queue figure. Before #969 a never-sent first email read as "due today" for months (566 rows, 2026-10-02). Guards: "firstOverdueSequences" in `queue-breakdown.test.ts`, "new sequences assigned today" in `account-health.test.ts`.
- `queueSize` = queued-but-unsent STEPS per account (`fetchQueueSizeByAccount`): `provisioned` holds on active campaigns (same gate as `loadPendingLeads`: active + `delivery_status IN ('contacted','sent')`), distinct steps, attributed via `COALESCE(persisted account_email, observed email_sent account)`; NULL account with no real send is excluded, never fabricated.
- `accountType` via `mapProviderCode` (**1 `imap`, 2 `google`, 3/4 `microsoft`**, else null; the 185 `provider_code 1` are the Gandi/Mailforge IMAP fleet, 81 `provider_code 2` Google). It is the CONNECTION provider, not the provisioning class (that is the infra inventory). Guards: `account-health.test.ts`, `account-health-route.test.ts`.

## Queue breakdown (`queue-breakdown.ts` pure, `fetchQueueBreakdownByAccount` IO)
- Four buckets PARTITION the queued STEPS: `queueSize === queuedFirstUnsent + queuedNextToday + queuedNextTomorrow + queuedNextLater`. `queuedSequences` (lead count) is a different granularity, exposed alongside. **`queuedOverdue` is a SUBSET of `queuedNextToday` (nominal due strictly before today = backlog), NEVER added into the four-bucket sum.** `queueSize` on the row is sourced FROM the breakdown's step total.
- Inputs all LOCAL: distinct un-sent `sequence_costs` steps + last-sent step/timestamp, and the per-step `delay` array from the LATEST bronze sequence config. **Delay indexing: cost steps 1-based, config `steps` 0-based, gap `k -> k+1` = `steps[k-1].delay`, via the SHARED `delayForGap(fromStep, stepDelays)` from `sending-forecast.ts`** (+ `STEP_GAP_CALENDAR_DAYS` fallback; never a second copy). Projection chains hops: `projected(s) = lastSentAt + sum delayForGap(hop)` over every remaining step.
- **The projected date is a NOMINAL-CADENCE LOWER BOUND that compounds** (actual dispatch slips: a 3-day gap actualizes ~7.6 d under backlog); `queuedNextToday` = due today-or-overdue, not "will send today". Never relabel as an exact schedule. A never-contacted sequence has no anchor: all its steps count under `queuedFirstUnsent`, never date-projected here (selection DOES project them); only its FIRST email has a due day (assignment day, `queuedAt`). Per-campaign non-sending days/timezone are NOT modeled (raw nominal UTC date, no weekend snap); missing config falls back per hop (prod 4,926/4,926 have config). Unattributable steps excluded.
- **Forecast and breakdown share ONE cadence model and ONE day-bucketing model** (raw nominal UTC day, past-due clamped to asOf, NO weekend snap, NO base-clamp `max(lastSentAt, asOf)`), so the forecast's per-day `scheduledCount` reconciles with fleet-aggregated `nextToday`/`nextTomorrow`. Do NOT reintroduce either. Guards: `queue-breakdown.test.ts` (chained projection + steps-sum invariant), `account-health.test.ts`, `account-sending-stats.test.ts`, `sending-forecast.test.ts`.
