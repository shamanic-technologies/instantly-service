# Self-send transport (`src/lib/self-send/`, `src/routes/{self-send,unsubscribe,click}.ts`)

We dispatch our own mail from the same mailboxes to drop the $97/mo Instantly Email Outreach plan (#590). Instantly stays an SMTP relay for the DFY pool, a webhook emitter and a scheduler we cannot see. Cadence (`delayForGap`), caps (`rampCapForVolume`, `dailyLimitForStatus`), account choice (`accountFillOrder`), cost lifecycle and silver log are ours. Files: `transport.ts`/`capability.ts` (which pipe), `mailbox-credentials.ts`, `sequence-steps.ts`, `unsubscribe.ts`, `click-tracking.ts`, `message.ts`, `smtp.ts`, `dispatch.ts` + `dispatch-worker.ts` + `dispatch-scheduler.ts`, `sender-health.ts`, `inbound.ts` + `imap-poller.ts` + `instantly-sends.ts`, `inbox-watcher.ts`, `qualify-reply.ts`, `stop-sequence.ts`, `thread.ts`.

## Transport and credentials
- **ONE fact decides the pipe: do we hold a credential?** `capability.ts` `resolveTransportForNewSequence`, called by `POST /orgs/send` right after the account is chosen, frozen on the campaign row (`instantly_campaigns.send_transport`). Credential = `smtp`, none = `instantly` (DFY pool). **Do NOT reintroduce a stored policy as an input**: the old per-sequence A/B split loaded capacity only for accounts whose POLICY said smtp, freezing 1,486 sequences (1,176 never-contacted leads, already enriched and paid for) with `due: 0` and zero errors (prod 2026-09-06). `instantly_accounts.send_transport` is no longer an INPUT anywhere (`reconcileLifecycle` is its only writer, derived, for the ops table; `imap-poller` may read it). Capability is POSITIVE evidence; `loadCredentialedMailboxes` fails LOUD on anything but a key-service 404. Rollback lever = `SELF_SEND_DISPATCH_ENABLED=false`. The DFY carve-out (42 accounts, 9 domains: no `infra_mailboxes` row, no credential) needs no tag today; an explicit `is_dfy` column is deferred. Every send now depends on key-service (cached 60s via `getOrSetCachedStats`).
- **Two `send_transport` columns, not redundant (migration `0035`)**: account = policy-derived, campaign = DECISION frozen at send (a sequence spans days; reading the account live would strand followups mid-flight since an Instantly-pushed lead holds no local step bodies). `resolveTransportForSend` maps anything not exactly `'smtp'` to `'instantly'` (deliberate asymmetry).
- **SMTP goes out on 587 with mandatory STARTTLS** (`requireTLS: true`, `secure: false`); the box blocks outbound 465 and 25. Probe outbound paths from the BOX, never only a laptop. IMAP `imap.gmail.com:993`. Primeforge 16-char `appPassword` authenticates both; do NOT use `smtp.google.com`/`imap.google.com` or the vendor `password`.
- **ONE credential resolution for sending AND measuring: `resolveMailboxCredential`** reads the MANUAL key-service list first (`mailbox-credentials` platform key, JSON array `address, appPassword, smtpHost, imapHost, authUser?`; Gandi/Mailforge passwords are hand-entered), then Primeforge (platform key + DIRECT REST `/mailboxes` pagination; the forge CLI/MCP return only 10). Manual wins. Do not add a second resolver: the seed harness only wraps it in a batch loader (`loadSeedCredentialResolver`; unresolvable = skipped there, THROWS on the send path). 404 on the manual key = none configured; any other failure propagates.
- **Layering: silver does NOT fork.** Everything promotes through `promoteEvent` into `instantly_events` + `instantly_campaigns` (table name stays). New: `sequence_steps` (SILVER, step bodies; `step` 1-based, `delay_days` = gap AFTER the step, null falls back to `STEP_GAP_CALENDAR_DAYS`, `stepsFromSequenceConfig` drops body-less steps and renumbers; guard `self-send-foundation.test.ts`); bronze named for the transport: `smtp_dispatch_raw`, `imap_messages_raw`, `tracking_hits_raw`. The queue is still the `provisioned` `sequence_costs` rows; no schedule table.
- **`POST /orgs/send` branches on transport BEFORE the Instantly call** (`selectSendingAccount` split out so both paths use it). Reading it only at phase-2 (v0.73.1) double-sent every email. Guard: "does NOT create an Instantly campaign when the account is on smtp". Phase-2 freezes `send_transport` through `resolveTransportForSend` and persists bodies via `stepRowsFromSendPayload` for BOTH transports. **The delay shifts by one**: payload `daysSinceLastStep` is the delay BEFORE a step, `delay_days` the delay AFTER it (step k stores step k+1's value, last stores null, step 1's is discarded).
- **Self-send `instantly_campaign_id` is a local `self:<uuid>`** (`mintSelfSendCampaignId`); column stays `notNull().unique()`. **Any sweep over `instantly_campaigns` that calls Instantly per row MUST exclude `self:%` (and `reserving:%`)**; excluded in `reconcileAll`, `selectOneStuckRow`, `cleanup:escaped-newlines`, `cleanup:stacked-signatures`; `SELF_SEND_CAMPAIGN_LIKE` kept in lockstep by a test.
- **The message uses the EXISTING `buildEmailBodyWithSignature`** (`message.ts`), never a second copy; `subjectForStep` prefixes `Re:` once; `In-Reply-To`/`References` thread. Guard `self-send-message.test.ts`.
- **Every campaign side effect that "pauses on Instantly" needs a LOCAL equivalent, and the asymmetry reverses.** Instantly transport: pause on Instantly, write nothing locally, let nightly reconcile's `finish` cancel holds (marking terminal yourself makes `reconcileAll` skip it and leaks holds). Self-send: no campaign and reconcile skips `self:`, so `stopSelfSendSequence` (`stop-sequence.ts`) does both, cancel holds (refund) THEN mark the row. Branched in `stop-on-click.ts` and `manual-qualifications.ts`. Guard `self-send-side-effects.test.ts`.
- Not in scope: the $47/mo Inbox Placement plan (survives cancelling Outreach, replaced later by our seed harness). Cancelling Email Outreach PAUSES the Instantly DFY accounts: retire that pool first. `DELIVERY_EVIDENCE_MAX_AGE_DAYS = 16` makes the placement plan a hard deadline (no fresh test, whole fleet stops).

## Unsubscribe and click tracking
- **Unsubscribe ships with the SENDER.** URL only in the `List-Unsubscribe` header, never as a visible body link (see Send path footer rule). Stateless: `/u/<base64url(campaignId:leadEmail)>/<HMAC-SHA256>` (`unsubscribe.ts`), constant-time compare, bad MAC and unknown campaign both 404. **GET renders a confirmation, only POST unsubscribes** (corporate link scanners fetch every URL; RFC 8058 is POST). Both hits recorded in bronze. The opt-out reuses `promoteEvent` (real `lead_unsubscribed`), never reimplement. Guard `unsubscribe-route.test.ts`.
- **`SELF_SEND_PUBLIC_URL` is its own var** (neutral domain CNAME'd here; a brand domain would put it in the cold stream) and `SELF_SEND_UNSUBSCRIBE_SECRET`; both read LAZILY at use so a service without them still boots.
- **Click tracking** (`click-tracking.ts`, `src/routes/click.ts`): `rewriteLinksForTracking` runs LAST, skips our own origin (the opt-out link). **Opens are NOT tracked on either transport** (`open_tracking: false`; the pixel costs deliverability; do not add for parity). **The destination is inside the signed payload (JSON, base64url, HMAC), never a `?url=` param** (open redirect); `isRedirectableUrl` refuses non-http(s) even with a valid signature. GET acts (302, not 301). **The route promotes NOTHING**: a hit is recorded undecided and classified later (Click classification). Without it `stop-on-click` never pauses a self-sent lead. Guard `self-send-click.test.ts`.

## SMTP failures
- Classified by reply class (`smtp.ts`): 5xx permanent, 4xx transient, **unclassifiable = transient**. A dispatch with any `rejected` recipient is a failure, never partial success. One connection per dispatch, no pool.
- **A permanent 5xx is NOT automatically a bounce (`classifyPermanentFailure`)**: `recipient` (RFC 3463 `5.1.*`/`5.2.*`, bare 550/551/553) = bad address, promote `email_bounced`, stop sequence; `sender` (`5.4.5` daily limit, `5.7.x` policy) = WE were refused, record it, leave the hold, touch NO lead state. The enhanced-code separator may be a HYPHEN (`550-5.4.5`); a `(?:^|\s)` regex misfiled the commonest Gmail throttle as a bounce.
- Fail-loud PER STEP; every outcome (sent/permanent/transient) lands in `smtp_dispatch_raw`; a step with no persisted body is skipped loudly.

## Dispatch worker (`POST /internal/self-send/dispatch`, `dispatch-worker.ts`, pure `dispatch.ts`)
- Owns no scheduling rules: queue = `provisioned` holds, cadence = `delayForGap`, cap = `min(daily_limit, rampCapForVolume)` computed off the CONSTANT, not live `daily_limit`. 202 + background, log `self-send-dispatch: done`. Idempotent: a step leaves the due set when its hold stops being `provisioned` (`handleEmailSent`).
- **Driven by an IN-PROCESS interval (`dispatch-scheduler.ts`, armed after `listen`); `self-send-cron.yml` is only a BACKSTOP** (GitHub cron fired 6.2/day vs 24 declared). `SELF_SEND_DISPATCH_INTERVAL_MS` default 10 min IS the latency bound. Kill switch `SELF_SEND_DISPATCH_ENABLED` read at EACH tick; it is the ONLY gate (per-account `send_transport` is not a gate).
- **A STOPPED campaign sends no NEW first email; its contacted leads KEEP their follow-ups unless the org cannot go on (`stopped-campaigns.ts`, first thing in `runDispatch`).** Owner 2026-10-06: "stopping a campaign SHOULD NOT pause the followups!!!" campaign-service owns status + `stopReason` and pushes to nobody; the queue ASKS (`GET /campaigns/list`, one call) every tick. Stopped = row `stopped` AND no row of its identity family live. `stopReason` in `CUT_ALL_STOP_REASONS` (`org_teardown`, `payment_declined`, `no_payment_method`) = every queued sequence cut; `manual`/null = only never-contacted sequences (no real `email_sent`, no `actual` hold), contacted ones counted `keptFollowups`. Cut: self-send = `stopSelfSendSequence`; Instantly = pause FIRST, then cancel holds + mark `paused`. Unknown campaign id = left alone. 200/tick, Instantly first; leftovers `notYetStopped`, filtered by the dispatcher. **Fails LOUD: campaign-service unreadable = the run sends nothing.** 2026-10-02 → 10-06 the sweep cut contacted leads too (~2,900 leads); `POST /internal/campaigns/restore-stopped-followups {campaignIds, dryRun}` (`restore-stopped-followups.ts`) re-queued an owner-approved list through the normal cost path. Guards `stopped-campaigns.test.ts` ("customer stop keeps the follow-ups"), `restore-stopped-followups.test.ts`, `self-send-worker.test.ts`.
- **ONE sweep at a time across every trigger: the mutex lives in `runDispatch`** (a contended run returns `skippedConcurrent: true`).
- **A run that can send nothing does NOT read the mailboxes** (probe: two local queries + pure selection + waiting-reply read). A run that sends polls first and RE-TAKES the selection. Summary carries `polled`.
- **A due step still waits for the prospect's business hours** (`selectDueSteps` filters on `isWithinLocalSendWindow(asOf, timezone)`, zone from `instantly_campaigns.timezone`, absent = `DEFAULT_LEAD_TIMEZONE`); stricter than the weekend gate, never looser.
- **Nothing goes out on a weekend** (`selectDueSteps` gates the run on `isSendingDay(asOf)`; overdue steps drain Monday, most-overdue-first). Gate on the RUN, not a snap on due dates. Tests in `self-send-dispatch.test.ts` (fixtures must not sit on a Sunday).
- **At most ONE step per lead per run.** A never-contacted lead is due immediately. A step at or below the last sent is skipped. **An account with NO capacity row has NO room.**
- **A missing credential is the ONLY reason `loadSendingAccounts` excludes an account.** Do NOT re-add `a.send_transport = 'smtp'` (decision already frozen on the campaign) or `a.lifecycle_status = 'in_production'` (lifecycle governs where a NEW sequence is assigned, never whether an assigned one may finish; demotions of 2026-08-29/09-05 stranded 1,031 sequences).
- **Capacity is spent per real MAILBOX, not per address (`AccountCapacity.mailbox`)**: Gandi = one mailbox, several aliases (154 accounts on 44 mailboxes); relay refuses `450 4.7.1 Too many mail per day for sasl <user>`. Grain from `loadMailboxLogins`; `cap` = MIN across aliases, `sentToday` = SUM. Guard: four alias tests in `self-send-dispatch.test.ts`.
- **The daily cap ramps on MEASURED VOLUME, not elapsed time (`rampCapForVolume`, `account-lifecycle.ts`)**: `min(daily_limit, rampCapForVolume(sustained, IN_PRODUCTION_DAILY_LIMIT))`, grows `RAMP_GROWTH_FACTOR` 1.5/day from `RAMP_FLOOR_PER_DAY` 5 (5, 8, 12, 18, 27, 41, 50). A time anchor was rewound by every weekly placement flip (prod 2026-09-07: 197 of 197 mailboxes pinned at 5-13). Rules: (a) **statistic = SECOND-highest day** (the weekly seed test is a one-day fleet burst: peak 78, second 51); (b) **all three sources count** (outreach, warmup, seed; `fetchRecentDailyVolume`), since an `in_recovery` mailbox has only warmup/seed volume; (c) **total per real mailbox and per DAY first, then take the statistic (`sustainedForMailbox`)**; four callers hold the alias map (dispatch worker, warmup mesh, `aggregateCapacityByMailbox`, `sustainedByMailboxForAccounts`); `sync-lifecycle-limits` alone uses the address's own `sustainedFor` (under-states an alias fleet, safe). The sweep writes `daily_limit` on each ACTIVE smtp alias of one login (since 2026-09-29), safe ONLY because Instantly never dispatches `smtp` campaigns (our selector clips per login); never remove the transport check on `enable_slow_ramp` nor extend the smtp branch to anything Instantly dispatches per alias; (d) **window = 7 CALENDAR days** cut on `date_trunc('day', now()) - interval '6 days'`, NOT `now() - interval '7 days'` (rolling cutoff = 8 days, 1,681 vs 1,501 disagreement). Guards: `account-lifecycle.test.ts`, `recent-send-volume.test.ts` (second-highest vs simulated spike).
- **A mailbox the relay keeps refusing is SILENCED (`selectSilencedSmtpSenders`, `sender-health.ts`)**: 3 sender-side failures in 7 days AND `lastSuccessAt < earliest sender-side failure` (a zero-successes test cannot fire: a deprovisioned mailbox worked until its last day; v0.82.19 to .20). Only `sender`-side failures count (re-read via `classifyPermanentFailure`). Grain = real mailbox, alias group takes the LATEST success. Counted as `skippedSilenced`, never folded into `blockedNoCapacityRow`. Self-heals. Guard `self-send-silenced-sender.test.ts` (incl. do-NOT-silence on recipient bounces). Cost 2026-09-18: 4,210 attempts, 240 failures, zero emails in an hour.
- **Summary reports `dueBeforeCapacity` AND `blockedNoCapacityRow`** (`due` is after clipping; `due: 0` hid an 8-day throttle). `blockedNoCapacityRow` = no credential (needs a credential, not patience).
- **A FIRST email must not wait for room that arrives at 20/day**: a never-sent first email is due from `queuedAt` (campaign `created_at`), NEVER `asOf` (stamped `asOf` it sorted behind every overdue followup forever; 678 first emails stuck, sends fell to 359/day). **A stranded FIRST email is rehomed to a production mailbox with room** (`rehomed`; stranded = no room, silenced, or no credential; a FOLLOWUP is never moved; only `adoptsFirstEmails` mailboxes with room after their own due steps; `rehomeFirstEmail` persists BEFORE sending, guarded on nothing sent, appends `metadata.rehomed`).
- **An Instantly sequence that never STARTS is taken back (`stalled-first-emails.ts`, #969)**: run before every dispatch tick (`dispatch-scheduler.ts`, limit 50) and by `POST /internal/self-send/stalled-first-emails {dryRun default TRUE, limit}`. Stalled = `send_transport='instantly'`, active, no `email_sent` and no `actual` hold, after `STALLED_FIRST_EMAIL_SENDING_DAYS` 3 full Mon-Fri days. Instantly's lead record is asked first (a contact there = untouched, logged); the Instantly campaign is PAUSED before anything else (pause fails = row untouched: never two first emails). MOVE = re-key onto a fresh `self:` id (`instantly_campaigns`, `sequence_costs` incl. NULL-id holds, `sequence_steps`, `instantly_lead_status_current`, `instantly_leads`; bronze keeps the Instantly id; `metadata.movedFromInstantly`), same holds, the dispatcher sends/rehomes it. Do NOT flip `send_transport` on the Instantly id instead (`reconcileAll` would read the paused campaign and cancel the moved holds). CLOSE (cancel holds, mark `paused`, `metadata.stalledFirstEmailClosed`) on opt-out, reply/bounce/unsub in the org, a NEWER sequence for the same brand, re-contact window, > `STALLED_FIRST_EMAIL_MAX_AGE_DAYS` 45, no step-1 body, no provisioned hold. Supersedes the disabled retry-stuck redispatch for first emails. Prod 2026-10-02: 560 stalled (321 on Instantly-disabled mailboxes, Instantly showed them `active`/`not_sending_status 1`), 453 moved, 107 closed. Guard `stalled-first-emails.test.ts`.
- **`POST /orgs/status` serves `queued`/`queuedSince`/`awaitingFirstEmail`** on every scope (`queued` = active campaign row with >=1 `provisioned` step; brand scope any, `queuedSince` = earliest). A duplicate `POST /orgs/send` carries `held: {state in_flight|queued|finished, awaitingFirstEmail, queuedSince, remainingSteps}` (`src/lib/held-lead.ts`; a failed lookup omits `held`). Guards: `self-send-stranded-first-email.test.ts`, `held-lead.test.ts`, `status.test.ts`.

## Reading what comes back (`imap-poller.ts`, pure `inbound.ts`)
- **Correlation key = a `Message-Id` we know went out** (`In-Reply-To`/`References`; inside the DSN for bounces). Never match on recipient (replies come from other addresses) or subject.
- **Two key sources**: `smtp_dispatch_raw` AND `instantly-sends.ts` `loadKnownSends` (bronze `instantly_emails_raw`, `payload->>'eaccount' = mailbox`, `ue_type='1'`, `message_id` on 100% of 112,626 rows). The `eaccount` key is served by hand-written expression index `instantly_emails_raw_eaccount_idx` (migration `0065`; without it every poll and every watcher arrival seq-scanned the 270 MB table, ~0.9 s each, the service's top Postgres load); a new per-mailbox read of this table filters on the SAME expression. The second makes an Instantly-DISABLED mailbox readable (its in-flight sequences stay frozen on `instantly`). Our own dispatch wins a collision. Lead comes from the campaign JOIN. `parseInstantlySequenceStep`: `<variant>_<stepIndex>_<subStep>`, `0_1_0` = our step 2; unreadable step DROPS the row. Guard `imap-known-sends.test.ts`.
- **Ambiguity is declined: `correlateSend` returns `matched|ambiguous|none`**, never `.find()` first. Several refs on the SAME sequence = normal (latest step wins); distinct campaigns = ambiguous (stored, WARN, promoted to nothing).
- **The mailbox is the bottleneck, not correlation**: a reply forwarded away without a server copy is unrecoverable. `replies: 0` is not evidence of a matching bug; check the inbox holds threaded mail first (120-day catch-up: 50,725 read, 0 with In-Reply-To; 74 bounces all correlated = positive control). Per-domain retention split (molthost/techmonastery/clawdbot keep months; `marketingagency.*` hold ~1 day) points to a Gmail POP fetch without "leave a copy". Do NOT "fix" forwards (88 Gandi senders are real aliases; catch-alls never fire on aliases; adding the mailbox to a catch-all is a mail loop). Do NOT measure credential coverage from `imap_messages_raw` absence (88 of 90 smtp accounts are in `mailbox-credentials`; aliases of one domain read the same mailbox several times, bronze dedups per `(account_email, message_id)`).
- **A human reply on an Instantly-transport sequence MUST also stop the sender** via `stopLeadSequence`; `promoteEvent` marks the row and cancels holds but tells Instantly nothing (Instantly's own stop-on-reply never fired for a broken mailbox). One helper, three callers.
- **An autoresponder is NOT a reply** (`auto_reply_received`, neutral, absent from `SEQUENCE_STOP_EVENTS`; `isAutoReply` keys on RFC 3834 `Auto-Submitted`, `X-Auto-Response-Suppress`, `Precedence: auto_reply|bulk|junk`, `X-Auto*`). **Classification order: bounce BEFORE auto-reply BEFORE reply** (some systems stamp DSNs `Auto-Submitted: auto-replied`; guard "DSN stamped Auto-Submitted" in `self-send-inbound.test.ts`).
- **Only a PERMANENT delivery failure is a bounce**: `isTransientDeliveryReport` files temporary-delay DSNs as kind `delay`, which promotes NOTHING. Order: RFC 3464 `Action:` (any `failed` = bounce, else `delayed` = delay), then RFC 3463 `Status:` (5.x.x bounce, all 4.x.x delay), then Gmail markers ("Delivery incomplete", "(Delay)"); else bounce. No time heuristic; free-text SMTP codes are NOT read (Outlook quotes `450` beside final `550`). `POST /internal/audit/delayed-dsn-backfill` (`dryRun` default TRUE) re-applies it to stored `bounce` rows (re-points to the later permanent notice or deletes and restores `delivery_status` to `sent`); touched events archived whole in `instantly_events_retracted` (migration `0060`), bronze keeps `payload.reclassifiedFrom='bounce'`; undo via `INSERT INTO instantly_events SELECT (jsonb_populate_record(NULL::instantly_events, event)).* FROM instantly_events_retracted WHERE action='retracted'`. Guard `delayed-dsn.test.ts` (captured prod DSNs). Cost 2026-09-24: 122 of 952 stored DSNs were delays turned bounces.
- A message referencing none of our sends is `unrelated`, stored in bronze (the dedup key and the "why was it missed" record).
- **A prospect answering from ANOTHER address is recovered by a Jev judgment (`orphan-reply.ts` pure, `orphan-reply-sweep.ts` IO; prod 2026-09-24 Doc Dinners: Stacy answered from drblecher@chsmetabolismdoc.com as a NEW email, filed `unrelated`, the sequence kept going).** Three stages, only the last is a verdict: (1) `orphanReplyExclusion` drops structural noise BEFORE any spend (own domains = `instantly_accounts` + `infra_domains` + staff via `own-mail-domains.ts`; lists, autoresponders, DSNs, machine local parts; Instantly warmup tag `INSTANTLY_WARMUP_TAGS` `WNT6JJB` in subject or body; NOT `info@`/`hello@`, small practices answer from those); 716,030 `unrelated` rows/30 d leave 3,128 (~104/day). The poll flags survivors `payload.orphanCandidate` and STORES THEIR BODY. (2) `rankOrphanReplyLeads` offers only leads this mailbox wrote to BEFORE the message that share a name / company domain / subject token (score >= 2, top 8); none = no judgment. (3) `platformJudgment` `choice` (`lead_N` | `none`), act at probability >= 0.75. The judgment is PERSISTED on the row (`payload.orphanJudgment`, every outcome incl. `none`/`no_candidate_lead`; a failed call leaves it unjudged for the next run). A match re-files the row (`kind='reply'`, campaign, step = last step sent BEFORE it, `reclassifiedFrom`) then `promoteEvent reply_received` + `actOnInboundReply` (the SAME helper as a threaded reply: Instantly stop, qualification, opt-out). Routine sweep runs inside `runDispatch` right after the poll, before the re-selection. Backfill `POST /internal/self-send/orphan-replies {dryRun (default TRUE), backfill (default true), sinceDays 30 (max 120), limit}` re-reads missing bodies over IMAP by Message-Id. The sweep also runs on IDLE dispatch ticks (the inbox watcher flags candidates at night). **Do NOT merge the two addresses into one person here**: that is crm-service's (owner 2026-10-08); the recovered reply is filed on the emailed lead's sequence only. Guards `orphan-reply.test.ts`, `orphan-reply-sweep.test.ts`, the Stacy case in `imap-known-sends.test.ts`, idle case in `self-send-cadence.test.ts`.
- **The poll fetches HEADERS first and a body only where the words matter; do NOT put `source: true` back** (`client.fetch({since}, {uid, envelope, headers:true})`; a body only for a DSN, a message that correlates, and an orphan-reply candidate). Structural-noise `unrelated` rows keep a bronze row with `textSnippet: null`. 67,098 messages / 214 mailboxes took ~54 min per run inside the dispatch mutex. `seed-placement/sync.ts` had the same shape. Guard `imap-known-sends.test.ts` incl. the positive control that a correlated reply gets its body.
- **Idempotent WITHOUT a cursor**: re-reads `POLL_WINDOW_DAYS = 3`, unique `(account_email, message_id)` on `imap_messages_raw`. `POST /internal/self-send/poll` accepts `{sinceDays}` clamped `[3,365]` for a one-shot catch-up (the ONLY instrument that reaches replies in a mailbox Instantly could not log into; do NOT build a bronze-side reply backfill, its candidate set is empty). `instantly_events.campaign_id` holds the INSTANTLY campaign id. A stored cursor would silently lose replies.
- **The poll runs INSIDE the dispatch run (`runDispatch({pollFirst:true})`), awaited**, not as an earlier cron step (both endpoints 202; ordering would be hoped-for). A poll failure is logged and does not block sends. The cron calls `/dispatch` only.
- **Reply qualification is ours via chat-service (`qualify-reply.ts`)**: does NOT decide whether to stop (`reply_received` already stops and cancels holds); it decides what the reply MEANS (forward, gold sentiment). Label set = `REPLY_CLASSIFICATION_MAP` (lockstep test; `lead_closed` excluded). **An unusable classification promotes NOTHING, never defaults to neutral** (`unqualified`). Spend through chat-service `POST /internal/platform-complete` (platform run), `deepseek-flash`, thinking off, temp 0, quoted history stripped; needs `CHAT_SERVICE_URL` + `CHAT_SERVICE_API_KEY`.
- **The positive-reply forward rebuilds the thread from BRONZE** (`thread.ts`): `smtp_dispatch_raw` (`outcome='sent'`) interleaved with `imap_messages_raw` (`kind IN ('reply','auto_reply')`), same `ThreadMessage` shape and `htmlToText`.
